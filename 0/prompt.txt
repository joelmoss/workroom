**Finding 1**

`[CRITICAL] (confidence: 7/10)` `macapp/WorkroomSessionProtocol/SessionFrame.swift:32-38` — attach requests carrying the caller's full process environment are encoded with no cap against the wire's own 1MB frame limit, so an oversized environment produces a confusing daemon-unreachable error instead of a clear "payload too large."

```swift
public func encoded() -&gt; [UInt8] {
    var writer = SessionByteWriter()
    writer.writeUInt8(kind.rawValue)
    writer.writeUInt32(UInt32(payload.count))
    writer.writeRaw(payload)
    return writer.bytes
  }
```

versus the receiver's hard cap:

```swift
guard length &lt;= SessionFrame.maximumPayloadSize else {
      failed = true
      throw SessionProtocolError.frameTooLarge(length)
    }
```

Traced end to end: `SessionAttachClient.makeRequest` (`macapp/WorkroomSession/SessionAttachClient.swift:219-230`) builds `SessionAttachRequest.environment` from `SessionProcessEnvironment.current()` — the *entire* OS `environ` of the `workroom-session attach` process, which `GhosttySurfaceView.applyPersistentSession` (`macapp/WorkroomApp/Core/GhosttySurfaceView.swift:397-418`) launches with the full interactive-shell-enriched environment (per `macapp/CLAUDE.md`'s `ShellEnvironment` probe: `.zshrc` exports, tool shims, exported bash functions, etc.). `SessionAttachClient.attach()` (line 92) calls `connection.enqueue(SessionFrame(kind: .attach, payload: makeRequest(configuration).encoded()))` with no size check anywhere in `SessionConnection.enqueue` either.

If the encoded payload exceeds `SessionFrame.maximumPayloadSize` (1&lt;&lt;20), the daemon's decoder throws `frameTooLarge`, and `SessionDaemon.swift:190-198` catches it, logs `"dropping connection with a malformed frame"` to its own (invisible, detached) stderr, and closes the connection *before ever replying*. Back on the client, `SessionAttachClient.receive()` sees EOF with nothing decoded, returns `.retry` (`transportOutcome(isAttached: false)`), and `run()` retries the *same* oversized request `handshakeAttempts` (3) times before giving up with `report("could not reach the session daemon")` — a message that misattributes the failure to the daemon being down rather than the payload being too large. Net effect for the user: that terminal silently never persists across quit, with a misleading diagnostic and no indication of the real cause (an oversized shell environment).

Real-world likelihood of actually clearing 1MB is the soft part of this — typical environments are KBs, but exported bash functions (`asdf`, `direnv`, `nvm` hooks) or a bloated `PATH`/`MANPATH` can genuinely bulk up `environ`; this isn't purely theoretical, and either way the encode/decode contract has zero symmetry (decode enforces the cap, encode doesn't), which is the actual defect independent of exact trigger frequency.

Fix: validate/clamp in `SessionFrame.init`/`encoded()` (or at `SessionAttachClient.makeRequest`) so an oversized attach payload fails loudly and specifically at the source, rather than silently degrading into three doomed retries with a wrong error message.
