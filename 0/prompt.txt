**What actually repopulates the footer on reattach — this is the key finding:** the daemon-side `attach` handler synthesizes fake live escape sequences and feeds them through the *same* live-parsing pipeline used during normal operation, rather than the app calling any restore API:

- `SessionDaemon.attach(session:request:connection:)`, `/Users/joelmoss/dev/workroom/macapp/WorkroomSession/SessionDaemon.swift:343-426`. Before replaying the scrollback buffer, it reads the PTY's **current** foreground process group (`SessionPTY.foregroundProcessGroup`, `SessionPTY.swift:143-146`, via `tcgetpgrp`), resolves its argv0 basename (`SessionPTY.executableName`, `SessionPTY.swift:154-181` — deliberately argv0 via `KERN_PROCARGS2`, not `proc_name`, because Claude Code renames its own title) and its cwd (`SessionPTY.workingDirectory`, `SessionPTY.swift:184-192`), and — only if that foreground group differs from the idle shell's own pgid (line 376-377) — enqueues two synthetic frames *before* the replay:
  - `\u{1B}]2;&lt;name&gt;\u{07}` (OSC 2 title) — `SessionDaemon.swift:390-393`
  - `\u{1B}]7;kitty-shell-cwd://localhost&lt;cwd&gt;\u{07}` (OSC 7 pwd) — `SessionDaemon.swift:394-401`
- Comment at `SessionDaemon.swift:368-375` explains why: title/pwd are normally one-shot escapes from the shell's preexec/prompt hooks, and `SessionReplayBuffer` drops its whole buffer the instant the alternate screen activates (`SessionReplayBuffer.swift:47-148`), so a long-running full-screen program's original OSC 2/7 never survives in the replay buffer and the foreground program itself never re-emits them on its own.
- `enqueueReplay` (`SessionDaemon.swift:454-...`) then sends `session.replay.replayBytes`, which deliberately preserves OSC 0/2 (title), 7 (pwd), 8, 9, 133 in the buffer — `SessionReplayBuffer.swift:323-335` explicitly excludes those from the query-stripping logic ("Title (0/2), pwd (7)... are deliberately excluded: those are always sets").

**Why this needed a fix at all, and what it doesn't fix:** `updateTitle`'s live foreground-PID recognition (`s.view.foregroundAgentBackend` / `foregroundExecutableName`, `GhosttySurfaceView.swift:36-59`) queries `ghostty_surface_foreground_pid(surface)` — the foreground pid of the **locally spawned `workroom-session attach` client's own pty**, not the daemon's remote pty, so it can never see the real agent process on a reattached pane. `updateTitle` (`TerminalSessions.swift:1396-1401`) already falls back to title-string recognition (`AgentTitleRecognition.backend(for:)`) and `ToolLogoRegistry.tool(forTitle:)` when the PID-based lookup misses — which is exactly the fallback path the daemon's synthesized OSC 2 title feeds into, making the whole thing work.
