### Q2 — `SessionPTY.foregroundProcessGroup`/`executableName` (`/Users/joelmoss/dev/workroom/macapp/WorkroomSession/SessionPTY.swift:143-181`)

- `foregroundProcessGroup` returns `nil` whenever `tcgetpgrp` returns `&lt;= 0`.
- `executableName(processID:)` reads `KERN_PROCARGS2` for the given pid — it looks up **argv0 of the process group's own pid**, assuming pgid == the group leader's own pid (true for a normal simple foreground command). If a wrapper script/shebang were involved (e.g. an npm-shim `#!/usr/bin/env node`), the kernel's shebang exec-substitution replaces argv[0] with the interpreter path before `KERN_PROCARGS2` ever sees it — this is a real theoretical gap in the doc comment's claim ("matches what the shell's own preexec title-report already uses"), but **I could not confirm it's what's happening here** (see below).

**Concrete finding, not theory**: I found an actual daemon debug log (`~/Library/Application Support/com.developwithstyle.workroom.dev/sessions/session.sock.log`) containing real `attach()` events for a Codex TUI session:

```

attach 195c5079-...: replaying 10961 bytes: ...&lt;ESC&gt;]2;codex\x07&lt;ESC&gt;]133;C\x07...&lt;ESC&gt;[?2026h... "OpenAI Codex" TUI paint...
```

i.e. the gate at `SessionDaemon.swift:376-377` (`if let group = SessionPTY.foregroundProcessGroup(...), group != session.processID`) fell to the **else** branch and skipped synthesis *even while a genuine full-screen program was actively drawn in the replay*. This is the exact reported symptom (both title AND cwd synthesis skipped by one shared gate — see Q3 below for why that explains both being absent together).

However, checking the **live**, currently-running process tree for a real persisted Claude session (Nightly build) shows the mechanism working correctly right now:

So the gate is not *always* broken — it is at least intermittently wrong. The daemon log I found is dated **Aug 14**, a week stale relative to today's session, so it documents a real past occurrence of the bug but I can't pin today's exact repro to it. This needs a fresh reattach with fresh daemon logging to nail down whether it's still misfiring today, or whether it was specific to Codex's process tree.

### Q5 — callback-wiring race

**Disproved by construction.** `onTitleChange`/`onCwdChange` are assigned in `makeTerminalTab` (`TerminalSessions.swift:1609-1614`) immediately after `makeView(...)` returns — for *both* a freshly-created tab (`addTab`) and a restored one (`restore()`, `TerminalSessions.swift:665-711`, which the file's own comment states explicitly: "Nothing spawns here: constructing a surface is inert until it enters a window" at `:662-663`). `createSurface()` (which is the only thing that can ever call `ghostty_surface_new` and thus receive any libghostty action callback) only runs later, from `viewDidMoveToWindow` or an explicit `ensureSurfaceCreated`/`reattachPersistentSession` call — always strictly *after* the tab (and its callbacks) already exist. There is no code path where a `GHOSTTY_ACTION_SET_TITLE`/`GHOSTTY_ACTION_PWD` callback can fire before `onTitleChange`/`onCwdChange` are wired.

Also traced the render side per the advisor's flag: `TerminalStatusBar.swift:51-53,67` gates the footer usage icon directly on `state?.activeAgentBackend` with no additional/independent gate, and `cwd` (`:45`) falls back to `state.view.lastKnownCwd` — but that's fed by the *same* `onCwdChange`/`handlePwd` path, not an independent source. So there's no separate rendering-layer failure mode; if `updateTitle`/`updateCwd` never fire, the footer/cwd genuinely have nothing to show.

### Second, independently-confirmed bug: `SessionReplayBuffer`'s alt-screen detection misses synchronized-output TUIs

`SessionReplayBuffer.swift:13-23` only recognizes classic DEC alt-screen codes (`?47h`, `?1047h`, `?1049h`) as "entering the alternate screen," and drops its buffer only on that transition (`:71-72`: `guard !alternateScreenActive else { return [] }`).

The captured daemon log's replay bytes for the Codex session (11.7KB total) contain **zero** occurrences of `1049h`, `1047h`, or `[?47h` anywhere (verified with `grep -c` against the full, untruncated log file), while clearly containing a full-screen TUI repaint (box-drawing "OpenAI Codex" panel) driven instead via `\x1B[?2026h` (synchronized-output mode) and absolute cursor positioning on the **primary** screen. Because the enter-sequence is never matched, `alternateScreenActive` never becomes `true`, so the buffer never drops — and its byte count visibly grows across the three captured reattach events (10961 → 17958 → 19467 bytes), meaning stale primary-screen content (including old OSC 2/OSC 7 from job-start time) keeps accumulating and gets replayed in full on every subsequent reattach, right alongside whatever the daemon does or doesn't synthesize.

This is a genuine, currently-reproducible gap independent of the tcgetpgrp question: any TUI (possibly including newer Claude Code builds) that uses synchronized-output instead of classic alt-screen defeats the "drop while full-screen" replay heuristic that the reattach fix depends on.
