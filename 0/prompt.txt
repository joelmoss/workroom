## Finding #1 (fix this first — ~33% of total suite time, one line)

**File:** `WorkroomAppTests/WorkroomStatusTests.swift`
**Test:** `WorkroomStatusTests.testCancelledGitHubCLIProbePublishesNothing()`
**Measured cost:** **60.085s** — by far the single most expensive test in the entire suite (the xcresult's own "Longest Test Runs" insight flags 3 outlier tests covering 38% of total duration; this one test alone is ~33%).

What it does: spins up a `GatedGHRunner` stub whose `run()` does `try? await Task.sleep(nanoseconds: 60_000_000_000)` (60s) until cancelled, then cancels the wrapping `Task` and awaits `task.value`, asserting the store's `githubCLIStatus` wasn't mutated by the cancelled probe.

**Why it costs the full 60s every single run:** `GitHubAuthCache` is deliberately single-flight (by design, per its own header comment) — multiple callers coalesce onto one shared underlying probe. Cancelling *this test's* wrapper `Task` does not cancel the shared in-flight probe task, so `await task.value` blocks until the shared task actually finishes — i.e., the full hardcoded 60-second sleep, unconditionally, on every run, whether in CI or locally. The test's own comment ("long enough that the test's own deadline fails first if cancellation never propagates") assumed cancellation *would* propagate quickly; it structurally can't, given the single-flight design it's testing against.

**Recommendation — fix, don't cut:** the assertion is legitimate and worth keeping (real regression: `refreshGitHubCLI`'s guard against a cancelled probe stomping a good cached value). Just shrink `GatedGHRunner`'s sleep from 60s to ~1–2s (still far longer than the 2s poll window used to detect probe entry) or stop blocking on `task.value` and instead poll `githubCLIStatus` for a bounded window as the test already does for probe-entry. Either change is a 1-line diff, preserves 100% of the signal, and removes ~60s from every single `make app-test` invocation — bigger than every other finding in this report combined.

## Finding #2 (second-highest leverage — shared anti-pattern, ~14s, restructure not cut)

**Files:** `ChangedFileRowInvalidationTests.swift` (3 tests, 6.87s measured), `HistoryRowInvalidationTests.swift` (6 tests, 6.19s), `DiffViewerLazyRenderingTests.swift` (3 tests, 1.32s)

All three define an identical `settle(_ view: NSView, seconds: TimeInterval = 0.6)` helper:
```swift
private func settle(_ view: NSView, seconds: TimeInterval = 0.6) {
  let deadline = Date().addingTimeInterval(seconds)
  while Date() &lt; deadline {
    view.layoutSubtreeIfNeeded()
    RunLoop.current.run(until: Date().addingTimeInterval(0.02))
  }
  view.layoutSubtreeIfNeeded()
}
```
This is a **fixed-duration busy-wait, not an early-exit poll** — it always burns the full `seconds` argument regardless of how quickly SwiftUI actually converges. `ChangedFileRowInvalidationTests.testSelectionChangeRebuildsChangedFileRows` calls it 3 times (1.2s + 0.6s + 0.6s = 2.4s guaranteed minimum), which matches its measured 3.095s almost exactly.

**Recommendation — restructure, keep the assertion:** these are legitimate regression nets for real App Hangs (WORKROOM-2B/2T/2S, named in the doc comments) and the assertions themselves (`bodyPasses` counts) are good — this isn't the kind of test to delete. Replace the fixed busy-wait with a poll-until-condition-or-ceiling (check the actual `bodyPasses`/render-settled signal each spin iteration and `return` early), keeping the same `seconds` value only as a safety-net ceiling. Typical cost drops from "always pays 0.6–1.2s" to "pays whatever SwiftUI actually needs," likely cutting this ~14.4s cluster by 70–90% with zero loss of regression coverage. `PaneRenderingTests.swift` and `HistoryCommitCardTests.swift` use the same offscreen-NSWindow-hosting harness pattern (per their own doc cross-references) — worth checking whether they duplicate the same fixed-wait pattern in the same pass.
