## 1. First-run / onboarding flags — none exist today

`macapp/WorkroomApp/Core/DefaultsKeys.swift` (the single `Defaults.Keys` extension, lines 27-225) has no `isFirstRun`/`hasCompletedOnboarding`/`hasSeenWelcome` key of any kind. The closest analog is:

- `Defaults.Keys.lastSeenVersion` (`DefaultsKeys.swift:186-189`, `Key&lt;String?&gt;("app.lastSeenVersion", default: nil)`) — drives the "What's New" dialog.
- `WhatsNewService.checkOnLaunch()` (`macapp/WorkroomApp/Core/WhatsNewService.swift:40-63`) explicitly treats `nil` as "fresh install / first launch after this feature shipped: record, no backfill" and **deliberately suppresses** the dialog on a brand-new install (line 47-49: `Defaults[.lastSeenVersion] = currentStr; return nil`). This is the one place in the codebase that already distinguishes "never launched before" from "upgraded," and it's the natural sibling for a new `hasCompletedOnboarding`/`onboardingSeenVersion` key — issue #151 will need to add its own key rather than overload this one (their semantics differ: this one is "don't show release notes on day one," an onboarding flag is "do show something on day one").

There is a **documented gotcha directly relevant to any new Defaults flag**: `macapp/WorkroomApp/Core/UITestFixture.swift:490-527` — a plain launch-argument (e.g. `-hasSeenOnboarding 1`) arrives in the **argument domain**, which outranks the app's persisted domain and is read as a **string**, not a bool. A typed `Defaults[...]` read does `as? Bool` and silently falls back to the key's default, which then **also shadows every later write** for the rest of that process's life. Any test/dev harness for an onboarding flag must mirror the `UITestFixture` pattern (a UserDefaults `bool(forKey:)` coercion, or a fixture-namespaced arg mirrored into `Defaults` before first read) rather than relying on a bare launch arg.

Gotchas for a **new auxiliary window** (documented across `AppDelegate`/`WindowRegistry`):
- `WorkroomApp.swift:220,238`: "Settings, About, Sparkle's updater or the quick terminal" are all windows with **no `AppStore`** — every `shortcutStore`/`switcherGate` lookup treats them as unregistered, so app-wide shortcuts just no-op there rather than needing an allowlist.
- `WorkroomApp.swift:310-320`: ⌘W on an auxiliary window (Settings, About) has no menu-bound "Close Terminal" to fall back on, so a local key-monitor branch explicitly calls `keyWindow.performClose(nil)` for any window with `WindowRegistry.shared.store(for:) == nil`.
- `Core/WindowRegistry.swift:71`: "Settings/About/quick terminal closing here is a no-op" — the registry only tracks workroom windows; an onboarding window would need the same non-registration treatment (or explicit registration if it should influence `lastActiveStore`/quit behavior).
- `WindowRegistry.swift:165`: cycling logic (⌘`) works "front-to-back z-order" across Settings/About panels too.

**Implication for #151**: a dedicated onboarding window is architecturally closest to `Settings` (a small `Scene` with no `AppStore`) — but the existing precedent (`WhatsNewSheet`, see §5 below) is to present it as a **sheet on the launch `RootWindow`** rather than mint a new `Scene`, which sidesteps all the aux-window shortcut/registry carve-outs above.

- **The actual pattern to copy for showing UI on first run is `RootView.rootLifecycle`** (`Views/RootView.swift:347-378`): a `.task { guard store.isRestoreWindow else { return }; ... }` gated on `AppStore.isRestoreWindow` (`AppStore.swift:142`), feeding a `@State private var whatsNewContent: WhatsNewSheetContent?` and `.sheet(item:)`. An onboarding sheet would plug into this exact same `.task`/`.sheet(item:)` slot, gated on the new "has completed onboarding" Default instead of `whatsNew.checkOnLaunch()`.
