## 1. Occlusion mechanism in `GhosttySurfaceView.swift`

State (lines 123-130):

```swift

```

**`updateWindowVisibility()`** (531-536) — driven off `NSWindow.didChangeOcclusionStateNotification`:
```swift
private func updateWindowVisibility() {

  guard isWindowVisible != visible else { return }

```

**`applyOcclusionState()`** (538-541) — the single write to libghostty:
```swift
private func applyOcclusionState() {
  guard let surface else { return }
  ghostty_surface_set_occlusion(surface, isPaneVisible &amp;&amp; isWindowVisible)
}
```

**No warm-up delay / no async work on the Swift side.** `setVisible` → `applyOcclusionState` → `ghostty_surface_set_occlusion` is a fully synchronous call chain on the calling thread (normally main). There is no `Timer`, `DispatchQueue.asyncAfter`, or `Task` anywhere in this occlusion path. Un-occluding a surface (`setVisible(true)` after having been `false`) takes effect the instant it's called; any warm-up latency for the *first rendered frame* would have to come from inside libghostty's own (opaque, closed-source) Metal render loop, not from Workroom's code — the codebase introduces zero artificial delay here.

**`viewDidMoveToWindow()`** (456-500):

When a background tab's surface is re-homed into a new container/window and `surface` already exists, `createSurface()` is **never called again** — its whole body (lines 235-313: `ghostty_surface_new`, C-string/env-var allocation, `applyColorScheme`, re-adding the scrollbar/go-to-bottom overlay subviews, `adoptFocusIfFirstResponder()`) is skipped entirely. ## 2. CAMetalLayer / layer ownership

Grepped the whole file (and the whole app) for `CAMetalLayer`, `makeBackingLayer`, `layer(for:`:
```
$ grep -rn "CAMetalLayer\|makeBackingLayer\|layer(for:" WorkroomApp/
(no matches)
```
`GhosttySurfaceView` does **not** own or create a `CAMetalLayer` in Swift. Its only layer-related code is:
```swift
// init(...), line 199
wantsLayer = true
```
It never overrides `makeBackingLayer()`, never assigns `self.layer = ...`, and never touches `CAMetalLayer` anywhere. The class doc comment (lines 6-7) states the actual mechanism:
```swift
/// One terminal surface: an `NSView` that hosts a `ghostty_surface_t` (Metal-rendered by libghostty
/// given our `nsview`), drives a local PTY, and bridges macOS keyboard/IME/mouse into libghostty.
```
The `nsview` handoff happens in `createSurface()` (243-247):
```swift
var config = ghostty_surface_config_new()
config.platform_tag = GHOSTTY_PLATFORM_MACOS
config.platform = ghostty_platform_u(
  macos: ghostty_platform_macos_s(nsview: Unmanaged.passUnretained(self).toOpaque()))
```
So Workroom sets `wantsLayer = true` (so AppKit provisions a backing `CALayer`) and passes the raw `self` pointer to libghostty; libghostty's macOS embedded backend (inside the prebuilt, closed-source `GhosttyKit.xcframework`) is what installs the real `CAMetalLayer` against that NSView internally — nothing in Workroom's own Swift does it. I confirmed there's no public C entry point for this either (`ghostty.h` under `DerivedData/Build/Products/Debug/include/libghostty/ghostty.h` has zero `layer`/`CAMetalLayer` symbols, only `void* nsview;` at line 449 and unrelated `ghostty_inspector_metal_*` calls at 1211-1213) — the layer install is entirely internal to the engine.

For cross-reference only (not Workroom's code path): the vendored SPM package also ships a separate, unused reference wrapper at `DerivedData/SourcePackages/checkouts/libghostty-spm/Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView.swift`, which explicitly does `wantsLayer = true; let metal = CAMetalLayer(); ...` and assigns it as `self.layer`. Workroom does **not** use `GhosttyTerminal`/`AppTerminalView` — its own `GhosttySurfaceView` talks directly to the `GhosttyKit` C API — but this reference implementation confirms the general mechanism (a real `CAMetalLayer` becomes the view's backing layer) that libghostty's embedded macOS backend performs internally for Workroom's view too.

**Implication for your plan:** once `GhosttySurfaceView` is mounted (added as a subview) into the app's real window and un-occluded, its backing layer *is* a genuine `CAMetalLayer` that is part of that window's normal Core Animation compositing tree — there is no separate offscreen/headless render surface to route around. An `SCContentFilter` built against that real window (`SCShareableContent`/`SCContentFilter(desktopIndependentWindow:)` or an included/excluded-window filter) will see this surface's rendered Metal content exactly as a human would, as long as the view is on-screen, unoccluded (`ghostty_surface_set_occlusion(surface, true)`), and the window itself isn't occluded/minimized.

```swift
/// solo tab. Drives occlusion.
```

Supported by `isSplitVisible(for:)` (581-586):

So for an arbitrary hovered `TerminalTab.ID`, the check is simply: `TerminalSessions.visibleTabIDs(for: target).contains(hoveredTabID)`. `true` ⇒ already on screen (splits show multiple; skip re-mounting, the preview can just... watch it, or not preview at all). `false` ⇒ a background tab that needs re-homing for the hover preview.

**`reconcileOcclusion(for:)`** (1332-1339) is the doc-comment-mentioned mechanism you asked about — the single reconciliation pass that keeps `GhosttySurfaceView.setVisible` in sync with `visibleTabIDs`:
```swift
/// One reconciliation pass: exactly the on-screen tabs render; every other surface for the target is
/// paused (its shell keeps running — `setVisible(false)` toggles GPU occlusion, not the PTY). Called
/// from every state change that can alter what's on screen (focus / split / close / move / reap).
func reconcileOcclusion(for target: TerminalTarget) {
  let visible = Set(visibleTabIDs(for: target))
  for tab in (tabsByTarget[target.id] ?? [:]).values {
    tab.surface?.setVisible(visible.contains(tab.id))
  }
}
```
It's called from `restore`, `addTab`, `openContentPreview`/`openContentPersistent`, `splitFocusedPane`, `moveTabIntoSplit`, `extractFromSplit`, `focus`, `closeTab`, `addRunTab`, `respawnRunTab` — i.e., every state transition that can change what's on screen (lines 675, 699, 756, 778, 1078, 1166, 1179, 1188, 980, 1024, 1277).

`displayedTabIDs(for:)` (477-495) is a *different*, broader query — it's the full strip order (every tab, split members normalized into a contiguous run) — **not** what's currently rendered; don't confuse it with `visibleTabIDs`.
