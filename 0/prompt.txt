**Detection wiring (app-side, live pane):**
- `macapp/WorkroomApp/Core/GhosttySurfaceView.swift:36-43` — `foregroundAgentBackend` computed property: asks libghostty for the PTY foreground pid (`ghostty_surface_foreground_pid`) and resolves it via `AgentProcessRecognition.backend(forPID:)`.
- `macapp/WorkroomApp/Core/AgentUsage.swift:129-145` — `enum AgentProcessRecognition`: `backend(forProcessName:)` (:130-137) matches lowercased basename `"claude"`/`"codex"`; `backend(forPID:)` (:139-144) resolves the name via **`proc_name(pid, ...)`**.
- `macapp/WorkroomApp/Core/AgentUsage.swift:101-127` — `enum AgentTitleRecognition.backend(for title:)`: the title-based fallback, matching provider-owned titles (`"claude code"`, `"codex"`) or the first token's basename (`"claude"`/`"codex"`).
- `macapp/WorkroomApp/Core/TerminalSessions.swift:1360-1368` (`updateTitle`) is where the two are combined and latched: `s.view.foregroundAgentBackend ?? AgentTitleRecognition.backend(for: trimmed)`, only written into `activeAgentBackend` once (`if $0.activeAgentBackend == nil { … }`) until `command_finished` clears it (:1403-1407, `handleCommandFinished`).

**Known asymmetry worth flagging for planning (not something to fix here):** the daemon-side foreground detector (`SessionPTY.swift`, next section) deliberately avoids `proc_name`/`p_comm` with an explicit comment that Claude Code renames its own process title post-launch (so `p_comm` reads as a version string like `"2.1.232"`, not `"claude"`). The **live-pane** detector, `AgentProcessRecognition.backend(forPID:)` (`AgentUsage.swift:139-144`), still calls `proc_name` today. In practice this likely means `foregroundAgentBackend` returns `nil` for a live Claude pane and detection actually succeeds via the `AgentTitleRecognition` title fallback in `updateTitle` (`TerminalSessions.swift:1360-1361`) instead — i.e. the two recognizers in the codebase disagree on method, and only one of the two call sites (daemon reattach) uses the method the code itself says is correct.

**Daemon-side foreground detection ("session-daemon reattach foreground detection"):**
- `macapp/WorkroomSession/SessionPTY.swift:143-146` — `foregroundProcessGroup(masterDescriptor:)`, via `tcgetpgrp`.
- `macapp/WorkroomSession/SessionPTY.swift:148-181` — `executableName(processID:)`: reads `argv[0]` at exec time via `sysctl(KERN_PROCARGS2, …)`, explicitly **not** `proc_name`/`p_comm`, with the rationale above.
- `macapp/WorkroomSession/SessionDaemon.swift:343-407` (`attach(session:request:connection:)`), esp. :368-407: on client reattach, resolves the foreground pgid (excluding the shell's own pgid), resolves its `executableName`/`workingDirectory`, and synthesizes fresh OSC 2 (title, :390-393) and OSC 7 (cwd, :394-402) frames before replay — because the shell's original preexec/prompt OSC escapes were one-shot and lost once the alternate screen took over (`SessionReplayBuffer` drops on alt-screen).
- **Does the tool identity survive relaunch?** No — it is not persisted. `TerminalSessions.swift:216-227` (`TabSession.init?`, the on-disk snapshot bridge) writes only `defaultTitle`, `cwd`, `sessionID` into `TerminalPayload`; `activeAgentBackend`/`liveTitle`/`progressActive` are pure runtime state and never serialize. On relaunch, a tab that reattaches to a still-alive daemon session gets its title (and thus `activeAgentBackend`, via the `AgentTitleRecognition` fallback in `updateTitle`) **re-derived fresh** from the daemon's synthesized OSC 2 (the path in the paragraph above); a tab that spawns a brand-new shell has no agent identity until the next real title/foreground-process report arrives.
