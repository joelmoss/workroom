Three genuinely different mechanisms exist in this codebase; none of them is a generic "hover preview" but each is a real precedent for a different piece of the puzzle.

### a) `TerminalSearchBar.swift` — pure SwiftUI `.overlay`, no separate window
File: `/Users/joelmoss/dev/workroom/macapp/WorkroomApp/Views/TerminalSearchBar.swift`, mounted at `/Users/joelmoss/dev/workroom/macapp/WorkroomApp/Views/PaneTreeView.swift:496-502`:
```swift

// Scrollback find bar (⌘F), pinned top-trailing over the focused pane only — search state
// is per-surface, and only the focused pane can be searched. Nothing until active.
.overlay(alignment: .topTrailing) {
  if focused {
    TerminalSearchBar(model: s.view.searchModel)
  }
}
```
- **Mechanism:** a plain SwiftUI `.overlay(alignment:)` directly on `TerminalContainerView` (the `NSViewRepresentable` hosting the terminal surface) — it lives in the same view hierarchy, above the AppKit-hosted surface, not a separate window/panel.
- **Positioning:** `alignment: .topTrailing` on the overlay + the bar's own `.padding(10)` (`TerminalSearchBar.swift:71`) — no measured frame math, just corner-alignment + fixed inset.
- **Shown/dismissed:** conditional on `focused` (SwiftUI `if`, so it mounts/unmounts) and `model.isActive` (an `@ObservedObject` model's published flag) — driven by ⌘F, not hover. Dismissed via `model.end()` from an explicit close button or `.onExitCommand` (Esc), `TerminalSearchBar.swift:82`.
- **Focus interplay is notable and load-bearing** for anything else that wants to sit over a terminal: `TerminalContainerView.applyFocus` (`TerminalContainerView.swift:118-119`) explicitly yields to the search bar (`if view.searchModel.isActive { return }`) so it doesn't steal first-responder back from the field. A hover preview overlay wouldn't need first-responder, but it's the concrete example of "a SwiftUI overlay sitting on top of the Metal surface" already existing and being hit-testable (SwiftUI overlay content over an `NSViewRepresentable` does receive clicks/hover — confirmed by this bar's own buttons working).

### d) The closest existing analogue to "hover to reveal a small preview": `TerminalStatusBar.swift`'s delayed-hover popover
This is the single best precedent for your feature — same shape (hover a small chip → after a short delay, show more detail in a floating panel → hide on exit), already shipped:
```swift
// TerminalStatusBar.swift:34-42
@State private var usageDetailHovering = false
@State private var usageHoverRevealWorkItem: DispatchWorkItem?
...
private let usageHoverRevealDelay: TimeInterval = 0.4

// TerminalStatusBar.swift:162-171
.onHover { hovering in
  usageHoverRevealWorkItem?.cancel()
  if hovering {
    let workItem = DispatchWorkItem { usageDetailHovering = true }
    usageHoverRevealWorkItem = workItem
    DispatchQueue.main.asyncAfter(deadline: .now() + usageHoverRevealDelay, execute: workItem)
  } else {
    usageDetailHovering = false
  }
}
.popover(isPresented: usageDetailPresented, arrowEdge: .bottom) {
  AgentUsageDetailView(snapshot: snapshot, now: Date())
    .frame(width: AgentUsageDetailView.popoverWidth)
}
```
Key details: exit is instant (no symmetric delay on hide — `usageDetailHovering = false` immediately), the delay is only on *reveal* (arm-and-cancel via `DispatchWorkItem`, cancelled on every hover-state change so a quick pass-through never fires it), and it composes with a separate "pinned" boolean (`usageDetailPinned`, set by click) via a combined `Binding` (`usageDetailPresented`, lines 123-132) so click-to-pin and hover-to-peek share one popover without fighting each other. Comment at lines 31-33 states the intent plainly: "Set after a short hover delay ..., so a mouse merely passing over the segment doesn't pop a popover; cleared the instant the mouse leaves."

## 3. `TerminalContainerView.swift` — full file read

File: `/Users/joelmoss/dev/workroom/macapp/WorkroomApp/Views/TerminalContainerView.swift` (129 lines, read in full above).

**Surface-frame/container relationship:**
- The container is a bare `NSView` created in `makeNSView` (line 40), `wantsLayer = true`, corner-radius/clip applied via `container.layer` (lines 44-46) — not an `NSView` subclass with any custom logic beyond that.
- The surface (`view: GhosttySurfaceView`) is pinned to the container purely via **frame + autoresizing mask**, deliberately **not** AutoLayout constraints:
```swift
// TerminalContainerView.swift:90-93
view.translatesAutoresizingMaskIntoConstraints = true
view.frame = container.bounds
view.autoresizingMask = [.width, .height]
container.addSubview(view)
```
The comment (lines 85-89) explains why: a surface is re-homed between containers (split ⟷ solo) while the old container may still be alive mid-transition, and lingering AutoLayout constraints to a stale container previously left the surface at a broken/zero frame (a blank pane, issue #3). So **the surface's frame always == its current container's bounds**, kept in sync automatically by the autoresizing mask on every container resize — there's no independent sizing of the surface from its container today.
- On every `updateNSView` (SwiftUI re-render), `mount(in:)` runs again (line 55) but is a no-op frame-wise if the surface is already the container's subview: `if view.superview === container { view.frame = container.bounds; view.setVisible(true); return }` (lines 77-81) — i.e. it re-asserts `view.frame = container.bounds` on every update pass regardless of whether it changed.

**No existing "resize the surface without making it the active tab" path.** There is exactly one sizing mechanism (frame == container.bounds, via autoresizing mask) and it is coupled 1:1 to `mount(in:)`/re-homing into *the* container this `TerminalContainerView` instance owns — there's no API to size a surface against an arbitrary rect while it stays parented elsewhere, and no notion of "preview size" distinct from "real pane size" anywhere in this file. A hover-preview that wants to show a live/near-live rendering of a background tab's surface would need either (a) a second, temporary host (e.g. a scratch `NSView`/container the surface is briefly re-homed into — which the re-homing comment says is exactly the risky path that caused the split↔solo blank-pane bug, issue #3), or (b) a snapshot/bitmap approach that doesn't touch `view.frame`/`superview` at all. This file gives no ready-made third option.

**Occlusion note (adjacent, may matter for a live preview):** `TerminalContainerView` intentionally has **no `dismantleNSView`** (comment lines 66-70) — occlusion (whether a background surface renders at all) is centrally driven by the model (`reconcileOcclusion`, referenced but not defined here) and by AppKit's own window-occlusion, not by this view's mount/dismantle. This matters because a background tab's `GhosttySurfaceView` may already be marked non-visible (`setVisible(false)`) precisely because it's not the mounted/focused surface — relevant if a preview wants to read "the current rendered content" of a tab that the occlusion system has paused.

**Focus (`applyFocus`, lines 111-127):** unrelated to sizing — purely first-responder bookkeeping (claim/resign `NSResponder`), gated by `isFocusedPane` and the search-bar-active guard already covered in §2a. No interaction with frame/bounds.
