## 3. Output/progress capture and reporting back

- The actual process spawn/drain lives in `StatusCommandRunner.run(...)` — `macapp/WorkroomApp/Core/StatusCommandRunner.swift:197-349`. It's not streamed/NDJSON — it's a single buffered `CommandResult` returned after the process exits:
  - `Process` spawned via `/usr/bin/env`, stdout/stderr each drained concurrently on `DispatchQueue.global()` (`StatusCommandRunner.swift:262-270`) into `StatusRunState` (capped at `maxBytes = 4MB`, `StatusCommandRunner.swift:126, 353-368`) so the child never blocks on a full pipe.
  - `proc.terminationHandler` (`StatusCommandRunner.swift:287-308`) assembles the final `CommandResult(stdout:stderr:exitCode:timedOut:signaled:)` and resumes a `CheckedContinuation`.
  - This is routed for push specifically through `runNetwork` (`StatusCommandRunner.swift:190-195`), which additionally forwards SSH/auth env vars and pins `BatchMode=yes` (`networkEnvironment`, `StatusCommandRunner.swift:161-175`).
- Back in `CLIVCSWriter.push`, the raw `CommandResult` is turned into a typed outcome by `classify(result, action: .push, tool: vcs, ...)` — `VCSWriting.swift:1092-1166` (matches stderr/stdout substrings — auth failure, host-key, rejected push via `--porcelain` flag column at `gitPushRejected`/`VCSWriting.swift:507-509`, needsDescription, locked, etc.) and surfaced as `VCSRemoteActionResult.ok(summary:)` / `.failed(VCSRemoteFailure)`.

- No progress percentage/streaming exists — the UI only shows a static "Pushing…" state (`activeAction`/`inFlight`) until the single buffered result returns.

## 4. Timeout logic

- Value: `CLIVCSWriter.pushTimeout: TimeInterval = 120` — `VCSWriting.swift:332` (shared struct-level default; fetch is also 120, pull is 300, commit is 600).
- Enforcement lives entirely inside `StatusCommandRunner.run` (not an outer `withTimeout`, per the doc at `VCSWriting.swift:1409-1414` explaining that's deliberate since a subprocess can genuinely be killed):
  - `DispatchQueue.global().asyncAfter(deadline: .now() + timeout)` → SIGTERM (`timeoutItem`, `StatusCommandRunner.swift:272-276`).
  - A hard-kill fallback 2s later: `DispatchQueue.global().asyncAfter(deadline: .now() + timeout + 2)` → `ProcessTree.killTree` (SIGKILL) (`StatusCommandRunner.swift:282-285`).
  - Result marks `timedOut = true`, `signaled = true`.
- What happens when it fires (**not silent**): `classify` (`VCSWriting.swift:1102-1105`) turns a timed-out result into `.timedOut(action)` (with a pull-specific upgrade to `.rebaseInProgress` if a rebase was left behind). This propagates to `.failed(.timedOut(.push))` from `CLIVCSWriter.push`, then:
  - `RemoteStateModel.finish` sets `lastFailure = .timedOut(.push)` (toolbar segment shows this) **and** raises a modal `failureReport` (since push is always `userInitiated: true`) — `RemoteStateModel.swift:389-393` / `raiseFailureReport`.
  - User-facing copy: `"Push timed out."` — `VCSSyncPresentation.swift:445-446` (`describe(_:)`).
  - Retry is offered: `retryAction` maps `.timedOut` → `lastAction` (i.e., "Push" again) — `VCSSyncPresentation.swift:392-393`.
- So: timeout → SIGTERM then SIGKILL the child → typed `.timedOut(.push)` failure → toolbar notice + modal dialog with a retry offer. It does not silently give up.

## 5. Cooperative thread pool vs GCD

Push does **not** run on the Swift cooperative thread pool for its blocking work — it correctly uses GCD, consistent with the pattern documented elsewhere in this codebase (`Timeout.swift:105-117` `runBlocking`, and comments in `GitProvider.swift:177`, `RustJJProvider.swift:21,49,230`, `WorkroomStatusResolver.swift:130,170` warning that blocking libgit2/jj-lib calls must never run on the cooperative pool / `Task.detached`).

- `StatusCommandRunner.run` (`StatusCommandRunner.swift:197-349`) wraps everything in `withCheckedContinuation`, but the actually-blocking pieces are explicitly hopped to `DispatchQueue.global()`:
  - stdout/stderr drains: `DispatchQueue.global().async { ... }` (`StatusCommandRunner.swift:262-270`).
  - timeout/kill scheduling: `DispatchQueue.global().asyncAfter(...)` (`StatusCommandRunner.swift:276, 285`).
  - stdin feed: `DispatchQueue.global().async { ... }` (`StatusCommandRunner.swift:316-326`).
  - cancellation kill: `ProcessBox.terminate()` hops to `DispatchQueue.global(qos: .userInitiated).async` specifically because `onCancel` "runs synchronously on whichever thread called `cancel()`" and that's often the main thread (`StatusCommandRunner.swift:378-393`).
- `proc.run()` itself (`StatusCommandRunner.swift:311`) is called inline inside the continuation closure, but that's a `posix_spawn`-based non-blocking call, not a long-running blocking operation, so it's safe to run wherever the continuation body executes.
- `JJSnapshotGate.run` (`JJSnapshotGate.swift:39-92`) is a plain `actor` using structured `Task`s, not a blocking primitive, so no cooperative-pool concern there either.

Net: the "shell-outs must use GCD not cooperative pool" rule this codebase enforces elsewhere for libgit2/jj-lib blocking calls is already satisfied for push — the actual blocking I/O (pipe reads, timeout waits, process kill) happens on `DispatchQueue.global()`, and `withCheckedContinuation` only suspends the calling Task rather than blocking a cooperative-pool thread.</result>

**Push output-visibility bug — root cause found.**

1. `classify` (`VCSWriting.swift:1092-1166`): computes `err = result.stderr + "\n" + result.stdout` at line 1100, but checks `result.timedOut` immediately after (line 1102) and returns bare `.timedOut(action)` (line 1104) **before** `err` is ever attached. `VCSRemoteFailure.timedOut(VCSRemoteAction)` (`VCSWriting.swift:35`) carries no output payload — unlike `.authRequired(String)`, `.rejected(String)`, `.other(String)` etc., which all carry the raw combined stderr+stdout as their associated value.

3. `VCSFailureSheet.swift` **already has a full "Details" disclosure UI** (`detailsSection`, lines 82-98): collapsed `DisclosureGroup`, monospaced scrollable text, Copy button — built and working today for auth/reject/lock/other failures. But `rawOutput(of:)` (`VCSSyncPresentation.swift:576-588`) explicitly maps `.timedOut` (along with `.toolMissing, .noRemote, .rebaseInProgress, .locked, .launchFailed`) to `nil` — so `dialog.details` is nil and the whole Details section never renders for a timed-out push.

4. `RemoteStateModel.finish`/`raiseFailureReport` (`RemoteStateModel.swift:370-423`) just pass the `VCSRemoteFailure` value through unchanged into `lastFailure`/`failureReport` — no separate raw-output channel; whatever `classify` didn't attach is gone for good by this point.

**Bottom line:** the raw process output the user wants to see (`result.stderr`/`result.stdout`) is captured all along by `StatusCommandRunner`, and the UI plumbing (`VCSFailureDialog.details` → `VCSFailureSheet`'s Details disclosure) already exists and already works for other failure types.
