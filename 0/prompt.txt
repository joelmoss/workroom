**[CRITICAL] (confidence: 7/10)** `SessionDaemon.swift:107-110` — lock file is unlinked *after* the flock is released, not before, opening a window where two later daemons can both believe they hold the exclusive lock, leading one of them to unlink the other's live socket.

```swift
SessionIO.close(listener)
unlink(socketPath)
SessionIO.close(lockDescriptor)
unlink(socketPath + ".lock")
```

`acquireLock` (`SessionSocket.swift:91-99`) does `open(path, O_CREAT|O_RDWR)` then `flock(LOCK_EX|LOCK_NB)`. Trace: daemon A shuts down, `close(lockDescriptor)` releases the flock on the lock file's inode while the path still exists. If daemon B starts in that window, `open()` reopens the *same* inode and successfully `flock`s it. A then runs `unlink(socketPath + ".lock")`, removing the directory entry — B's fd still references the now-unnamed inode and B is unaffected, but the inode is no longer reachable by path. A fresh daemon C started afterward calls `open(path, O_CREAT, …)` and gets a *brand-new* inode (nothing exists at that path anymore), flocks it uncontested, and now both B and C believe they are the sole daemon. Each independently `unlink`s and rebinds `socketPath` in `makeListener`, so whichever of B/C runs its own idle-timeout `shutdown()` later will `unlink(socketPath)` again — potentially deleting the *other* daemon's live, in-use socket file out from under active clients, which is exactly the "already running detection silently fails / stale socket" failure mode this daemon exists to avoid. Fix: don't unlink the lock file on clean shutdown (let the next starter's `open`+`flock` on the pre-existing path be the source of truth), or at minimum unlink the lock path before releasing the flock so no unlocked-but-named window exists.
