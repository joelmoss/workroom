# Workroom signs in to Railway with Login with Railway, and keeps the refresh token in the Keychain: the first provider credential Workroom stores itself

Proposed 2026-11-13, from the Railway sandboxes design interview. It is accepted once the live spike shows a Native app refreshing its token without a client secret and Railway accepting the localhost redirect. The spike of 2026-11-13 (branch `prototype/railway-sandbox-spike`, `vcs/scripts/railway-spike/FINDINGS.md`) found Railway's dynamic client registration disabled (`POST https://backboard.railway.com/oauth/register` answers `access_denied`, "Dynamic client registration is disabled"), so the Codaset-owned app stays. It also showed Railway's own CLI working as a public client: its refresh sends no secret, and it redirects to `http://127.0.0.1:<ephemeral port>/callback`. That is Railway's first-party client, so the two conditions above are still to be shown with Codaset's registered app, along with which scopes it needs to create a project, an environment, a sandbox and an ssh key; the spike's calls all used the CLI's `workspace:admin project:admin ssh_keys` token.

boxd and exe.dev are driven through their own CLI and ssh, and Workroom holds no credential for either. Railway's CLI has no region or size flag for a sandbox, so every host would land in `us-west2` at the plan's default size, and it rewrites the "active sandbox" in the user's `~/.railway/config.json` on every create, ssh and exec. So the Railway driver calls Railway's GraphQL API itself and reaches a host with the system `ssh` through the relay, with a key Workroom makes for each Mac and registers on the account. Codaset registers a Native (Public) OAuth app with Railway, in Codaset's workspace: no client secret, PKCE required. A client ID is something Railway only issues to an app registered in a workspace, and the app's owner holds its consent screen, redirect URIs and rotation, so it belongs with the product's publisher (Workroom is a Codaset product), not a personal workspace; each user still signs in to their own Railway account. The setup sheet opens Railway's consent page in the browser and takes the callback on a fixed localhost port, asking for `workspace:member`, `project:member`, `ssh_keys` and `offline_access`. `ssh_keys` is in Railway's discovery document (`/.well-known/oauth-authorization-server`), not its docs, and registering Workroom's key needs it. The refresh token goes in the Keychain, in an access group Release and Nightly share; a Dev build keeps its own. Access tokens last an hour and are refreshed by one owner at a time, which always stores the newest refresh token, since a rotated one fails and forces a new sign-in. Signing out is allowed while Railway workrooms exist, with a warning that their sandboxes keep running and billing; they show signed out, with Sign in, until the user signs in again.

Rejected: driving the user's `railway` CLI, for the region, size and config side effects above. Rejected: a pasted workspace or account token. It is one manual copy from Railway's dashboard, and an account token reaches every workspace. Rejected: reading the CLI's session from `~/.railway/config.json`, a private format. Rejected: a project token, which can't register an ssh key. Rejected, because Railway has it turned off: a client each install registers for itself by dynamic registration. Not yet weighed, both offered by Railway's discovery document: the device-code grant, which needs no localhost listener, and a client ID metadata document, which needs no registered app.

Source: [`docs/designs/railway-sandboxes-research.md`](../designs/railway-sandboxes-research.md) (section 5), Railway's OAuth docs: <https://docs.railway.com/integrations/oauth/creating-an-app> (app types) and <https://docs.railway.com/integrations/oauth/login-and-tokens> (refresh and rotation).
