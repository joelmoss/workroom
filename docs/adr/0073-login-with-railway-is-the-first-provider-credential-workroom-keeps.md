# Workroom signs in to Railway with Login with Railway, and keeps the refresh token in the Keychain: the first provider credential Workroom stores itself

Decided 2026-11-13, from the Railway sandboxes design interview. Accepted on two live runs of 2026-11-13. The spike (branch `prototype/railway-sandbox-spike`, `vcs/scripts/railway-spike/FINDINGS.md`) found Railway's dynamic client registration disabled (`POST https://backboard.railway.com/oauth/register` answers `access_denied`, "Dynamic client registration is disabled"), so the Codaset-owned app stays. Codaset's registered app (client ID `rlwy_oaci_H1zdJw3FGIwJ4Uyzuvb6HQNu`, in `macapp/project.yml` as `RailwayOAuthClientID`) then showed, through a throwaway wizard: the code exchanged with PKCE and no secret; a refresh with no secret, which rotated the refresh token; a loopback redirect accepted on a fixed port and on an ephemeral one against a registered URI with no port; and, with only the scopes below, `projectCreate`, `environmentCreate`, a `sandboxCreate` with `idleTimeoutMinutes: 0` that reached `RUNNING`, `sshPublicKeyCreate`, and the deletes of the key and the sandbox. The project's delete did not go through, for a reason the run did not record; Workroom never deletes its project, so the design does not need it.

boxd and exe.dev are driven through their own CLI and ssh, and Workroom holds no credential for either. Railway's CLI has no region or size flag for a sandbox, so every host would land in `us-west2` at the plan's default size, and it rewrites the "active sandbox" in the user's `~/.railway/config.json` on every create, ssh and exec. So the Railway driver calls Railway's GraphQL API itself and reaches a host with the system `ssh` through the relay, with a key Workroom makes for each Mac and registers on the account. Codaset registers a Native (Public) OAuth app with Railway, in Codaset's workspace: no client secret, PKCE required. A client ID is something Railway only issues to an app registered in a workspace, and the app's owner holds its consent screen, redirect URIs and rotation, so it belongs with the product's publisher (Workroom is a Codaset product), not a personal workspace; each user still signs in to their own Railway account. The setup sheet opens Railway's consent page in the browser and takes the callback on `http://127.0.0.1:<port>/callback`, on a port the system picks for each sign-in, against the registered `http://127.0.0.1/callback`, so no other program holding a fixed port can break sign-in. Railway's docs say a redirect must match a registered one exactly, port included; it accepted the ephemeral port anyway, as RFC 8252 asks of a loopback redirect, so the fixed `http://127.0.0.1:61421/callback` stays registered too, for a release to switch to if Railway starts enforcing the port. It asks for `openid email profile workspace:member project:member ssh_keys offline_access` with `prompt=consent`. `openid` is required on every request; `email` and `profile` are what `me { workspaces }` needs; `ssh_keys` is in Railway's discovery document (`/.well-known/oauth-authorization-server`), not its docs, and registering Workroom's key needs it; and a refresh token comes only with `offline_access` and `prompt=consent` together. On the consent screen the user ticks which workspaces to share, and the token reaches only those, so the sheet lists the granted workspaces (`me { workspaces }`) for the `Workroom` project of [ADR 0071](0071-railway-hosts-never-idle-out-and-each-mac-has-its-own-environment.md), and when its workspace is not among them it says so and offers to sign in again. The refresh token goes in each build's own Keychain item: Release, Nightly and Dev each sign in once. A Keychain access group the builds share needs a provisioning profile on macOS, which neither build carries, and two sign-ins cost only one extra consent, since Release and Nightly still share the project, environment, ssh key and hosts of [ADR 0071](0071-railway-hosts-never-idle-out-and-each-mac-has-its-own-environment.md). Each build's grant is its own authorization at Railway, so one build refreshing never rotates the other's token. Access tokens last an hour and are refreshed by one owner at a time, which always stores the newest refresh token, since a rotated one fails and forces a new sign-in. Signing out is allowed while Railway workrooms exist, with a warning that their sandboxes keep running and billing; they show signed out, with Sign in, until the user signs in again.

Rejected: one sign-in shared through a Keychain access group. It needs a Developer ID provisioning profile embedded in both builds and renewed in CI signing, for the sake of one consent screen. Rejected: the file-based keychain with an access list naming both apps, on deprecated APIs that can prompt after an update changes the signature. Rejected: driving the user's `railway` CLI, for the region, size and config side effects above. Rejected: a pasted workspace or account token. It is one manual copy from Railway's dashboard, and an account token reaches every workspace. Rejected: reading the CLI's session from `~/.railway/config.json`, a private format. Rejected: a project token, which can't register an ssh key. Rejected, because Railway has it turned off: a client each install registers for itself by dynamic registration. Not yet weighed, both offered by Railway's discovery document: the device-code grant, which needs no localhost listener, and a client ID metadata document, which needs no registered app.

Source: [`docs/designs/railway-sandboxes-research.md`](../designs/railway-sandboxes-research.md) (section 5), Railway's OAuth docs: <https://docs.railway.com/integrations/oauth/creating-an-app> (app types) and <https://docs.railway.com/integrations/oauth/login-and-tokens> (refresh and rotation), <https://docs.railway.com/integrations/oauth/scopes-and-user-consent> and <https://docs.railway.com/integrations/oauth/fetching-workspaces-or-projects> (scopes and workspace selection).
