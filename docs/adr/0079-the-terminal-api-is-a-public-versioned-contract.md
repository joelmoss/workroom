# The terminal API is a public, versioned contract: a JSON service on the daemon's stream that only ever adds fields, with `workroom` commands as thin clients

Decided 2026-11-19 (owner, terminal API design for #360); built from 2026-11-20 (#683). The `api.*` namespace, `InvalidRequest`, `workroom sessions [TARGET]` with `session.resolve`, the exit codes past a target and `DaemonTooOld` were settled while building it, decided 2026-11-20. So were `workroom api`'s names, before any of the API reached a release tag and the add-only rule froze them: the `revision` reply field, `examples` as the only examples, `error_schema` in `api describe` and `api.describe`, each subcommand's envelope name, and `call` with no PARAMS, decided 2026-11-20 (#685). Extends [ADR 0013](0013-cli-json-contract.md) and [ADR 0078](0078-one-rust-binary-named-workroom.md). The socket stays the only security boundary ([ADR 0043](0043-agent-socket-trust-boundary-is-shell-grade.md)).

Coding agents and the user's scripts need to read, type into, wait on and watch a Workroom terminal from inside a pane, on the Mac and on hosts. Until now the only way into a session was the app's private binary protocol, which changes whenever the app needs it to. Callers outside the app can't keep up with that, and the app can't be held back by them. So the daemon gets a second, public way in, named the **terminal API**.

**How it works**
- **A service of its own.** It's `Service::TerminalApi` (byte `0x08`) on the daemon's multiplexed stream, added at protocol 12 (`MIN_TERMINAL_API_VERSION`). It isn't a new listener: the same socket, so the same trust.
  - A client checks the daemon's greeting before sending. An older daemon's envelope decoder fails the whole connection on a service byte it doesn't know.
  - The service never sends anything nobody asked for, so the app, which never calls it, sees no difference.
  - The app's handshake moves to protocol 12 with it. Negotiation still takes the lower version, so older apps and daemons are unaffected.
- **JSON request and reply, one stream per request.** A request is `{"method": "<namespace>.<name>", "params": {…}, "caller": "<session id>"}`, `params` and `caller` optional (`caller` under **Which pane is calling**). The reply is `{"revision": <revision>, "result": …}` or `{"revision": <revision>, "error": {"kind", "message"}}`. The API's number is named `revision` everywhere it appears, in the reply, in `api.describe` and in `workroom api call`'s envelope, not the `version` of the daemon's other services' replies (decided 2026-11-20).
  - Methods are named in namespaces: `session.*`, `terminal.*`, `client.*` and `events.*`, and `api.*` for the API describing itself (`api.describe`, the method under #360's `workroom api list | describe`). It describes the API, not a session, terminal or client, so it gets a namespace of its own.
  - Every method publishes the JSON Schema of its parameters and its result, and `api.describe` returns them, with the error's schema. So a caller can learn what a daemon supports without docs.
  - `session.resolve` turns a target into the one session it names, by the rules under **Targets**. Resolution happens on the daemon, so every caller gets the same answer.
  - `terminal.wait` (#690) answers when what it waits for happens, or with `WaitTimeout` once its `timeout_ms` passes, and the connection takes other requests meanwhile. Its one reply is a reply like any other, with `more: false`. A connection that closes cancels its waits. A regex is matched on the daemon against the output the session's reader already reads, escape sequences stripped, so nothing is streamed to the caller. The reader only copies each read into the wait's bounded queue, and the wait's own thread matches it, so no number of waits slows a session's output to its clients. A wait that falls a queue behind drops the read that doesn't fit and every one after it, matches what it kept, which came first, and failing that is `WaitInterrupted` (3), whose message says it fell behind and output was dropped: a match may have gone by unmatched, and a wait that went on would have to match across the gap or wait on its timeout, or forever, never knowing. That is what the kind already says after a hand-off, so no new kind (decided 2026-11-20, owner). A status, a run state and the session's end are states, so one already true answers at once; output and a command's end are events, so only those after the wait starts count. A run state the run passes through reaches a wait however soon the next replaces it (`stopping`, which a restart goes straight on from to `starting` and `running`): the run supervisor appends each transition, numbered, to a bounded log beside its status file (`<session>.status.log`, started afresh every 64th), and the daemon's runs watcher hands each to the run's waits, those after the wait started. The status file, which the app's state comes from, is unchanged. A run whose supervisor writes no log, one an older daemon started and a hand-off adopted, is heard from its status file's changes, as before, so a transient state can go unheard there. Nothing of the API has shipped, so the revision stays 1. A client reads a wait's answer for as long as its `timeout_ms` and 10 s more, or with no limit when it has none, so neither `workroom wait` nor `workroom api call terminal.wait` reads a long wait as a daemon gone quiet (7).
    - **Names** (decided 2026-11-20, owner). The result's run state is `run_state`, since a session's `run` in every listing is a boolean, whether it is a run session. `command_finished` (`--command-finished`) waits for the next command to finish, the first to end after the wait starts, whether it was running then or starts later; the CLI's help and the API's schema both say so. The input `ended: true` keeps its name: each condition's input key is the name the result's `condition` gives it.
    - **`exit_code` reports, it doesn't filter** (decided 2026-11-20, owner). A wait for `run: exited` with an `exit_code` answers when the run exits, whatever its code: a run that exited 1 will not exit 0 until it is restarted, so waiting on would only run to the timeout, or forever. With the code asked for it is met, and `workroom wait` exits 0; with another it is `ExitCodeMismatch` (3), whose message says which code it was and whose `details.exit_code` carries it (null when unknown), so a `--json` caller reads the code rather than parse the message. That kind is new: none in the registry says "it happened, but not as asked", and reusing `ConfirmationMismatch` or `SessionEnded` would give either a second meaning. It is 3 because it is a precondition of the caller's that failed, as the others in 3 are (kind, name, number and `details`, decided 2026-11-20, owner). `details` is an error's object for what a kind says beside its message; `api.describe`'s `error_schema` lists its fields, and a kind with none leaves it out, as `matches` is left out but for `TargetAmbiguous`.
    - **Bounded** (decided 2026-11-20, owner). Each wait is a thread and a matcher on its session's output, so a daemon holds about 32 waits on one session, 64 from one connection and 512 in all. One past a bound is refused at once with `Busy` (3), as a capture past its bound is, and a retry once a wait has ended gets past it. Bad input and a target that names no one session are refused as such before any bound is looked at. A wait whose thread can't start is `InternalError` (1), and leaves nothing held. A regex wait holds at most 256 KiB of output it hasn't matched, queued and being matched counted together, in 8 KiB chunks, and a window of 16 KiB and a chunk: about 320 KiB as allocated, so 160 MiB for 512, and only while waits are behind sessions printing flat out. The 256 KiB is the burst a wait gets through before `WaitInterrupted`, so it stays, and the copies beside it were cut instead (an earlier queue held one batch while matching another, and its window grew by a whole batch, about 784 KiB a wait). Besides that, `include_screen`'s screen text, once, and the regex, compiled twice (to search, and as the lazy DFA that says when a match is settled), each program and its cache capped at 1 MiB, a few KiB for a pattern such as `ready in \d+ ms`. These are implementation limits, not contract: a release may change them without raising the revision. So is the order of refusals: a precondition the session fails, such as `NoShellIntegration`, comes before `Busy`, which a retry gets past and a precondition never does.
    - **What a regex matches** (#690). The answer is the regex's first match, leftmost-first, in the session's output since the wait started with its escape sequences and other controls but `\t`, `\n` and `\r` stripped: what one search of that whole stream would find, however it arrived, in one read or a byte at a time, and however the wait's thread took the reads. So a match is answered only once more output can't change it (the lazy DFA's state says when): `TICK-\d+` answers `TICK-12` once a byte that is no digit follows, never `TICK-1` because a read ended there, and a match that can end in an assertion (`ready$`, `\bok\b`) once a byte follows it, since that byte decides it. A literal is answered the moment it is all there, and the session's end, or the output going quiet (below), settles what is left. A test checks this answer against the whole stream stripped and searched once, for every split of small streams and a seeded sweep of generated ones. The one approximation: a pattern with no bound on its length and a Unicode `\b`, over text that isn't ASCII (where the lazy DFA gives up), is answered once a line ends after its match, and a longer match a later line completes can be missed; with a bound, it waits for the bound's worth of output after the match's start and the whole of the character there, as long as its UTF-8 says (`Ready…` answers `\bReady\b` once the three bytes of `…` are in), which is exact. The window is the last 16 KiB of that text, cut wherever it falls, and a match longer than it may be missed; what came just before it is kept beside it, so anchors at its start see the stream as it was. **Anchors:** `^` and `$` are line anchors, `\r\n`, `\n` and `\r` line ends; `$` needs a line's end, or the output's once it stops: the session's end, or a quiet. The wait's text starts a line, its first output or the screen's top row with `include_screen`, so `^` and `\A` match there; a wait that joins inside an escape sequence starts mid-line as far as is known, where neither does. `\A` (and `(?-m)^`) matches only at that start, while the window still holds it, and `\z` (and `(?-m)$`) only where the output stops. The owner decided the window keeps the bytes a match needs rather than trim at a line, and that the answer is split-invariant (2026-11-20). **Output that goes quiet** settles too (decided 2026-11-21, owner), expect-style: once a regex wait's output has had nothing new for a quiet period, what it holds is answered as the session's end would answer it, the output so far searched once as if it ended there. So `$` matches the end of the output so far, and a match that could still grow (`\d+`, a greedy tail, `Password: $`) is answered once the program waits, the screen's text with `include_screen` included. Output that arrives before the period is up starts it again, so output that keeps coming settles nothing early. The timer runs on the wait's own thread, from when it took the last batch, so the session's reader pays nothing for it. The period is 200 ms (`terminal::wait::QUIET`), an implementation value a release may change; that a quiet settles is the rule. The split-invariance test checks a quiet at the output's end, between two pieces and inside a character against the same oracle, cut where the quiet falls; a quiet inside a character settles the output so far as it stands, its last character cut short, as the rule says.
    - **Shell integration** (#690). `command_finished` needs the shell's OSC 133 marks, and whether a shell has sent one crosses a hand-off with its program status, so the next program doesn't refuse the wait until the shell's next prompt. A session younger than about 5 s with no mark yet may still be starting its shell, so a `new` followed at once by a wait gets until then for the first one, and is `NoShellIntegration` only if none comes; its `timeout_ms`, when sooner, is `WaitTimeout` as for any wait. An older one is refused at once.
    - **Across a hand-off** (decided 2026-11-20, owner: the CLI reconnects and resumes). A hand-off replaces the daemon's program in place and closes every client connection, a waiting one's included, but keeps the listening socket, so the new program takes a connection at once. When the daemon hangs up on a wait before answering, `workroom wait` and `workroom api call terminal.wait` connect again: nobody listening is 7, as ever. A wait for a state (`status`, `run`, `ended`) is sent again with what is left of its `timeout_ms`, and the new program answers as the old would have, since a state already reached is met at once; the CLI says on stderr that it went on. Such a wait is pinned to its session's id first (`session.resolve`, which resolves as the wait does), and sent again by that id. The first time, it is sent as given, so the daemon checks it as any request, bad input before an unknown target, and its errors name the target as typed, as do those of the wait sent again; a target that names no one session pins nothing, and fails as the wait finds. A session that ended between the two programs is gone from the new one, which says `TargetNotFound`, and the CLI answers as the old program would have, met for `ended` (its exit code unknown) and `SessionEnded` for `status` and `run`. A target that never named a session is still `TargetNotFound`. A wait for an event (`regex`, `command_finished`) is `WaitInterrupted` (3, a new kind, which the daemon sends too, for a regex wait that fell behind), not re-armed. A session's unread output stays in its pty while the old program is frozen, but output read, or a command ended, between the new program's readers starting and the wait reaching it would never be seen, and a re-armed wait for something that went by in that gap would wait to its timeout, or forever, with nothing on stdout to say why. Refusing at once says so, and a script that can live with the gap waits again. The kind's name is the builder's, for the owner to settle before a tag.
- **Fields are only ever added.** No field or method is removed, renamed or given another meaning. The API's **revision**, in every reply and in `api.describe`, counts the additions, and a caller that needs a later one checks it. It's the service's own number, separate from the protocol version, which only says whether the service exists. It is 1 until the first release that ships the terminal API, whatever changes before then; the add-only rule and the count start from that release (decided 2026-11-20).
- **The commands keep ADR 0013's contract.** `workroom sessions`, and each later command, prints one envelope on stdout with `schema_version` and passes the API's objects through as they are. Errors carry a `kind` from the registry every `workroom` command shares. The daemon replies with those codes by name, and the CLI exits with their numbers.
  - A missing or ambiguous target is 3, like the CLI's other not-found errors.
  - A valid request the session can't take now is 3 too, like the CLI's other precondition errors: `AgentBusy`, `NotAnAgent`, `SessionEnded`, `AlternateScreen`, `NoShellIntegration` and `RefusedSelf`. So a script can tell "not now" from "broken" by exit code alone.
  - A daemon at a limit on concurrent work refuses with `Busy` (3), so a script can retry (decided 2026-11-20, owner).
  - Bad input to a request is 2: `TooLarge`, and `InvalidRequest` for a request the daemon can't read, such as an unknown method or parameters it refuses. It's #360's malformed request, a kind of its own so that a refused request isn't reported as `InternalError`.
  - A malformed command line is still 1, `InternalError`, for these commands as for every other: they share one parser, which keeps Go's rule.
  - New exit codes: 7 when no daemon can be used and 8 for `WaitTimeout`. 7 is `DaemonUnreachable` when no daemon is named or none is listening, and `DaemonTooOld` when the one reached is below protocol 12 and so has no terminal API. They're two kinds because the fix differs: a missing daemon is started, an old one is updated, and the message says which.
  - Anything else is 1.
  - An ambiguous target's error lists its matches, in the envelope too.
- **`workroom api list | describe METHOD | call METHOD [PARAMS]` (#685).** Raw access to every method, asked of the daemon reached, so it says what that daemon supports. Each method's input and output schemas, and the error's, carry examples under JSON Schema's `examples`; a reply gains no field, so the revision stays 1. PARAMS is inline JSON, `@FILE` or `-` for stdin. PARAMS that aren't UTF-8 JSON, or can't be read, are `InvalidRequest` (2); whether a method takes them is the daemon's to say. `call`'s envelope nests the reply as `method`, `revision` and `result`, so no result field can stand in for one of the envelope's own.
  - Each subcommand's envelope names it: `command` is `"api list"`, `"api describe"` or `"api call"`, success and failure alike, one name per payload shape as Go's `"trust status"` is (decided 2026-11-20).
  - The error's schema is `error_schema`, not `error`, which every failure envelope and every failed reply uses for the failure itself: in `api describe`'s envelope, and in the `api.describe` method's own result on the wire, so the two read alike (decided 2026-11-20).
  - A schema's examples are only under `examples`. The single `example` beside each method's schemas, which #683 added, is gone (decided 2026-11-20); nothing of the API had shipped in a release, so the revision stays 1. Example values are illustrative and not covered by the add-only rule: a release may change what an example shows, but not the schemas.
  - `call` with no PARAMS is allowed and sends `{}`, so a method that takes nothing needs nothing typed (decided 2026-11-20).
  - `call` reads `@FILE` and `-` no further than one byte past 1 MiB, what one request can carry. PARAMS, or a request, over that are `TooLarge` (2), refused before any daemon is looked for, so `yes | workroom api call METHOD -` ends and oversized input exits 2 even with no daemon.
- **`workroom sessions [TARGET] [--all]`.** With no target it lists the caller's workroom's sessions, or every session with `--all` (`session.list`); with one it shows the session that target names (`session.resolve`), or fails as any target does. So a caller can check what a target names before acting on it.
- **A reply can come in parts: the stream rule** (#686). Any method may send several replies on the request's stream, in order, each a whole reply. Every reply, one alone included, carries `more`: `true` when another reply follows on the stream, `false` on the last. It's the reply's, beside `revision` and outside the method's `result`, so a caller reads every method the same way, until `more` is false, without knowing which methods stream. An error is always a stream's last reply (`more: false`), and a reply with no `more` counts as the last. A daemon stops making a stream's replies once the caller hangs up (decided 2026-11-20).
  - `workroom api call` prints every reply of a stream as it arrives, one envelope per line with `--json`, each with `more`, until `more` is false.
  - `terminal.capture` with `all` streams: the whole scrollback is cut into chunks of whole lines, numbered by `chunk`, so no reply has to hold 50 MB. `workroom capture --all` writes each as it arrives, one envelope per line with `--json`, and stdout's end is the stream's. The chunks are one copy of the terminal, so output arriving meanwhile doesn't shift them.
- **`workroom capture TARGET`** (#686). The visible screen as plain text, trimmed as Ghostty trims what it copies; `--lines N` adds N rows of history and `--all` streams the scrollback; `--unwrap` joins lines the pane wrapped; `--vt` keeps escape codes. Every reply has the cursor, size, whether the alternate screen is up and the live title.
  - **The alternate screen.** The visible screen is the active one, so a full-screen program's alternate screen while it has it up. The history is the primary screen's, the only history there is: `--lines` and `--all` add it above the visible screen on either. Under a full-screen program that is the shell's lines, its scrollback and its screen down to its last line of text (not the blank rows below it), which only a copy of the terminal reaches. `alternate_screen` says which screen is visible. Never `AlternateScreen`: a capture reads, so a program in the way is no reason to refuse (decided 2026-11-20).
  - **Bounded under the session's lock** ([ADR 0051](0051-shadow-keeps-the-apps-history-and-sends-a-bounded-tail.md)'s rule). Only the screen and up to 100 rows of history are formatted on the live terminal. More, and all of `--all`, come from a copy taken under the lock (about 27 ms on 50 MB, as a repaint's primary screen costs) and formatted after it is released, 500 rows at a time, each window sent as it is done: the pty reader and attaches never wait on a big format, the first chunk comes after one window, and a capture holds the copy and one window, never the whole text. A daemon runs 4 captures from a copy at once; a fifth is refused at once, not queued, so it never waits behind a stalled reader and its caller never reads the wait as a daemon gone quiet. The refusal is `Busy` (3), which a retry once a capture has finished gets past.
  - **The bounds are implementation limits, not contract.** 100 rows of history formatted live, windows of 500 rows, and 4 captures from a copy at once are what this daemon chose, and a release may change them without raising the revision. What a caller relies on is what the replies say: `more` and `chunk` for a stream, `Busy` and `TooLarge` for a refusal.
  - **`--lines` is one reply.** Rows it can't hold even at a byte a cell (rows × (columns + 1) past the reply's 16 MiB) are `TooLarge` before anything is copied, and a format that runs past the reply stops there as `TooLarge`; `--all` streams any length. A daemon built without terminal-state keeps no screen, nor does one whose shadow terminal failed, and a capture there is `InternalError` (1) whose message says which. It has no kind of its own: no caller acts on it differently from any other broken daemon (decided 2026-11-20).
- **`workroom events` and `events.subscribe` (#687).** The daemon's events as a stream (the stream rule's), one JSON object per line on stdout, or with `--json` one ADR 0013 envelope per line (`command` `"events"`), the event's fields in it. It runs until it is stopped or its reader goes; a quiet daemon is one with nothing to tell, so the CLI reads it with no timeout, and the request's thread is its own, so the connection takes other requests meanwhile (as a wait's).
  - **The stream.** The sessions as they are, one `session` event each, then `snapshot-complete` (its `sessions` the ids, its `reason` `subscribed`), then live events as they happen: `session.created`, `session.ended`, `session.program_status`, `session.run_state` and `session.moved`, `client.attached` and `client.detached` (#688, below), and `session.input` (a send, #689, below). Every event has `event`, `boot` and `revision`; every one about a session has `session` (its id) and `scope`. The names are the namespaces' (`session.*`; #360's later client and typing events are `client.attached`, `client.detached` and the like), and the fields are the ones the API already has: `session`, `scope`, `label`, `title`, `run`, `cwd` and `coding_agent` as `session.list` gives them, and `run_state` and `exit_code` as `terminal.wait` does. `session` events and `session.created` carry the whole session, `run_state` included; `session.ended` its shell's `exit_code` when the daemon saw it. `snapshot-complete` keeps the program-status service's name, which #360 gave it. Callers ignore an `event` they don't know: later revisions add some. (Names and fields decided 2026-11-21, builder's, for the owner to settle before a tag.)
  - **Which events.** By default the caller's scope's, as `session.list`: the caller's workroom's sessions, or every session's from no pane or from one with no scope. `--workroom ID` keeps to that workroom's (a session's `scope.id`), `--all` widens to every session (not with `--workroom`), `--session TARGET` keeps to the one session the target names as the stream starts, wherever it is: naming one drops the default scope, though not a `--workroom` given beside it (decided 2026-11-21, owner), and `--type`, repeated or comma-separated, to those live event types. A snapshot keeps to the sessions the scope and `--session` pass, whatever `--type` says, so a script always starts from the state.
  - **Program status as an event.** `session.program_status` is sent when the coding agent's state, program or `waiting_on_user` changes, or its message does while it isn't `working`: an agent may report a message per token while it works, which is no event each time, and `session.list` and every snapshot have the latest. A blocked agent's new question is an event.
  - **Run state as an event.** Every transition of a run, from the supervisor's transition log (#690's), each once by its number, so `stopping` on a restart is told however soon `starting` follows. A run with no log (one an older daemon started) is told its status file's changes. Accepted (2026-11-21, owner): a transition the runs watcher sees before the session's `session.created` is told is dropped, a window under a millisecond between the store taking the session and its creation being told, before its supervisor has started.
  - **A session moved** (decided 2026-11-21, owner). A session the app tags with another workroom (its `Retag`) is `session.moved`: `session`, `scope` the one it joins and `previous_scope` the one it leaves, sent to the subscribers of either scope and of every session. From then on it is the new scope's: its events reach that scope's subscribers and not the old one's, and that scope's next snapshot holds it.
  - **Where a filtered stream stands** (`place`, decided 2026-11-21, owner). A stream whose filters skip events would otherwise only ever hear its last passing event's revision, which the ring may long have dropped, so resuming would be a `gap`. So once skipped events have moved it on, the daemon sends `{"event": "place", "boot", "revision"}`, the revision it has reached, at most once a second. A caller resumes from it like any event's; `workroom events` never prints it, and `api call` prints it as any reply.
  - **`boot` and `revision`: one numbering, daemon-wide** (decided 2026-11-21, builder's). Every live event takes the next `revision` of the daemon's events, from 1, under a `boot` that names that numbering: kept across a hand-off, new when the daemon starts afresh. Not program status's per-session revision: a script's place in a stream of several sessions' events, and of later events that are no session's state (a client attaching, typing), is one number, the same one it resumes from (#360's story 34). Each live event's revision is higher than any before it; a filtered stream skips the ones it doesn't pass, so revisions are not consecutive, and the only evidence of loss is a snapshot (below). A snapshot's events and its `snapshot-complete` carry the revision it was taken at. `revision` inside an event is the event's place; the reply's `revision` around it, on the wire and in `api call`'s envelope, is the API's, as ever. In `workroom events --json` only the event's appears, since the envelope carries the result's fields.
  - **What a snapshot is.** The daemon keeps, beside its last events, what they add up to: each live session, its coding agent and its run state, changed by each event under the same lock. A snapshot at revision R is exactly R's, and a subscriber starting from it hears every event after R and none before, so a session created as it subscribes is in the snapshot or a `session.created`, never both. The fields no event tells (`label`, `title`, `cwd`) are read live as it is sent.
  - **Resuming** (`since`). `events.subscribe` takes `since: {boot, revision}`, the last event a caller had. When the daemon has that boot and still keeps every event after it, it answers `resumed` (its `boot` and that `revision`), then each of them the filters pass, then live ones: nothing missed, nothing twice. When it can't (another boot, a daemon started afresh; or older than it keeps), it sends the sessions afresh, a snapshot whose `snapshot-complete` says `reason: gap`, which replaces what the caller knew.
  - **Across a hand-off** (decided 2026-11-21, builder's). A hand-off closes every connection, so `workroom events` (and `api call events.subscribe`) connects again, as a wait does, and asks with `since` the last place it reached: a live event's, a `place`, or a snapshot's end, never a snapshot's middle. The new program has that place: the hand-off table carries the boot, the revision, the last events and what they add up to (table version 4; a table from before carries none, and the next program starts a boot of its own, which is safe because no program that wrote one ever served events). The old program seals what it carries as it writes the table: an event made after that is held back, never sent, so no client hears a revision the next program numbers again, and sent after all if the hand-off is called off. A session's end is told under `TERMINATING`, with its removal from the store, so what is carried never holds a session the table doesn't. The next program adopts every session with its reader held back, compares the carried state with what it adopted, tells what changed (a session created, or whose coding agent changed, while the hand-off was under way), and only then starts the readers: a shell that ended meanwhile is seen ending by its reader, one `session.ended` with its exit code, never a session the events go on holding. A run's transitions logged meanwhile are told from its log, after the last one told. The CLI swallows `resumed`, says on stderr that the connection ended and it asked again (nothing on the wire tells a hand-off from the daemon closing a reader too slow), and prints the rest, so a script reading stdout sees one stream. When the new program can't go on, the sessions come afresh as above, and stderr says events may have been missed. `--session`'s target is pinned to its id before the first request, so a session that ended meanwhile is still the one asked about. Nobody listening is 7, as ever; the CLI gives up after 16 hand-offs with no live event between, as a wait does.
  - **Bounded, and a slow reader slows nothing** (decided 2026-11-21, builder's). The daemon keeps its last 1024 events in one ring, which each subscriber reads from its own place: an event is appended under a short lock and the subscribers woken, so a publish (a session's reader, the runs watcher) never waits on any subscriber, and one that stops reading costs nothing but its place. One that falls further behind than the ring holds is not cut off and not sent a gap silently: when it next reads, it is sent the sessions afresh, a snapshot whose `snapshot-complete` says `reason: lagged` (the events it was never sent were dropped), and goes on live from there. So the signal for lost events is always the same, in band, and the stream doesn't end for it: an error would end a long-running script's stream for something a snapshot repairs. A reader that reads nothing at all for the transport's write timeout (10 s) fails the write, which may leave part of an envelope behind, so the daemon closes that connection; the CLI connects again with `since`, as after a hand-off, and is answered `resumed` or, past the ring, `gap`. The ring is capped by count, not bytes: an event is at most about 5 KB (a session's label, title and cwd, a coding agent's 512-byte message), so the ring, and the table a hand-off writes inside its frozen window, hold at most about 5 MB of it (accepted 2026-11-21, owner). Each subscription is a thread, so a connection holds 8 and the daemon 64; one past either is refused at once with `Busy` (3), and a retry once one has ended gets past it. Bad input and a target that names no session are refused first. 1024, 8 and 64 are implementation values, not contract, as a wait's bounds are; that a lagged subscriber is sent `lagged` is the rule. The kind registry is unchanged.
- **`workroom sessions --clients` and the client events (#688).** A client is an attach: a connection whose Terminal-service `Attach` the daemon registered on a session, which is what has a size, may own it ([ADR 0042](0042-clients-share-a-session-size-owner.md)) and may be probed (#593). The terminal API's own callers (`wait`, `events`, `capture`) never attach, so they are no session's clients.
  - **Who a client is, said on the attach** (decided 2026-11-21, builder's). The attach request names the client's kind (`CLIENT=pane|app|cli`) and its machine (`HOSTNAME=`), two more of its `KEY=VALUE` entries. A daemon from before them ignores entries it doesn't know, and a client from before them sends none, which this daemon lists as null, so neither needs a protocol version. A kind this daemon doesn't know is null, and so is a hostname that isn't UTF-8, is empty, is longer than 255 bytes or holds a control character: never kept or cut, since a cut name could be another machine's. `workroom attach` says `pane` when the app started it (its session variables, or `--dial`), else `cli`. Its hostname is its own machine's, except for the attach the app runs on a host (`--no-spawn`, the container driver's), whose own name would be the host's passed off as the Mac's: it says the Mac the app names in `WORKROOM_SESSION_HOSTNAME`, or none; the app sets it there to this Mac's `gethostname`, the name a local pane's attach gives. The app never attaches over its own service connection, which is what `app` is for (its daemon connection refuses the Terminal service), and the only attach it encodes itself is the retired Swift helper's, a frozen protocol to a different daemon, so `app` is the name kept for an app that does, sent today only by a client built for it.
  - **The fields** (names decided 2026-11-21, builder's). `session.list` and `session.resolve` take `clients: true`, a boolean beside `all`, which adds each session's `clients`, in the order they attached: `id`, the attachment's number, unique within the boot; `kind`, `pane`, `app`, `cli` or null; `hostname`, or null; `attached_at_ms`, milliseconds since the Unix epoch, a whole number, the unit in its name as in `timeout_ms`; `size`, `{columns, rows}` as `capture` gives it, 0 by 0 for a client with none yet; `owns_size`; and `keepalive`: `off` (it didn't ask to be probed), `answering` (it asked and has missed no probe, which a client not yet sent its first hasn't), `late` (one or more missed in a row) or `stale` (missed enough that it no longer counts as attached, and its connection is being closed). A string, not a boolean, so a later state can be added; a client not yet probed is `answering` rather than a state of its own, since nothing it did differs from one that answered. Without `clients` a reply is as it was. A daemon that knows `clients` lists it for every session asked, `[]` for none, so a session without it is from a daemon from before, which ignored the parameter: `workroom sessions --clients` then fails `DaemonTooOld` (7), as a daemon with no terminal API does, rather than show no clients; `api call` shows the reply as it came. Nothing of the API has shipped, so the revision stays 1. `workroom sessions --clients` asks for them: with `--json`, each session's `clients`; for a person, each client as a row under its session's, indented and lined up across every session's clients, with how long ago it attached (layout decided 2026-11-21, owner).
  - **The events.** `client.attached` and `client.detached`, each with `session`, `scope` and `client`: the client's `id`, `kind`, `hostname` and `attached_at_ms`, which stay true for as long as it is attached. Its size, whether it owns it and its keepalive change with no event, so only the listing has them. A snapshot's `session` events and `session.created` carry `clients` in the events' shape, as of the snapshot's revision. A client leaves once, whether its connection ended or the daemon dropped it for not reading. A session's end is its clients' too, with no `client.detached` each. A client's coming and going is told under the attachment lock that changed it, so the events' clients change in the order the session's do: a client dropped as it attaches is told arriving, then leaving. `--type` and `types` take both.
  - **Across a hand-off.** It closes every connection, and no client comes with an adopted session, so the next program tells each client the carried events hold as `client.detached` before any of its own attaches, and numbers its clients past the highest number the boot gave out, carried in the table beside the events, whether that client is attached still or left long before, so an `id` names one client in a boot. A table from before (version 4 all the same) carries no clients and no number, and adopts as holding none.
- **`workroom send TARGET [TEXT]` and `terminal.send` (#689).** Types into a session without attaching to it. Its params are `target`, `text`, `keys` (names, in order), `enter` and `allow_self`; the CLI's are TEXT (or `--stdin`, stdin's text exactly as it comes, which a shell's `$(…)` would not keep), each `--key` repeated, `--enter` and `--allow-self`. What it types is the text, then the keys, then Enter. Its reply is `session`, `caller`, `bytes` (what was typed, a paste's markers included) and `modes`, the session's modes it was encoded for (`kitty_keyboard_flags`, `application_cursor_keys`, `bracketed_paste`); `workroom send` prints nothing but with `--json` that envelope (`command` `"send"`). The names `terminal.send`, `allow_self`/`--allow-self`, `session.input`, `--stdin`, `modes` and `sender` are kept, and `kitty_flags` became `kitty_keyboard_flags`, the protocol's own name (decided 2026-11-21, owner).
  - **No client.** The bytes go to the pty and nowhere else, and the session's attachment lock is never taken: no repaint, nobody counted as attached, no size claimed or arbitrated ([ADR 0042](0042-clients-share-a-session-size-owner.md)) and no keepalive probes, so a send changes nothing anyone watching sees but the program's answer to it. A client's typing and a send each take the pty's input in turn, so a client's keystrokes never land inside a send's paste, nor one send inside another. The one write outside that turn is the daemon's answer to a program status probe (OSC 7501, written by the session's reader): it is written as it comes, without waiting, and can land between two writes of a long paste, inside it. Accepted (decided 2026-11-21, owner): the reader must never wait on a writer, as a send can take 30 s, and every client's output would stop meanwhile; the answer is a few bytes a program asks for, rarely, and only one in the middle of a paste is inside it.
  - **Text exactly as given**, as a bracketed paste (`CSI 200~` … `CSI 201~`) when the program has turned bracketed paste on (`CSI ? 2004 h`), which the shadow terminal knows, so a multi-line text isn't run a line at a time. With paste off, the text goes as it is, its newlines run line by line; inside a paste, control bytes go as they are too. Both are "exactly as given", which a caller asked for (accepted 2026-11-21, owner). Text holding the paste's end, as `ESC [ 2 0 1 ~` or as C1's CSI (U+009B, UTF-8 `C2 9B`, then `201~`, which a terminal reading C1 controls takes the same), is refused as `InvalidRequest` (2), in any mode, rather than stripped: stripped, it would not be the text given, and left in, what followed it would reach the program as typed keys. Refused in any mode, so whether a text is accepted doesn't hang on a mode of the moment (decided 2026-11-21, owner).
  - **Keys** (`terminal::keys`) are named `Enter`, `Tab`, `Escape` (or `Esc`), `Backspace`, `Space`, `Up`, `Down`, `Left`, `Right`, `Home`, `End`, `Insert`, `Delete`, `PageUp`, `PageDown`, `F1`–`F12` or one character, after any of `Ctrl+`, `Alt+`, `Shift+` and `Super+`, in any case; a letter with a modifier is any case (`Ctrl+C`), alone it is the one typed (`A` is `Shift+a`). Each is encoded as the pane's terminal, Ghostty, sends it for the session's modes: with no kitty keyboard flags, xterm's legacy encoding (cursor keys, Home and End as `SS3` under DECCKM with no modifier, `CSI 1;m X` with one, C0 controls for Ctrl, ESC before a key for Alt, a modified F3 as `CSI 13;m~`, and Enter, Tab and Escape with modifiers as Ghostty's `function_keys.zig` has them: `CSI 27;m;13~` for Shift+Enter or Ctrl+Enter, `CSI 27;5;9~` for Ctrl+Tab, `CSI 27;m;27~` for Shift or Ctrl with Escape, but Alt alone, which puts ESC before the key, and Shift+Tab, xterm's `CSI Z`; Backspace is DEL, BS with Ctrl, ESC before either with Alt); with any kitty flag, the kitty keyboard protocol's (`CSI 99;5u`, Escape `CSI 27u`, never `SS3`, since Ghostty consults DECCKM only for the legacy encoding), Enter, Tab and Backspace unmodified and text keys with at most Shift staying as they were unless the program asked for every key as an escape code (flag 8), with the shifted key (4) and the text (16) when it asked for them. A press only, never a release; modifyOtherKeys isn't tracked, so keys are encoded as Ghostty encodes them with it off (its mode 2 changes Alt with Enter, Tab or Escape and every modified Backspace), and there are no keypad keys. `--enter` is Enter encoded the same way, last. A unit test holds each encoding to the published tables (xterm's ctlseqs, the kitty keyboard protocol, Ghostty's function keys), and the end-to-end test reads what reached a raw-mode program under each mode.
  - **At most 1 MiB** typed in one call, text and keys together, a paste's markers aside; more is `TooLarge` (2), refused whole rather than typed in parts, so a paste never arrives half-typed. Text alone over it is refused before the target is looked for, as bad input always is, and the CLI refuses it before any daemon is looked for, reading `--stdin` no further than a byte past it. 1 MiB of text can escape to six times that as JSON (a control character is `\u001b`), more than one envelope carries, so the CLI sends `terminal.send`'s request in chunks, as the app's VCS requests go, up to the 16 MiB a daemon reassembles; every other request is still one envelope, and `api call`'s PARAMS still stop at 1 MiB.
  - **The caller's own session** is `RefusedSelf` (3) without `allow_self` (`--allow-self`), so an agent doesn't feed keystrokes into its own input by mistake. `close`'s refusal of the caller's own session (#693) takes the same flag.
  - **Without the shadow terminal** (a daemon built without terminal-state, or a session whose shadow failed) the modes can't be read: text goes as it is, never as a paste, and the reply's `modes` is null; keys are `InternalError` (1), as a capture there is, since an encoding guessed could be the wrong bytes for the program (decided 2026-11-21, builder's: an honest refusal for keys, and text, which needs no encoding, sent).
  - **Every send is told**, as `session.input` (`session`, `scope`, `sender`, the caller's id or null from no pane, and `bytes`; never the text), before it is typed. `sender`, not `caller`: in an event every subscriber reads, the caller is the subscriber, so the session the send came from needs a name of its own (decided 2026-11-21, owner). It is told so the app can mark who typed into a pane (#696) and a script can trace traffic between agents. `--type session.input` keeps to them. A send while a hand-off has sealed the events is refused as `Busy` (3), not typed untold: an event numbered then would never be sent should the hand-off go ahead, and nothing could tell it after. A retry once the hand-off is done gets past it, and the ring carries the events told before it.
  - **Bounded, and never cut off by a hand-off** (decided 2026-11-21, owner). A send types for at most 30 s (`terminal::api::send::DEADLINE`), its wait for the session's input included. The pty's write deadline (5 s) is for reading nothing, renewed by each write the program takes, so a paste to a program reading it as fast as it can is never cut off for taking longer than that in all; a client's typing gets the same. The CLI waits for a send's answer past both, 30 s, 5 s to close a paste and its usual 10 s, so a long send is never read as a daemon gone quiet. One stopped early says how many of its bytes went, and the write can't be taken back: `Busy` (3) when another input to the session held it to the deadline, which a retry can get past; `InternalError` (1) when its program read nothing for 5 s or read too slowly to take it all in 30 s, which a retry would meet again. A send holds a request permit while it types, as a repository command does, so a hand-off waits for it (its 2 s to quiet the daemon) and is refused when the send outlasts that, rather than cut it off with the exec; a send while one is under way is `Busy`.
  - **A paste is never left open.** A send stopped inside its paste writes the paste's end at once if the program takes it within the write deadline (one reading too slowly does); otherwise the pty owes it, and the next input to that pty, a client's keystroke or another send, writes it first, and is not written while it can't be, so nothing typed later lands inside the paste. A hand-off writes what is owed before it carries the sessions, for 100 ms; a program that hasn't read for that long and more keeps its paste open in the next program, which owes it nothing.
  - **The caller a daemonized tmux server's window names** (#684, above) is the pane its `WORKROOM_PANE` says, which may be another pane's, given that pane's environment by tmux: such a send is refused as that pane's own, or told as sent from it. Accepted (decided 2026-11-21, owner): the walk places every process in a pane's tree, and the socket is the boundary, not the caller's name.
- **`workroom command TARGET [--] COMMAND…` and `terminal.command` (#691).** Runs one shell command in a session and answers once it has ended, with its exit code and what it printed. Its params are `target`, `command` (one line), `allow_self` and `timeout_ms`; the CLI's are TARGET, the COMMAND's words, joined with spaces into one line as `ssh` joins a remote command's (so quoting in it is the session's shell's to read), `--allow-self` and `--timeout`, read as `wait`'s is. Its reply is `session`, `caller`, `exit_code`, `output` and `truncated`; `workroom command` prints the output and a newline (nothing for none), or with `--json` that envelope (`command` `"command"`), and exits with the command's own code. Answered from a thread of its own, as a wait is, and counted as one of the connection's, the daemon's and the session's waits. It needs the shadow terminal, which keeps the marks: a daemon built without terminal-state refuses it as `InvalidRequest` (2), as it does a wait for a command's end. (Names, fields and every choice below the builder's, decided 2026-11-21, for the owner to settle before a tag.)
  - **Typed as a send types.** The command goes through `terminal.send`'s typing (`send::type_into`): its text as a bracketed paste when the shell has turned that on, then Enter as a key, outside the paste, which is what runs it; the 1 MiB bound, the 30 s deadline and its permit, and a `session.input` event naming the caller, as for any send. Pasted, not typed as keys, so the line is the shell's to run as given: a Tab in it completes nothing and nothing in it is a line editor's key. So a command is one line: a line end or any other control character (C0, DEL, C1) is `InvalidRequest`, in every mode, rather than typed as keys when paste is off and run a line at a time; an empty command, which no shell marks, is refused too. Join commands with `;` or `&&`.
  - **Paired with its own marks, race-free.** Its wait is added to the session under the locks every read holds, before anything is typed, and counts commands from there: the first command the shell ends after that (`terminal.wait`'s `command_finished`, the same count) is the one it typed. That holds because, under those locks, a session is refused when anything else could end first: one whose shell has a command open (an OSC 133 C with no D, prompt or input start since) is `Busy` (3), as is one with another `terminal.command` on it, so a script retries once it has ended; one with a full-screen program up is `AlternateScreen` (3), the registry's kind for it, unused until now. A program that took over after a hand-off left no C for the next program to see, so until the shell's next prompt the marks can't say, and the session is `Busy` while the pty's foreground process group isn't the shell's (a program it started has the terminal). Not that test alone: a shell inside the shell (`ssh`, `nix-shell`) sends marks of its own and runs its commands under a foreground that isn't the pane's shell. The exit code is the D's; a code outside 0–255, or none, makes `workroom command` exit 1.
  - **What the output is.** The bytes between the command's C (after its terminator, so not its options) and its D: not the command line the shell echoed as it was typed, which comes before the C, nor the prompt after the D. Kept as the session's reader hands each read to its waits, a scan for `ESC ] 133 ;` and a copy, never a format, and nothing dropped for falling behind, since nothing is queued; the session's end and the timeout come from the same count as any wait's. Once the command has ended they are rendered in a terminal of the session's size, its own, and read back as `terminal.capture --unwrap` reads a screen: plain text, escape codes gone, a line a progress bar redrew with `\r` as it last stood, a line the pane wrapped one line, trailing blanks trimmed and no final newline. As a capture reads, not as a regex wait strips (escape sequences out, `\r` kept): a command's output is read by a caller as the pane showed it, and each frame of a progress bar would fill an agent's context for nothing.
  - **Bounded.** The last 1 MiB of what the command printed is kept as it arrives (`wait::transcript::RAW_MAX`), from a line's start once its start is dropped, and the last 1 MiB of the text rendered from it is replied (`OUTPUT_MAX`), from a line's start: the end of a test run's output is where its summary is. Past either, `truncated` is true, and `workroom command` says so on stderr. Implementation values, as a wait's bounds are; that the end is kept, and `truncated` says so, is the rule.
  - **Without shell integration** a command's end can't be seen, and nothing is typed. A session whose shell has sent no mark, here or before a hand-off, is `NoShellIntegration` (3) at once; one younger than the marks' 5 s grace waits for its shell's first mark before typing, so a `new` followed at once by a command runs it at the first prompt, and one with no integration is refused with nothing run in it, rather than run a command whose end can't be seen and whose retry would run it twice.
  - **Its failures and the command's.** `command`'s own failures exit with their kind's number, as every command's do: a missing target or a session not ready 3, `DaemonUnreachable` 7, `WaitTimeout` 8. A command can exit with any of those too, so the exit code alone never says which failed, as #360 has it: with `--json` the envelope does (`ok`, `exit_code` beside it on success, `error.kind` on failure); without, a failure of `command`'s own is an `Error:` line on stderr with nothing on stdout, while all the command printed is on stdout, its errors too, since the pane's terminal merges them.
  - **`--timeout`** (`timeout_ms`) ends the wait with `WaitTimeout` (8), as `wait`'s does, and leaves the command running in the pane, never interrupted: `capture` reads what it printed. It covers the wait for a young session's first mark too, and one already out of time when the command would be typed (`--timeout 0s`) types nothing; the typing has its send's own 30 s, and the CLI reads the answer for the timeout, the send's time and its usual 10 s more, or with no limit when there is no timeout.
  - **Across a hand-off** the connection closes mid-command. `workroom command` (and `api call terminal.command`) never sends it again, which would type it a second time: with a daemon listening on the socket at once it is `WaitInterrupted` (3), as a `command_finished` wait is, since the command may have ended unseen in between, and with none 7.
  - **The caller's own session** is `RefusedSelf` (3) without `allow_self`, as for `send`.
- **Targets.** A session is named by its full id, then an id suffix of at least 4 characters, then its label, then its live title. At the first step with any match, more than one match is `TargetAmbiguous`, and nothing happens. The live title is what the program last set with OSC 0 or 2. The daemon reads it from the shadow terminal and carries it across a hand-off.
- **Which pane is calling (#684).** The daemon gives every session's shell `WORKROOM_PANE`, the session's id, and `WORKROOM_DAEMON`, its socket. Both are outside `WORKROOM_SESSION_*`, which a shell still never sees, and whatever an attach client forwarded under those names is replaced, since it names the pane the client was typed in.
  - The daemon finds the **caller** from the connecting process first: its peer pid (`LOCAL_PEERPID` on macOS, `SO_PEERCRED` on Linux), then up through its parents to a session's shell. A process can't be wrong about where it runs, and a variable can: a process in pane B may carry pane A's `WORKROOM_PANE`, from a shell or a tmux session started in A. So the walk wins, and covers `env -i` too (decided 2026-11-20, owner). On macOS each parent is read with `PROC_PIDT_SHORTBSDINFO`, which a user's daemon may read for root's processes too, so a command under `sudo` is still placed; `PROC_PIDTBSDINFO` refuses them, and the walk would stop at the first.
  - A request may also name its caller, the pane's `WORKROOM_PANE`, which the CLI sends. The daemon takes it only when the walk finds no pane and it names one of this daemon's live sessions. That is a process outside every pane's tree: one re-parented to init, or one under a daemonized tmux server, whose windows' shells are the server's children and see the environment of the client that started it. tmux's `update-environment` option can list `WORKROOM_PANE` and `WORKROOM_DAEMON`, so a window made after an attach from another pane is given that pane's.
  - Results that depend on the caller say which they found, as `caller`.
  - `session.list` lists the sessions that share the caller's scope, and `all: true` widens it to every session, as `workroom sessions` does by default and with `--all`. With no caller, or a caller with no scope, every session is listed. A boolean, not a `scope` string, because `scope` already names a session's `{kind, id}` in every listing (decided 2026-11-20, owner). That changes what `{}` lists from #683's every session, which is allowed because none of the API has shipped yet, so the revision stays 1.
- **Finding the daemon.** A command reaches the daemon `WORKROOM_DAEMON` names. Without it, it reaches the nearest daemon it runs under: a pane's shell is its daemon's child, so a command in a pane has that daemon among its parents, started as `serve --socket <path>`, which a hand-off keeps. The parent's binary must be named `workroom` or `workroomd` too, so another program taking the same arguments isn't taken for one. No other daemon is ever reached. `new` starting one is #693's to settle.

**Rejected**
- **Exposing the app's binary protocol.** It's private so it can change with the app. Freezing it for outside callers would freeze the app.
- **A second socket or a network listener.** A second socket adds a second thing to secure for no gain. A network listener needs authentication strong enough for shell access, which #360 leaves out of scope.
- **The session listing as `workroom list`.** That name is the workroom list (ADR 0013), and `list --socket` is the daemon's pinned listing (ADR 0057). The terminal API's is `workroom sessions`.
- **Versioning by protocol number alone.** Each addition would then bump the protocol, which also gates the app's services, for changes the app never uses.
