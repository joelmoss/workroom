# ssh trust follows who owns the key, and no Mac ssh credential reaches a host

**Superseded in part by ADR 0060 (2026-10-24):** the container driver no longer uses ssh, so it has no key or `ssh_config` of its own; a container is reached through its runtime's exec. The rest stands for boxd, exe.dev and SSH hosts.

Where Workroom or the provider tool owns the key (the container driver and boxd), the driver writes its own `ssh_config`, passes it with `-F`, and pins the host's key out of band with `StrictHostKeyChecking yes` and `BatchMode yes`, so nothing can prompt. Where the user owns the key (exe.dev, and the planned generic ssh driver, #378), the driver runs the user's own ssh with only a few `-o` overrides and checks the host key against the user's `known_hosts` through `HostKeyAlias`. The owner asked for ssh as close as possible to normal usage, and a fingerprint built into the app would need an update after every rotation. The one exception is a first connection: when the user's `known_hosts` has no key for exe.dev, the exe.dev setup sheet (`ExeDevSetup`) writes exe.dev's gateway key there once, and only when it matches the fingerprint exe.dev publishes, which the app pins (`ExeDevHostDriver.trustGatewayKey`), as answering ssh's first-connection prompt would. From then on the user's `known_hosts` decides, as before. The first exe.dev build chose a key itself and could pick the wrong account's. Under both policies no ssh agent is forwarded and no ssh credential from the Mac's environment reaches the host, because a forwarded agent dies with the laptop connection, exactly when remote workrooms matter. On a provider's host, git credentials are the provider's own (ADR 0049); a container workroom on this Mac takes them from the Mac's `gh` through a relay (ADR 0039). The cost is two opposite ssh policies in one app.
