# A container workroom runs any image, reached through its runtime's exec, and is made from the repository's devcontainer.json once this Mac approves it

Decided 2026-10-23 (owner, for #308; how, in the engineering review's D1 to D13). Status: accepted, built for #308 (2026-10-24). Supersedes the `workroom-host` image and the ssh path for local containers in [`docs/designs/remote-workrooms.md`](../designs/remote-workrooms.md), and the "only its ports are read" rule for `devcontainer.json`.

The owner wants a container workroom's image and container fully customisable. The `workroom-host` image couldn't be: the container driver needed its far side (sshd, a supervisor loop, host-key minting, the `workroom` user), so a stock image failed at connect, and a stale local copy failed the same way. ssh was only the carrier: port forwards and the credential relay already ride the daemon's own connection. So the container driver drops both. Its `exec`, `openStream` and pane attach run the runtime's `exec -i` and `exec -it` (`ContainerExecTransport`), and the container's entrypoint is the bundled static `workroomd serve`, under `--init`. Docker restarts it (`--restart unless-stopped`); Apple's runtime has no restart policy, so start-on-open stands in. The daemon gets in by `docker cp` on Docker, which is not a bind mount because Docker Desktop's file sharing may exclude `/Users`, and through a read-only bind mount of the app's own folder on Apple, whose `cp` can't reach a created container. ADR 0028's bar holds: a client of the runtime's socket already has a root shell in every container on it, which is at least a shell login. The image needs only git and a shell, with no sshd and no distro or libc requirement. The cost is one runtime CLI process per open pane: about 26 MB for Apple's `container exec` and 26 to 30 MB for Docker's, against 2.7 MB for `ssh`.

What the container is comes from the Development Containers spec. `.devcontainer/devcontainer.json`, or `.devcontainer.json`, gives the `image` or `build`, its `features` (fetched from their registry, ordered, built into a generated Dockerfile on both runtimes), `mounts`, `containerEnv`, `remoteEnv`, `remoteUser`, `runArgs`, `workspaceFolder` and the lifecycle commands. The checkout is cloned into `workspaceFolder`. A repository without the file gets a pinned default image (the devcontainers project's Ubuntu base, user `vscode`); there is no per-Mac setting, since another image is the repository's to name in its devcontainer.json (owner, 2026-10-24). A lone Dockerfile is ignored, as the spec has it. Keys Workroom can't honour leave the create going with a warning that names each, and a Compose config is refused with Continue With Default Image. A create resolves one base commit, and the config, its build context and the new branch all come from it.

devcontainer.json decides what the container mounts from this Mac and what runs there, so it is a script: it is used only once this Mac has approved its exact bytes, in ADR 0054's store, with the same Approve and a Continue Without that uses the default image. Approval covers that file only. A Dockerfile or feature it pulls in is not covered, as ADR 0054 says for what a script calls. That includes what a feature's own metadata asks for: bind mounts of Mac folders and `privileged` can arrive with a feature's new release, or a pulled change to a feature kept in the repository, without a new approval (owner, 2026-10-24). Refusing them would break docker-in-docker and docker-outside-of-docker, and approving each feature's metadata would ask again at every feature release. `initializeCommand` runs on the Mac before the build. After the clone and Copy local files, `onCreateCommand`, `updateContentCommand`, `postCreateCommand` and `postStartCommand` run in the spec's order as the remote user, then `scripts/workroom_setup`, so the setup script sees the container as VS Code would leave it. `postStartCommand` runs again on the first connect after each start of the container, never after an app update's hand-off, and panes wait for it. `postAttachCommand` is not run. A changed config applies to workrooms made after it: the container records the digest of the devcontainer.json it was made from, and the Details pane says when the repository's has moved on. A change to only its Dockerfile is not noticed (owner, 2026-10-24). There is no Rebuild, since the checkout lives in the container.

Containers made before this were reached over ssh, and only Nightly and Dev builds ever made them. They are not migrated. This build adopts one only so its delete can take it down, and its workroom says it was made by an older Nightly and must be created again.

Considered and rejected: keeping ssh by layering a static ssh server onto the user's image (a second Linux artifact, and it still needs a shell); `FROM workroom-host` (Debian only, and a Dockerfile for every user); and a bind mount on Docker (file sharing differs between Docker Desktop, Colima and OrbStack).
