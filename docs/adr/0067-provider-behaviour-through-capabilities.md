# Provider behaviour is reached through capability protocols, never by casting to a concrete driver, and only `HostDriverRegistry` makes drivers

Decided 2026-11-06 (architecture cleanup plan, step 1.3). Extends [ADR 0028](0028-host-driver-swift-byte-stream-shell-grade.md) and the pattern `DaemonPlacingDriver` and `ProvisioningHostDriver` already follow.

What one provider does that the others don't is an optional protocol in `HostDrivers`, which a driver conforms to and the app asks for with `as? any <Capability>`: `HostPresenceReporting` (boxd says a box is asleep or gone without the login that would wake it), `StartableHostDriver` (a container is started, and its postStartCommand run, on this Mac), `ReconnectingHostDriver` (SSH drops the connection its exchanges share after a wake or a network change), `OptionedProvisioningDriver` (boxd and exe.dev make a host with the resolved host options), `CheckoutClearingDriver` (a boxd snapshot can hold a used checkout), `RepositoryGranting` (exe.dev's GitHub integration per repository), `HostRecording` (the descriptor fields a driver needs to reach a host again: a container's record, an SSH host's destination and home), `FolderPlacingDriver` (an SSH host's marked workroom folders, ADR 0056) and `HostOptionsReading` (what a provider says about its host options). Two facts every driver has are protocol requirements with defaults instead: `HostDriver.execIndependently` (a login of its own, which only SSH distinguishes from `exec`) and `HostTerminalDriver.linkCrossesNetwork` (false only for a container's loopback link). The app keeps the policy: when a background read asks about presence, when an opened workroom's host is started, when a wake drops a connection. The driver says what is so. `HostKind` (ADR 0066) answers what is the same for every host of a kind; a capability answers what a driver can do. The app target has no `as? BoxdHostDriver`, `ExeDevHostDriver`, `SSHHostDriver` or `ContainerHostDriver`, and no `is` check on one either.

`HostDriverRegistry` (`Core/RemoteHosts`) is the only place the app makes a driver: each `DriverKey`'s, made on first use and kept, and the fresh ones a provider's setup sheet, a create's account check and the SSH host check use. Since step 2.7 it also records which driver holds each host config names, adopts those records and runs the launch's sweep, while `HostReachability` holds the connection policy (connect, backoff, wake, start, credential relay) and asks the registry for a host's driver. It holds a container runtime's driver as `ContainerHostDriver`, because adopting its records, sweeping its labels and building a devcontainer's image are a container runtime's alone and stay code about that kind. An SSH create gets its checked `SSHHostDriver` from the host check, typed, for the same reason. Every driver it makes keeps its hosts' files in one folder, `RemoteHosts.hosts`. Before, the boxd setup sheet's driver and a create's boxd account check were given the folder above it. That was not a bug: they only run the boxd CLI and never write a host file or a pending-machine entry. A pane whose host no driver holds (a container whose runtime isn't on this Mac, or a record naming no driver this build knows; a boxd, exe.dev or SSH host whose panes open always has its driver) is registered against `UnreachableHostDriver`, which holds no host and keeps no files. It replaces a `ContainerHostDriver` holding no host, pointed at that same parent folder. Pointed at `RemoteHosts.hosts`, the old fallback would have read a last attach an earlier launch's real driver recorded for the same restored session, and a lost link read there would have had the pane retry its notice.

Rejected: a cast to the concrete driver wherever one provider differs, as before. Changing how one provider wakes or starts meant editing the connection policy every provider shares, and adding a provider meant finding each cast. Rejected: one protocol per concrete driver that lists its whole API. That is a cast under another name. Rejected: keeping the container fallback's parent folder and calling it the one directory. It is safe only because nothing writes there, which nothing checks.
