# A remote pane attaches from the Mac: the pane runs `workroomd attach`, which reaches the host's daemon over `ssh -T` and `relay`, on every ssh host

Proposed 2026-11-13, from the Railway pane-attach design interview. It is accepted once the new path attaches, resizes, reattaches and reports a refused or lost link live on a Railway host, an exe.dev host, a boxd host and an SSH host, and once a Railway sandbox that has taken a few hundred short ssh logins still accepts new ones (see the last paragraph).

Every ssh host driver attached a pane with `ssh -t <host> … workroomd attach`: a script on the host chose the terminal type, checked the daemon was installed, and ran the attach client in the pty sshd allocated, which set raw mode there and polled that pty's size. Railway's relay breaks that. The spike of 2026-11-13 (branch `prototype/railway-sandbox-spike`, `vcs/scripts/railway-spike/FINDINGS.md`) found that every login through it becomes a Railway durable session, and one with a PTY gets `Railway durable session <name>. Use CTRL + \ then D …` written into its stream on every login and reattach, with no way to turn it off, while Ctrl+\ then `d` never reaches the host and resets the terminal. A login without a PTY has neither, and its bytes arrive untouched.

So a pane's child is the Mac's own `workroomd attach`, the client a local pane already runs, and the client starts `ssh -T <host> <binary> relay --socket <path>` itself and speaks the daemon's framed protocol over it (ADR 0028's byte stream, as the service stream already does). It sets raw mode on libghostty's pty and sends the pane's size as the protocol's `Resize` frame. ADR 0070's probe passes through it to libghostty, which answers as before. This holds for every ssh driver, not only Railway's: one attach path, no pty or attach process on the host per pane, and `ssh -t … attach` goes away for panes. The container driver keeps its own exec transport (ADR 0060), and a local pane is unchanged.

What the host-side script did moves:

- **Environment.** A client on the Mac sends only `TERM`, `COLORTERM`, `TERM_PROGRAM`, `TERM_PROGRAM_VERSION`, `LANG`, `LC_*` and the `WORKROOM_SESSION_*` metadata (ADR 0047's workroom and title among them), never `PATH`, `HOME`, `SHELL`, `USER` or the rest of the Mac's environment. The daemon takes the rest from its own environment and the host user's account entry (`getpwuid`: the shell and `HOME`), and starts the shell as a login shell, so its profile sets `PATH` as an ssh login's did. A local pane still sends its whole environment.
- **Terminal type.** The Mac always asks for `xterm-ghostty`. The daemon, creating the session, uses it with `TERMINFO` and Ghostty's shell integration when the bootstrap's terminfo is at its resources, and `xterm-256color` without the integration when it is not (a tmpfs `/run` loses it on reboot), as the script decided.
- **ssh variables.** `relay` has sshd's `SSH_CONNECTION` and `SSH_CLIENT`, and passes them to the daemon when it connects; the daemon sets them on the sessions it creates for that connection, so a prompt that shows the hostname over ssh still does. `SSH_TTY` stays unset: there is no ssh terminal.
- **Failures.** ssh still logs to the pane's attach log (`-E`), and the attach wrapper of #241 and #392 still wraps the pane and records its status, so refusal detection and the retry notice are unchanged. The client exits 255, a lost link to keep retrying, for ssh's own 255, a host with no daemon binary yet, and `relay`'s `DAEMON_UNAVAILABLE`; it exits with a stop and a message for a host with only the former `wr-agent` layout; and otherwise with the session's own end. It clears the "waiting for this terminal's host" line itself once its handshake succeeds, since ssh's `LocalCommand`, which cleared it, would write into the framed stream.
- **Versions.** The attach client and the host's daemon are no longer one install, so the attach handshake follows ADR 0037 like the service stream: the app pushes the newest daemon before its panes attach, a client that meets an older one exits 255 and retries, and a newer one, from Nightly, still accepts the Release app's client.

Each pane keeps its own ssh connection, as before. Railway's own session resume is never used: no attach sets `RAILWAY_DURABLE_SESSION_NAME`, and a reconnect is an ordinary login and an ordinary daemon reattach, which restores the screen from the daemon's own history (ADRs 0031, 0051, 0062). Ending a login a Mac abandoned is the daemon's job ([ADR 0075](0075-the-daemon-closes-stale-remote-connections.md)).

Rejected: keeping `ssh -t` and stripping the banner. It is undocumented bytes Railway can change, and the intercepted Ctrl+\ `d` and the terminal reset would stay. Rejected: `-T` for Railway alone, with `ssh -t` kept for exe.dev, boxd and SSH hosts. Railway needs all the work above anyway, and two attach paths would drift apart. Rejected: resuming the relay's session by name (`RAILWAY_DURABLE_RESUME=lastread`). Picking a framed stream up mid-frame leaves a client it can't resync, and the daemon's reattach already does the job. Rejected: all of a host's panes multiplexed over the app's one service connection. It would open panes faster and make one Railway login per host, but one busy pane would slow typing in the others and one dropped link would take them all down.

Accepted risk, to be measured before acceptance: Railway lists every login as a session until the sandbox is destroyed, and nothing deletes one, so a host that lives for months collects thousands, one for each pane connect, service stream and one-off ssh command. Whether Railway caps that list, or refuses logins once it is long, is not documented. The acceptance spike makes a few hundred short logins on one sandbox and checks that logins still work and whether old entries go; a cap that refuses logins sends this back to design.
