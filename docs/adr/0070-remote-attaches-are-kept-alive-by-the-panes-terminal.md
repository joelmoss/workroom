# A remote attach is kept alive by the pane's own terminal answering, and a client that stops answering stops counting as attached without being cut off

**Amended by [ADR 0075](0075-the-daemon-closes-stale-remote-connections.md) (proposed 2026-11-13):** a client that misses three probes is closed, not only marked stale, and a remote service stream that sends nothing for 60 s is closed too.

Decided 2026-11-08 for #593. A session counts as attached while any client is attached to it, and the detached-sessions list hides one that is (#584), so Stop can't end a session someone is using. On a remote host a client is a `workroomd attach` under sshd, and when the Mac holding the pane sleeps or loses its network that relay does not end: it waits on an ssh channel sshd still thinks is open, about 2 h on stock Linux, or for good with TCPKeepAlive off. Nothing on the host can tell it from a quiet client. A heartbeat between the daemon and the relay would be answered by the relay, which is alive; the hop that died is the Mac's. The app can't send one through the pane either: every way libghostty writes to a pane's pty for the app (`text:`, `csi:`, `esc:` bindings) scrolls the viewport to the bottom, which would yank a user reading scrollback every interval. So the daemon sends the probe and the pane's terminal answers it: every 15 s, at ground and between two deliveries of output, the daemon writes `CSI ? 25930 $ p` (DECRQM for a mode no terminal has) to each client that asked, libghostty answers `CSI ? 25930 ; 0 $ y` from its IO thread whether or not anyone types, and the daemon takes the answer out of that client's input before the pty. Any input counts as an answer. A client that leaves three probes in a row unanswered (45 to 60 s) no longer counts as attached and gives up the size, as a detach does. It is not evicted: output still goes to it, so a Mac that wakes on a link that survived carries on with nothing missed and counts again at its first answer, where cutting it off would have made every remote pane reattach and lose its local scrollback after any sleep longer than a minute. A client left on its own is handed the size only if it still answers, so a sleeping Mac's window never sets the next attach's geometry. Accepted, and inherent to any probe: the first probe a sleeping Mac misses is data the host's TCP can't get acknowledged, so sshd's connection ends after Linux's retransmission timeout (`tcp_retries2`, about 15 min), whether or not later probes are sent. A sleep shorter than that wakes on the same link; a longer one makes an idle remote pane reattach on wake (the lost-link path, with its scrollback trimmed to the daemon's tail), as a pane whose program printed during the sleep already did. Before this an idle pane's link lasted until TCPKeepAlive gave up, about 2 h. Stopping the probes once a client is stale was weighed and rejected: the probes already in flight end the link at the same time, and a woken idle pane would then stay listed as detached until its first keystroke. Misses are counted in ticks, not time, so a container VM paused with the Mac misses at most one. A client asks with `WORKROOM_SESSION_KEEPALIVE=1` in its attach environment, which every relay forwards whole; the app sets it on every remote pane's attach and never on a local one, whose attach ends with the app. No protocol version moves: an older app never asks, so a newer daemon never probes it, and an older daemon ignores the variable (it drops `WORKROOM_SESSION_*` from the shell's environment), so the app sends it without checking the host's version. Accepted: an answer split across two input frames is still taken out only once its held part is at least `ESC [ ?`, so a split in its first two bytes, which needs a large paste in the same instant, reaches the program; a client whose program leaves the stream mid-sequence is not probed until it ends one, and is never counted stale meanwhile; a program's own mode report split just after `ESC [ ? 2` waits for the client's next input, at worst the next probe's answer, one interval; the line logged when a client goes stale is written under its session's attachment lock, which the daemon's log keeps drained.
