# What is the same in every window has one app-scoped owner, and a window keeps only what is its own

Decided 2026-11-05 (owner, architecture cleanup plan, decision D1). Recorded with step 2.4; steps 2.3 to 2.5 build it.

`AppStore` is one window's state: its selection, terminals, splits, history and modals. What every window shows the same way, and the work that keeps it current, belongs to one `@MainActor` owner for the whole app, which each window's store is handed when it is made (`.shared` in production; a test's `AppStore()` gets a fresh one). Views take an owner from the environment like any other environment object. An owner holds no `AppStore`. Where it needs a window to do something (bring a run's window forward, settle what the window caches from a status), the window registers itself (for `RunCommands`, its run controller) with it, through a protocol that names only what that owner needs of a window (`VCSStatusWindow`, `LifecycleWindow`). The owner holds each window weakly, in the order they registered (`WeakList`), and calls them synchronously on the main actor, so no window can miss a call. Owners derive downward only: a `WorkroomLifecycle` is made over a `VCSStatusService`, which is made over a `ProjectStore`, and none reaches back up.

The owners:

- `ProjectStore`: the project list and the saved session (issue #70).
- `RunCommands` (step 2.3): each project's run config, which window runs a workroom's command, and the quit and delete checks that span every window. Which tab is a workroom's run stays with the window whose tab it is, because two windows can show one workroom with tabs of their own (#444 Q12); what is known of the run is its tab's (ADR 0069).
- `VCSStatusService` (step 2.4): every workroom's VCS and CI status, the sweep that refreshes it, `gh`'s availability, and the commits and writes in flight against each project. Only one sweep runs in the app: a sweep started from any window replaces the one in flight, as one started in the same window always did. The probes that follow a window's selection (the debounced selection refresh, the selected workroom's file watch) stay with the window; the probe that names one row (after a create or a commit) is the service's. It also holds the set of workrooms being created, which every probe stands clear of. Every merged result settles every window's caches, not just the window whose lane produced it.
- `WorkroomLifecycle` (step 2.5): every create's run and the pane it holds, the creates and deletes in flight (the tombstones a reload filters by), the providers' setup waits, and what a create or delete does to every window. Each window registers with it, and it hands every window each effect as a `WorkroomLifecycle.Event` (a target removed, a pane replaced, a project's `.git` changed), a plain synchronous main-actor call in ADR 0021's style, so no window's store loops over its siblings any more. A delete stops its runs and reaps its terminals in every window through each window's `LifecycleWindow` (its run controller and its reap), and holds every window's store until the workroom's teardown has started (or the project's has finished), so a window closed mid-stop still finishes its stop and the teardown still runs. The create and delete flows are the lifecycle's too (`WorkroomLifecycle+Create`, `WorkroomLifecycle+Delete`). Each takes the window it was asked from as a `LifecycleWindow`, a protocol the window's `AppStore` conforms to that carries only what the flows need of that one window: its CLI and services, its modals, its selection, its reload, where a create's pane opens and closes, its auto-run, and its share of a delete's local removal. What every window shares, the flows read on the lifecycle and the owners below it, among them what a target id resolves to (`target(for:)`, `ProjectStore.sidebarID(for:)`). It also owns one `.git` watch per project for the whole app, where each window used to keep its own, the root branch labels' resolution after a load (one in flight in the app, a newer load's replacing it), and the once-a-launch flags that were statics on `AppStore`: the orphaned-session sweep, the Dev build's config claim, and the create announcements. The quit's "stop runs" flag went to `RunCommands`. The lifecycle's `creatingWorkrooms` reads and writes the set `VCSStatusService` holds.

The remote hosts are app-wide too but are not one of these owners. `RemoteHosts.shared` (step 2.7: its `registry`, a `HostDriverRegistry`, and its `reachability`, a `HostReachability`) is a lock-guarded `Sendable` class, not a `@MainActor` model, because connecting to a host runs off the main actor, from panes, the status sweep and the repository router. A window's store is not handed one of its own. Panes and their session service reach `RemoteHosts.shared` directly, so a window with a different instance would adopt hosts its panes could not find. It is injected where a test needs it, through the `reachability:` parameter of the remote delete and script run.

Rejected: keeping that state per window and fanning changes out over a notification bus. Every rule about what spans windows would live in each subscriber, which is the split ownership this replaces. Rejected: adding these to `ProjectStore`. It would grow back into the object `AppStore` was, with four contexts in one type. Rejected: registering the Quick Terminal's store with the owners' window lists. ADR 0064's reasons still hold. The Quick Terminal builds no store (update, 2026-11-07, row 4.9 of the architecture cleanup): a `QuickTerminalHost` hosts its panes, holds none of these owners and registers with none of them. Its one target is no project, so it needs none; its notifications' labels read `ProjectStore.shared`.
