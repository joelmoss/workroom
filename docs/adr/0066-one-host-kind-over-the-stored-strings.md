# One `HostKind` names a host's kind; config.json keeps the strings, and code reads them through typed views

Decided 2026-11-05 (architecture cleanup plan, step 1.2). Applies ADR 0014's untyped store with typed views to the Swift side.

`HostKind` in `WorkroomDomain` is the one list of host kinds: a container on this Mac (`ContainerRuntime`: Docker or Apple's runtime), boxd, exe.dev, or an SSH host. It replaces four enums that each listed the providers and were mapped onto each other by hand: the app's `RemoteWorkrooms.Place`, `CreationKind` (`Place` plus "this Mac", now `CreationRun.kind: HostKind?` with nil for this Mac), `HostProvider` (the two kinds that take host options), and the kind half of `RemoteHosts.DriverKey`. Docker and Apple's runtime were listed twice as well, as `RemoteWorkrooms.Runtime` and `ContainerHostDriver.Dialect`. Now `ContainerRuntime` is the only list. What is the same for every host of a kind belongs to the kind: its name, icon, phrase, the hint a failed clone adds, its dashboard link, the descriptor's `driver` string, the `WORKROOM_HOST` word its scripts get, and whether it takes host options, with the key Settings saves them under. The drivers' `driverName` constants read the kind's. A fifth kind is one new case. The compiler then lists every switch that needs to handle it.

A kind is not a driver. `RemoteHosts.DriverKey` stays as the driver's identity, the thing a driver acts for: a Docker context, a boxd org and account, an exe.dev account, or an SSH destination. Its `kind` is the only mapping left between the two. `DriverKey(descriptor)` also checks the record, and an SSH destination that doesn't check out gives nil. So where the code asks whether this build can reach or own a host, it keeps asking `DriverKey`, not `kind`.

Nothing on disk changes. `HostDescriptor` keeps `driver` and `state` as strings, and its lenient decode, because config.json and the CLI carry them (the CLI reads `state == "destroyed"`, ADR 0040). The settings keys stay `boxd` and `exeDev`, the old `HostProvider` raw values. They differ from exe.dev's `driver`, `exedev`, so they are a separate fact on the kind. Code reads a descriptor through two views. `kind` is nil both for a driver this build doesn't know and for a record that names none. Only the delete's `RemoteHosts.deletionKey` reads a missing `driver` as Docker's, as it did before, so an unknown host is never handled as some other kind. `lifecycle` is serving, creating, failed, destroyed, or `unknown(String)` for a state a newer build wrote. An unknown state is not serving, so its panes don't open, and it is written back unchanged. `lifecycle` can be set: setting it writes the same string `state` always held, so the app's writes need no literals either, and the stored value stays the string.

Rejected: one enum covering both the kind and the driver's identity, with an account or destination on each case. Every place that needs only the kind (menus, icons, step plans, host options) would have to supply or ignore an identity it doesn't have. Rejected: typed `driver` and `state` fields with a custom codec. A record from a newer build would lose a state or driver this one can't name, and the CLI would see a different shape.
