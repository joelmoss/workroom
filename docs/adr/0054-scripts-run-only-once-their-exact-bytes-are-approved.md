# Setup and teardown scripts run only once their exact bytes are approved

Decided 2026-10-17 (owner, #363). Builds on [ADR 0053](0053-setup-and-teardown-scripts-run-on-every-kind-of-workroom.md); [ADR 0029](0029-ssh-trust-splits-by-key-owner.md) and [ADR 0043](0043-agent-socket-trust-boundary-is-shell-grade.md) draw the other trust lines.

A repository's `scripts/workroom_setup` and `scripts/workroom_teardown` are code that arrives with a clone or a `git pull`, so Workroom runs one only once this Mac has approved its exact bytes. Each project's entry in `config.json` carries `trusted_scripts`, the hex SHA-256 of the approved bytes per script name, written under the config lock with unknown keys kept (ADR 0014). A digest that is absent, different, or of the wrong type means untrusted. An unreadable config already refuses every command, which is the fail-closed behaviour wanted, so there is no second file. Removing a project removes its approvals.

A root copy that git ignores (`git check-ignore`) is exempt: it can't arrive by a pull. The rule is on bytes, not on a path, so a workroom's copy that holds those same bytes (the include step copies ignored files in before setup) is exempt too. A tracked copy, or an untracked one git doesn't ignore, needs approval.

The check runs before anything exists. A create reads the base commit's setup script from git after the fetch (`cat-file --filters`, so it is the bytes the checkout will hold), else the root's copy, and refuses before the worktree, the config entry or a remote host is made; a delete checks the teardown script before removing anything. The refusal is `ScriptNotTrusted` (exit 3), its `--json` envelope carrying the script's name, origin, digest and text. A terminal shows the script and asks; elsewhere the app shows it with Approve, and approving sends those bytes back on stdin (`workroom trust --stdin`), so only the CLI hashes and judges. The app also offers Continue Without Script (`create --skip-setup`, confirmed first): the workroom is made without judging or running its setup script, and nothing is recorded, so the next create asks again. `workroom trust`, `trust status` (exit 0, 1, 2) and `untrust` manage approvals ahead of time; `trust status` fetches and resolves the base as a create does.

An approval covers the script's own bytes and nothing else. What it runs in turn (`bin/setup`, `npm install` reading `package.json`, a sourced library) is code from the repository that no approval covers, so a pull that changes it runs without a prompt; a script is only as reviewed as what it calls. Only a regular file of at most 1 MiB is read to judge it, so a link to a device never stalls the judge. An ignored root copy is exempt only as a regular file: an ignored symlink to a tracked file would let a pull change what runs.

The security property is the last check: whatever runs a script hashes the file it is about to execute, where it is, and refuses an unrecorded, non-exempt digest. Locally the Go service gates the file `findScript` found; on a host the app reads the checkout's copy (or the root's copy, before uploading those same bytes) and asks the CLI to judge it before `workroomd run-script`. A narrow window remains between that read and the exec on both paths; the daemon does not re-hash.

Rejected: a separate trust file (a second store to keep in step and fail closed on); trust by path, author, signature or branch (a pull changes the bytes behind a path); asking only after the worktree exists, with a command that runs setup alone (a refusal would leave a half-made workroom, and a paid host); a global "trust every project" switch or approving on first create (either defeats the point); a `--sha256` check inside `workroomd run-script` (the local path has the same read-then-exec window, and it would mean a daemon protocol change for parity only).
