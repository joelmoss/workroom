# `AppEnvironment` has two independent axes: services and isolation

Status: accepted, built (step 1.1 of [the architecture cleanup plan](../designs/architecture-cleanup-2026-11.md)). The test-fixture branches in production code are replaced by an `AppEnvironment` with `services` (live or fixture) and `isolation` (none or testProcess). Isolation is derived from the three signals the test-process check reads today, and it is selected before `UserDefaults.app` and the shell and ghostty probes are evaluated. A UI-test launch that runs the real bootstrap without fixture data maps to live services with test-process isolation: folding it into either existing mode would overwrite the developer's own preferences or stop testing the real bootstrap.

The services axis is a value, `AppServices` (`Core/AppShell/AppServices.swift`): the CLI, the repository reader and writer, the VCS toolbar model, canned diffs, seeded statuses, the remote-create services, the Trash, the banner notifier, and the host-layout and host-session reads. `WorkroomApp.init` chooses it once, `.live` or the fixture's `.fixture`; each window's `AppStore` holds it and hands views the parts they need, so code asks its service rather than branching on the environment. The fixture file is wrapped in `#if DEBUG`, and so is `AppEnvironment.isFixture`: a Release build compiles no fixture code and cannot branch on fixture mode, so a stray `defaults write` cannot latch a shipped build into it. Fixture behaviour no service carries (the fake project list, the window frame, accessibility handles for XCUITest, quitting without a prompt) stays behind `#if DEBUG` at its site.

Source: the maintainer's architecture cleanup plan (a private planning document, not in this repository), engineering review decision D10 (2026-10-10); the signals are in `macapp/WorkroomApp/Core/Testing/UITestFixture.swift` and `DefaultsSuite.swift`.
