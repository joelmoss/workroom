# Program status (OSC 7501) is kept by workroomd and published on its own service, not passed through the terminal relay

**Superseded in part by ADR 0052 (2026-10-16):** a program that never probes may alert once the daemon has seen it stay running, and a program's own notification is folded into its request whichever comes first, not only within 10 s.

Decided 2026-10-14 (#358). A program's OSC 7501 reports are parsed by each session's shadow terminal in `workroomd`, which keeps the records, answers the support probe, and publishes each session's records on `Service::ProgramStatus` (`0x07`, protocol 8) over the daemon connection the app already holds for each host. The app shows them beside the pane's busy indicator and, for a request that waits on the user, alerts and counts it in the Dock badge.

The daemon owns the state because the pane does not see the bytes in a form it can use. GhosttyKit's apprt ignores `.program_status`, so the app's own terminal drops 7501. A daemon-backed pane's process is the `workroomd attach` relay, which writes `Output` frames to the pane and ignores every other frame kind, so a new `0x1*` frame reaches the relay and stops there (`attach.rs`); Swift never reads attach frames. Synthesising some other escape into the pty stream is ruled out too: GhosttyKit drops 7501 itself, and an escape injected at an arbitrary chunk boundary can split one of the program's own sequences. The service also gives reattach, relaunch, a second Mac and a daemon hand-off one answer: the subscribe snapshot.

Alternatives rejected: Claude Code hooks (Claude-only, edits the user's `settings.json`, no lifetime rules, and nothing for reattach or remote; the deciding reason is that reattach and remote correctness come from the daemon owning the state, not emitter breadth); a method on an existing service (still needs a version gate, and mixes status into File or Layout semantics); patching GhosttyKit's apprt (a fork to maintain, and daemon-backed panes would still need the daemon for reattach and remote). If GhosttyKit later surfaces `.program_status`, non-daemon panes feed the same app-side monitor, and the daemon stays the source for daemon-backed panes.

The rules the daemon applies are the header's (`terminal.h`, `GhosttyTerminalProgramStatusFn`): one record per id, full replace, subtree `clear`, `app` inherited from the nearest ancestor, `working`/`blocked`/`idle` dropped at prompt start and `working`/`blocked` at program exit, `done`/`error` kept until the user has seen them. Workroom adds three. A record's owner is the pty's foreground process group when it was reported, and its `working`/`blocked` records go when that group no longer exists, so a program killed mid-question on a host without shell integration does not leave a request forever; a foreground change alone (`^Z`, `sudo`, an editor) keeps them. Only the probe reply is written to the pty: the client already answers DA1, DSR and colour queries, and a second answer lands in the program's input as garbage. And only a program run that answered the probe may notify (`notify` on the wire), so `printf` of a report shows a mark but never alerts.

Each session has one episode counter, so a request that resolves and a new one with the same id never share a number, and a `boot` id that names the session store and survives hand-off, so a daemon replaced on app update does not re-alert what it already alerted. A request alerts once per (session, record, episode). Claude Code's own OSC 777 notification arrives 6.0 s after its `blocked` report (measured), so an `.osc` from the same session within 10 s of a single waiting request's start is merged into it.

Residual risks, accepted and not fixed:

- Spoofing. Any program in a pane can claim any kind, app or message. The UI never presents `app` as an identity, and every tooltip and alert names the terminal as the source.
- A file containing both a probe and a `blocked` report (`cat hostile.txt`) satisfies the probe gate, so it can post one alert until that program run ends.
- A probe reply written while the pty's input queue is full is cut short and the rest dropped (logged), leaving a partial reply in the program's input. The queue is only full when the program is not reading its input.
- The reply is written outside the client-input path, so in theory it can land between two writes of a large paste. That needs a probe during a paste; programs probe at start.
- On a remote host without Ghostty's shell integration (no OSC 133), a request clears only on the next report, on exit or on owner death. Clear status is the escape.
