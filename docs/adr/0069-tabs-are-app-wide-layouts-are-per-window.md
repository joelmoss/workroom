# Terminal tabs are app-wide by id, and each window keeps only its layout of them

Decided 2026-11-05 (owner, architecture cleanup plan, decision D2 as revised by eng review D4). Built in step 3.9.

Two windows can show one workroom, each with tabs, splits and focus of its own, and moving a workroom into a window that already shows it appends the moved tabs after that window's own and keeps its layout (#444 Q12). So a tab is not a workroom's, and not a window's for good: it is the app's, and a window shows some of them.

Every terminal tab lives once, app-wide, in `TerminalTabs.shared`: its record (`TerminalTab`: content, session id, launch, live title, cwd, agent and program status) and, for a terminal, its surface. Each window's pane store (`TerminalPanes`, which was `TerminalSessions`) keeps, per target it shows, only a layout over tab ids (`TargetPanes` over a `PaneState`: order, split groups, focus and "Terminal N" counter). A window reads a tab only through its own layout, so it never sees another window's tabs. A move between windows, and the Q12 merge, hand over a layout (`TargetHandOff`): the window it leaves lets the ids go, the window it joins takes them, and the tabs stay where they are. No per-tab field travels, so none can be dropped on the way. A surface stays wired to the window that holds its tab: adopting re-points its events at the new window, as before.

A tab is held by one window at a time (`TabRecords`, in `Packages/TerminalModel`). Storing or claiming a tab another window holds is refused, and between a hand-off and its adopt the tabs are held by none. An adopt that finds a tab still held elsewhere stops, with an assertion in Debug.

Observation stays per target and per tab. The record dictionary is not observed; each record is its own observable, so a view reading one tab re-renders when that tab changes, and never when a tab in another workroom or another window does (the WORKROOM-2B class, ADR 0018). A layout's order changes whenever a tab joins or leaves it, which is what a view listing its tabs re-renders on. `TargetPanes.hasTabs` changes only when a target gains its first tab or loses its last, so the reads that span windows (⌥Tab's enablement, which RootView computes over every window) re-render on that and nothing else.

What stays per window, because it is the window's and not the tab's: the detached pane windows and their frames (the hand-off carries the frames, and the window it joins opens its own), the activity pulses, the in-flight reads of the pane collaborators (`PaneLiveState`, `ProgramStatusBinding`, `RemotePaneLinks`, which a hand-off cancels, as before), and the coding-agent manager, which each window's views observe as one environment object. Its banners and last failures go with a hand-off, since one manager for every window would re-render every window on each banner.

Every window, and the Quick Terminal, shares `TerminalTabs.shared`, tests included. The Quick Terminal keeps its own store, session service and owners (ADR 0064, ADR 0068); only its tabs' records are shared, because its pane moves into a workroom window by the same hand-off, and one registry is what makes that move a shift of ids. Unlike ADR 0068's owners, a test's store does not get a fresh registry: any two stores a test hands a tab between must share one, and since a window reads only the tabs it holds, sharing isolates them as well as separate registries would. A window that goes takes the tabs it holds with it (its pane store's `deinit`), so a closed window still frees its surfaces as it did when it owned them.

Rejected: one pane store per target, app-wide. Two windows on one workroom have different tabs (Q12), which one store keyed by target cannot hold. Rejected: keeping the tabs per window and copying them across on a move. That is what the hand-off did, and each new per-tab field had to be remembered there. Rejected: one window per workroom. It removes a shipped, tested behaviour.
