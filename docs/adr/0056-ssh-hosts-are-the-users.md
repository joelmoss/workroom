# An SSH host is the user's server: several workrooms per host, one daemon, no system changes, and a delete removes only the workroom's folder

Decided 2026-10-22 (owner, triage of #378); amended 2026-10-25 (owner, eng review of #378, decisions D1 to D7). Status: accepted. Narrows [ADR 0017](0017-remote-workrooms-fresh-host-no-wakefulness.md), [ADR 0027](0027-agent-lifetime-local-idle-remote-supervised.md) (no supervisor) and [ADR 0040](0040-deleting-a-remote-workroom-is-app-only.md) for SSH hosts; all three stand for every other driver.

An SSH host is a Linux server the user already has. Workroom never creates or destroys one. A create names the host as the user would after `ssh` (an alias from their config or `[user@]host`; ports and jump hosts come from their config), plus a parent folder that defaults to the one last used on that host (`~/workrooms` the first time), and makes `<folder>/<workroom name>` there. It refuses a folder that already exists, because the CLI keeps names unique per project only. One host holds any number of workrooms, served by one workroomd per login user. Release and Nightly share it, as they share provider hosts (ADR 0036), and a Dev build keeps its own state folder so a work-in-progress daemon never replaces the one real workrooms use. Destroying a host is a provisioning interface of its own, which the boxd, exe.dev and container drivers have and the SSH driver doesn't, so nothing can call destroy on an SSH host (D1). Right after a create makes the workroom's folder, it writes a marker in the daemon's state folder, `workrooms/<workroom id>`, holding the folder's path (D4). A delete runs the teardown script (ADR 0053), ends that workroom's sessions and removes only its folder, and only when the marker names exactly the path config records; a missing or different marker keeps the folder, and Delete Anyway names it. It never removes the folder the user typed. The host's shared state (status watch, connection) goes only with its last workroom. The daemon is never stopped, not even after the last workroom (D2): it keeps running with no sessions until the server reboots or the user ends it. When the host can't be reached, the delete fails and keeps the workroom, and Delete Anyway drops it and names the folder left behind. Nothing is installed with root: no sudo, no systemd unit. The app starts the daemon in the background on connect (`--idle-timeout never`, screens on disk, the systemd unit's fixed environment), and starts it again after a reboot. The app's git on a remote host runs with the daemon's environment, which on every remote kind (boxd, exe.dev, containers and SSH hosts) the daemon builds from the host user's login-shell environment, read once the way `run-script` reads it, with its own as the fallback (D5, D6). ssh follows ADR 0029 for a user-owned key. A host with no `known_hosts` entry gets an in-app Trust prompt showing its fingerprint; a changed key is never trusted automatically; ssh that needs a password or passphrase prompt stops the create before anything is made. git uses the host's own credentials, never the Mac's `gh`, and the origin must still be on github.com (ADR 0041). The clone keeps the origin's own GitHub URL form, `ssh://` included, since the host's credentials decide which scheme works (D7). Each workroom gets its own port-forward list, as a container workroom has, loopback on the host only (D3). No pending-host entry is ever written for an SSH host, so the launch sweep (ADR 0038) can never call destroy on the user's server.

The app checks reachability, the key, authentication, Linux/architecture, git and the remote home
before reserve, and resolves the parent on the host. `workroom create --host <descriptor>
--host-parent <absolute folder>` chooses the name and records `<folder>/<name>` in one operation;
`--host-parent` and the existing `--host-path` are exclusive. The host id is UUIDv5 from the exact
destination, and the descriptor records that destination and remote home. Creating the leaf is an
atomic `mkdir`, without `-p`; a failed create removes only a leaf it made and its marker. A delete
checks the folder and marker before teardown, skips teardown when the folder is already gone,
ends sessions by the workroom's UUID tag, and bounds folder removal to 600 seconds. Starting the
daemon applies whenever nothing listens, including a stale socket after a kill or reboot. The
10-second login-shell probe for remote git falls back to the daemon's own environment and logs
why; existing scrub and pins are applied on top. See [remote host states](../remote-host-states.md)
for the failure handling and parity table.

Rejected: one host per workroom (people have one server); the typed path as the workroom's folder itself (a slip like `~` would be deleted); a hosts list in Settings; refusing an unknown host key and sending the user to Terminal; `systemctl --user` with lingering or root units (Workroom shouldn't install services on a server it doesn't own, and a supervisor's only extra, restarting the daemon while the app is away, saves no sessions); relaying the Mac's `gh` (it dies when the laptop disconnects); one daemon per workroom (isolation from a crash nobody has seen, for many more processes); stopping the daemon after the last workroom when it reports no sessions (the daemon has no stop request, and a list-then-kill races another Mac opening a terminal); one port-forward list per host (a second workroom's `devcontainer.json` ports would never be forwarded, and every list would show the others' forwards); removing the recorded path with no marker (a wrong path in config would delete real data on the user's server); the daemon's fixed environment for the app's git (a git, `gh` or token set up in the user's profile works in the terminal and fails in the app's fetch and push).
