## Problem Statement

#255 asks for a remote workroom opened on a second Mac to land in the same sessions, in the same
tab layout, with a full-screen program repainted, and for closing the app on one Mac to leave the
other's attachment alone. Its first acceptance criterion is answering open question 8 in
`docs/designs/remote-workrooms.md`: how much workroom UI state moves to the agent, and what stays
per Mac.

Today all of it lives on the Mac that made it. `SessionSnapshot.swift` defines `session.json`
(`Application Support/Workroom/<bundle id>/`), whose `WindowSession` holds window frames,
`isKey`, `selectedTargetID`, `workroomSplits` and `expandedTargets`, and whose `TargetSession`
holds a workroom's tabs (terminal, diff, file, changeset payloads), split groups, `focusedKey` and
`terminalCounter`. A second Mac knows none of it, and the agent's session list gives it nothing
to rebuild from.

## What Makes This Cool

Shut the laptop, open the same workroom on the desktop, and every terminal, split and open diff is
where it was, with the running program repainted. The shells never moved; only the view of them
did.

## Constraints

- `session.json` stays bundle-id scoped (Workroom, Dev and Nightly must never restore each
  other's workrooms). Anything that replaces part of it keeps that separation.
- `SessionSnapshot.swift`'s codec rules hold: additive changes never bump `schemaVersion`, lossy
  arrays drop one element rather than the document, and sanitize caps bound what a file can make
  the app allocate.
- The agent protocol is shared by app builds of different ages; the app already pushes a new
  agent on a version mismatch (#231), and an older agent must degrade to today's behaviour.
- The size-owner policy already exists (`session.rs` `Attached`: ownership is claimed by typing or
  clicking, never by attaching), so two Macs on one session is not an open problem.

## Premises

Agreed by the owner, with premise 3 revised after the Codex cold read.

1. **What moves is the workroom's pane layout:** today's `TargetSession` (tab strip order,
   `splits`, `terminalCounter`, and every tab payload), minus the per-viewer fields `focusedKey`
   and `detachedFrame`, which the **app** strips before writing and fills back in from its own
   `session.json` by tab key after reading (the agent never parses the blob, so it cannot strip
   anything). All of `WindowSession` stays per Mac. The existing codec, `@Lossy`, `sanitized()`
   and caps are reused unchanged.
   **Portability audit:** tab keys are tab UUIDs (`AppStore+Session.swift`, `let key =
   tab.id.uuidString`), never `target.id`; split leaves and `focusedKey` point at those keys;
   diff and file paths are repo-relative (`DiffDescriptor.path`, `FileDescriptor.path`); a
   changeset names a commit ID; a terminal's `cwd` is already a path on the host. Nothing in a
   remote workroom's `TargetSession` is local to one Mac apart from the two stripped fields.
2. **Keyed by a portable ID.** A remote workroom's layout is keyed by `HostDescriptor.workroomID`,
   never `target.id`: `wr|<project>|<name>` embeds this Mac's project path.
3. **Three-state reconciliation (revised).** Every terminal tab in the layout is kept, and each
   attaches with `existing_only`; the agent's answer decides what the pane shows:
   - **live:** reattach;
   - **recorded:** the frozen screen kept by #232 (`serve.rs`, the `existing_only && !exists`
     branch of the attach handler; tested by
     `a_restored_pane_is_shown_the_record_of_a_session_that_ended_with_its_host`);
   - **missing:** the pane stays in the layout as an ended pane until the user closes it, exactly
     as a restored pane whose session is gone behaves today. Restore never removes a pane from
     the layout.

   Sessions tagged with this workroom that the layout does not mention, live or recorded, are
   appended as new tabs, and that append is an ordinary layout change, written through like any
   other. Pruning the layout against the live list, as first proposed, would have
   dropped every pane a host reboot left as a recorded screen.
4. **The agent's session list loses metadata today, which looks like a local bug as well.** Read
   in code, not yet proven by a test or a live probe: `encode_descriptor_list` (`serve.rs`) writes
   only `command`, and neither `SessionInfo` nor `FrozenSession` has a metadata field. If that
   holds, then for every agent-backed session `PersistentSessionService.orphanedSessionIDs`,
   `endSessions(matchingWorkroom:)`, the workroom filter in `TerminalSessionsStore` and the
   Detached Terminals titles never match. Next Steps 1 proves it with a failing test before
   anything else relies on it.
5. **The orphan sweep stays local only.** `liveControlPlanes()` reaches only local sockets today,
   and it must stay that way: once metadata exists, a sweep run against a remote host would kill
   every session the sweeping Mac has not imported, which on a shared host means the other Mac's.
   Lifecycle on a remote host belongs to the delete flow and #257.
6. **Sync on open, write through on change.** No live mirroring between two open Macs in #255.
7. **Close ends a session everywhere** (#283's rule, tmux `kill-pane`); quitting only detaches.
   Restored panes send `existing_only`, so a Mac never recreates a shell another Mac closed.
8. **Local parity is the direction** (design doc lines 225-230), but **not in #255**. #255's
   layout storage is for remote workrooms only, keyed by `workroomID`; a local workroom keeps
   today's `session.json` restore. Moving local layouts to the local agent is a follow-up, which
   then chooses a portable local key. The metadata fix (premise 4) does ship for local sessions,
   since it is the same code path.
9. **The layout survives hand-off and reboot.** A file on disk survives the `execve` hand-off with
   no change to `FrozenSession`. On boxd, `boxd.sh` already keeps the agent's state, `--screens`
   included, on the home disk, which outlives a stop and start; the ssh fixture does the same
   (`entrypoint.sh`, `/home/workroom/.local/state/workroom/screens`).
10. **Outside OQ8, but blocking #255's acceptance test:** Mac B must discover the workroom (the
    registry is Mac A's CLI config) and hold an ssh key the host accepts
    (`RemoteWorkrooms.swift` mints its `id_ed25519` once per Mac per build). Container workrooms on Mac A's
    Docker cannot be reached from Mac B at all, so the live test runs on boxd. This needs its own
    issue; the Codaset broker, which already keys grants by `workroomID` per user, is the likely
    registry.

## Cross-Model Perspective

Codex (gpt-6.1-sol, cold read of the repo):

- **Coolest version:** named workspace views. Each viewer can save a personal arrangement over the
  same processes, publishing one makes it the default, and layout history recovers yesterday's
  arrangement without restarting today's shells.
- **Challenged premise 3**, correctly: non-live does not mean disposable, because an
  `existing_only` attach repaints a recorded screen when no session exists. Reconcile live,
  recorded and missing. Adopted, with one change: Codex suggested collapsing missing panes, but
  this design keeps them as ended panes until the user closes them, as restore does today.
- **Also found:** neither `SessionInfo` nor `FrozenSession` carries metadata, and Swift tags
  sessions with `target.id` (`TerminalSessions.swift:2122`), so the metadata fix has to reach
  creation, storage, listing and hand-off, and must carry the portable workroom ID.
- **Prior art:** tmux control mode, as iTerm2 uses it, maps server-side panes and layouts into
  native windows that reopen after a disconnect. Useful as an executable reference, not something
  to adopt.
- **First build:** one complete two-client path on the ssh fixture: two terminal panes, a diff tab
  and Vim; Mac B restores with no copy of Mac A's `session.json`; quitting A leaves B working; a
  hand-off keeps metadata and layout; a reboot keeps recorded panes.

## Approaches Considered

- **A, metadata only:** sessions tagged with workroom ID, title and creation order; Mac B rebuilds
  one tab per session. Ruled out: it fails "same tab layout" (splits and non-terminal tabs lost).
  It survives as step 1 of the chosen approach.
- **C, live shared layout:** B plus agent-pushed layout changes to every attached client. Ruled out
  for #255: nothing in its criteria needs it, and it hardens a conflict model before anyone uses
  two Macs at once. B's protocol is shaped so C layers on without a format change.

## Recommended Approach

**B: the layout lives on the host, behind a revision, plus the metadata fix.**

### The answer to OQ8

| State | Where it lives | Why |
| --- | --- | --- |
| Terminal sessions (pty, screen, size owner) | Agent, already | Unchanged |
| Session metadata: workroom ID, title, creation order | Agent, new | Enumeration needs it; fixes the local sweep bug |
| Workroom layout: tab order, split groups and ratios, `terminalCounter`, terminal/diff/file/changeset tab payloads (incl. preview flags and view modes) | Agent, new, as an opaque blob | Any Mac rebuilds the workroom from it |
| Focus within a workroom (`focusedKey`) | Per Mac | Two viewers do not share a cursor |
| Detached pane frames (`detachedFrame`) | Per Mac | Geometry of this Mac's screens |
| Windows: frames, key window, selected workroom, sidebar expansion | Per Mac | Belongs to this Mac's desktop |
| Workroom splits (`workroomSplits`) | Per Mac | Can join workrooms on different hosts, or local ones |
| Live display state (OSC title, progress, activity) | Neither | Not persisted today; the agent's list already reports `command` and `cwd` live |

### Protocol

- `getLayout(workroomID)` returns the blob and its revision, or revision 0 and no blob.
- `putLayout(workroomID, expectedRevision, blob)` stores it and returns the new revision, or
  refuses with the current revision when `expectedRevision` is not the current one.
- **Revision:** a per-key `u64` counter, stored in the file with the blob and incremented on every
  accepted write. It survives hand-off and reboot because the file does. A key with no file is
  revision 0, so the first write sends `expectedRevision` 0.
- **Storage:** one file per key in a `layouts` directory beside the screens directory, on the home
  disk. The filename is the hex SHA-256 of the key, so a client-supplied key can never name a path.
  A blob must fit in one reply frame (the cap `list_reply` already enforces), and the directory
  holds at most 64 keys; a write past either limit is refused with a `Failure` frame, never
  truncated or evicted. Since each remote workroom is its own host, a real host holds one key;
  the cap only bounds a misbehaving client.
- **Trust boundary:** the same as attach and kill today. Any client that can reach the agent's
  socket can already end every session on the host, so reading or replacing a layout grants
  nothing new. The deferred path allowlist (`agent_remote_path_allowlist_deferred`) does not apply:
  no path comes from the client.
- **Capability detection:** the layout requests arrive with a protocol version bump; the app reads
  the agent's version at the handshake it already performs. An older agent means today's per-Mac
  behaviour for that workroom: no host layout, no second-Mac restore, nothing shown to the user
  (the remote UI is Nightly-only, and the bootstrap pushes the new agent on the next connect,
  #231).
- **Lifecycle:** a remote workroom's layout lives on that workroom's own host, so deleting the
  workroom destroys the host and its layout with it. No delete request is needed in #255.
- **Session metadata:** the workroom ID, initial title and creation order travel in the attach
  request that creates a session, and are immutable after that. The agent keeps them on the
  session, writes them into the list reply and the hand-off record, and keeps them with a screen
  record, so a recorded pane still knows its workroom. The layout blob is the authority for a
  tab's title and order; metadata is used only to place sessions the layout does not mention.
- **Sessions with no metadata** (created before the fix, or by an older agent) are never swept,
  never ended by a workroom match, and never appended; they appear only where a layout already
  names them. They drain as their shells exit. No backfill.
- **Attach encoding stays compatible both ways.** Metadata goes in as extra `META:<name>=<value>`
  entries in the attach request's `KEY=VALUE` list. An older agent ignores keys it does not know
  (`AttachRequest::decode`, the `_ =>` arm, which keeps only `ENV:` entries), so a new app on an
  old agent still attaches and simply makes a metadata-less session. An old app on a new agent
  sends no `META:` entries, with the same result.
- **Size:** the frame cap is `MAX_PAYLOAD_SIZE`, 1 MiB less the 5-byte frame header. Sanitize
  bounds a `TargetSession` to 20 tabs with strings of 4096 characters, which is well under that
  in practice, but characters are not bytes, so the bound is not a proof. The app therefore
  measures the encoded blob before `putLayout`. A blob over the cap, or a write refused for size,
  is logged and that workroom falls back to per-Mac restore (its `session.json` copy) until a
  later layout fits; the next open on another Mac then gets the last layout that did fit.

### Client behaviour

- **Each Mac remembers the revision it last read or wrote** for each remote workroom, beside the
  workroom's entry in its own `session.json`.
- **Opening a remote workroom, host has a layout:** the host's layout wins and replaces the Mac's
  copy. The Mac fills in its own `focusedKey` and `detachedFrame` by tab key.
- **Opening it, host has no layout (revision 0):** this Mac seeds it from its own `session.json`
  copy with `putLayout(expectedRevision: 0)`. Workrooms made by #253 seed themselves this way the
  first time their creating Mac opens them after the upgrade. A Mac with no copy writes its first
  layout on its first change.
- **Host unreachable:** the Mac's last copy is held and restored once the host is reachable, as
  #253 already does. On reconnect the Mac reads the revision first: if the host's is newer than
  the one the Mac remembers, the host's layout wins and the held copy is discarded (logged, not
  shown); otherwise the held copy is written with the remembered revision.
- **Restoring it:** `materialize` the blob as today; each terminal pane attaches with
  `existing_only` and shows live, recorded or ended (premise 3); sessions tagged with this
  workroom but absent from the layout, live or recorded, are appended at the end of the tab strip
  as solo panes, titled from their metadata.
- **Changing it:** written through on the same debounced digest that saves `session.json`.
- **Conflicts in #255:** a refused write re-reads the revision and writes again, so the last Mac
  to change the layout wins. What that can lose is stated plainly: another Mac's tab order, split
  placement and diff, file or changeset tabs. It cannot lose a session: the append rule brings
  back every live or recorded session tagged with the workroom, as a solo tab at the end of the
  strip. The guarantee covers sessions tagged with the workroom; a metadata-less session dropped
  from the layout by a stale write is no longer shown anywhere, which is accepted because those
  sessions only predate the fix and drain as their shells exit. Accepted until C.
- **Closing a tab** ends its session everywhere (premise 7). The other Mac's pane, still
  attached, receives the exit and shows ended, as it does today when a shell exits.
- **Closing a recorded or ended pane** goes through the same kill, and killing a recorded session
  removes its screen record (#232; `a_restored_pane_is_shown_the_record_of_a_session_that_ended_with_its_host`
  states it). So a closed recorded pane cannot come back through the append rule, and an ended
  pane has nothing left to append. A stale write that re-adds a pane another Mac closed shows it
  as ended, once, until it is closed again.

  size (a control frame on ownership change), and the pane showing a quiet "sized for another
  Mac, type to take over" marker, or letterboxing to the owner's grid. Not in #255.

## Success Criteria

- OQ8 answered in `docs/designs/remote-workrooms.md` with the table above.
- On the ssh fixture, then on boxd: start Vim and a second terminal in a split, open a diff tab on
  Mac A; open the workroom on Mac B with no copy of A's `session.json`; B shows the same tabs and
  split, Vim correctly repainted.
- Quitting the app on Mac A, while Mac B is attached and holds a keep-awake on the host, leaves
  B's panes attached and working and B's keep in force.
- Closing a tab on Mac A ends that session, and Mac B's pane for it shows ended.
- With a stale write from Mac A after Mac B changed the layout, every session tagged with the
  workroom is still present on both Macs on the next open (the append rule).
- Closing a recorded pane on one Mac means it does not reappear on either Mac's next open.
- New app against an old agent, and old app against a new agent: attach works and restore falls
  back to per-Mac behaviour.
- A layout over the size cap is logged and the workroom falls back to per-Mac restore.
- After an agent hand-off, and after a host reboot, Mac B still restores the layout, with recorded
  panes showing their last screens.
- Locally, deleting a workroom ends its agent sessions, and the launch sweep ends orphaned ones (a
  test that fails before the metadata fix).

## Post-review fixes (R3-1 to R3-7, applied after the last review round)

These amend the sections above; where they conflict, this section wins.

- **R3-1, oversized layout:** a Mac whose write was refused for size marks that workroom
  "host layout stale" in its own `session.json`, and its own copy wins on open until a write
  succeeds. Other Macs get the last layout that fitted. Next Steps 4 tests both.
- **R3-2, size cap:** one constant, `MAX_LAYOUT_BLOB`, equals `MAX_PAYLOAD_SIZE` less the
  `getLayout` reply and `putLayout` request overhead (key, revisions, header). Both the agent and
  the app use it, and the request frame is bounded by the same cap.
- **R3-3, refused writes:** a refused seed (`expectedRevision` 0) adopts the host's layout under
  the open rule and does not retry. A refused append or user change re-reads the host layout,
  re-applies the append rule or the one change to it, and writes once more. At most 3 attempts,
  then it is logged and left for the next change.
- **R3-4, local metadata:** local sessions carry `target.id` in the `workroom` metadata field,
  remote sessions carry `HostDescriptor.workroomID`. The sweep, the delete match and the filters
  compare against the form that fits the workroom's kind.
- **R3-5, atomic put:** `putLayout` checks the revision and writes under one per-store lock,
  writing a temp file then renaming it. A corrupt or truncated file reads as revision 0 with no
  blob. Tests: two concurrent puts at the same `expectedRevision` (exactly one wins) and a
  truncated file.
- **R3-6, no downgrades (a real gap, in #231's bootstrap):** `AgentBootstrap` pushes whenever the
  installed binary's hash differs from the bundled one, so an older app would replace a newer
  agent, and two Macs on different builds would keep swapping agents. Change the rule: push only
  when the host's agent build is older than the bundled one; never downgrade. An older app keeps
  the newer agent and talks to it over the versioned envelope. Add a mixed-build test: an old app
  connecting to a host that already runs the new agent leaves it in place. Read from code
  comments, not live-tested.
- **R3-7, close removes the record:** confirmed in code. Killing a recorded session reaches
  `SessionStore::end_if_absent`, which calls `screens.remove(id)` (`session.rs`). The app's
  pane-close path sends that kill for live, recorded and ended panes alike, and a "no session"
  answer counts as done. Next Steps 1 adds an agent test that pins the record removal.

### R3-1 — consistency

**Problem**

> The oversize-layout fallback contradicts the open rule. Size says an over-cap blob 'is logged and that workroom falls back to per-Mac restore (its session.json copy) until a later layout fits; the next open on another Mac then gets the last layout that did fit.' But Client behaviour says that when the host has a layout, 'the host's layout wins and replaces the Mac's copy'. After one oversize write is refused, the same Mac's next open finds the older host layout, replaces its own larger session.json copy with it, and silently discards the layout that did not fit. So per-Mac restore never actually applies, and the success criterion 'falls back to per-Mac restore' cannot hold on the next open. Nothing says how the Mac knows its copy is newer than the host's.

**Remedy**

> Choose one behaviour. Either an oversize workroom is marked 'host layout stale' on that Mac so its own copy wins on open until a write succeeds, or the host copy wins and the success criterion is reworded to say the oversize layout is lost on the next open. Add the matching test to Next Steps 4.

### R3-2 — clarity

**Problem**

> The blob cap is stated as the frame cap, MAX_PAYLOAD_SIZE (1 MiB less 5 bytes), but the getLayout reply also carries the revision (and any status or envelope) and the putLayout request carries the key and expectedRevision. The usable blob limit is therefore smaller than the stated cap. The document also does not say whether the request side has a matching cap, so the number the app measures against is ambiguous.

**Remedy**

> State the blob limit as MAX_PAYLOAD_SIZE minus the reply and request overhead, name the one constant both the agent and the app use, and say the putLayout request frame is bounded by the same cap.

### R3-3 — completeness

**Problem**

> A refused write is handled only by the Conflicts rule 'a refused write re-reads the revision and writes again'. That is wrong for the two cases that are not user changes. (a) The seed at expectedRevision 0: if two Macs open a #253 workroom at once, the loser is refused, and 're-read and write again' would overwrite the winner's seed, contradicting 'host has a layout wins' on open. (b) The append-on-open write-through. The document does not say whether the refusal path differs by case or whether the retry is bounded.

**Remedy**

> Say a refused seed adopts the host's layout (open rule) instead of retrying, and say whether a refused append write retries or re-derives from the new host layout. Bound the retry count.

### R3-4 — completeness

**Problem**

> Premise 8 says the metadata fix ships for local sessions, and Next Steps 1 says 'the app sends the portable workroom ID for a remote workroom'. The document never says what workroom ID the metadata holds for a local session. Today sessions are tagged with target.id (per the Codex bullet, TerminalSessions.swift:2122), and premise 8 defers choosing a portable local key. The last success criterion (local delete ends agent sessions, launch sweep ends orphans) depends on the sweep matching a local metadata value, but that value is undefined.

**Remedy**

> State that local sessions carry target.id in the metadata workroom field (non-portable, fine for local use) and remote sessions carry HostDescriptor.workroomID, and that the sweep and filters compare against the matching form per workroom kind.

### R3-5 — feasibility

**Problem**

> putLayout is a compare-and-swap on a file, but the document does not say how the agent makes it atomic. It names neither serialisation across concurrent client connections (two Macs each have their own connection, so two compares can interleave) nor crash-safe replacement (write to a temp file, then rename). A crash or hand-off execve mid-write could leave a truncated blob that the next getLayout serves, or let two writers both pass the revision check.

**Remedy**

> Specify that putLayout does the revision check and write under one lock (or on the single serve task), and writes via a temp file and rename. Add a test for two concurrent putLayouts at the same expectedRevision (exactly one wins) and for a corrupt or truncated file reading as revision 0 with no blob rather than failing.

### R3-6 — feasibility

**Problem**

> The Constraints say app builds of different ages share the agent protocol and that the app 'pushes a new agent on a version mismatch (#231)'. The document does not say whether mismatch means 'agent older than app' or 'any difference'. On a host shared by Mac A (older build) and Mac B (newer build), if the push is on any difference, the older app would replace the new agent with its old one, and the layout feature would vanish (silently, per Capability detection) until the next push. The mixed-version success criterion covers attach but not this ping-pong.

**Remedy**

> State the push condition (push only when the agent's protocol version is lower than the app's), cite where #231 enforces it, and add a mixed-build test: an old app connecting to a host already running the new agent must not downgrade it.

### R3-7 — feasibility

**Problem**

> The fix for closing a recorded pane rests on the claim that 'killing a recorded session removes its screen record (#232; a_restored_pane_is_shown_the_record_of_a_session_that_ended_with_its_host states it)'. That test name is the one premise 3 cites for displaying a recorded screen on existing_only attach, not for kill removing a record, so the claim is not shown to be pinned. The document also does not say that the app sends a kill for a recorded or ended pane (the pane may have no live attach, and a missing session may answer a kill with an error). I could not open the agent source with Read alone to check either point.

**Remedy**

> Verify in the agent that kill of a recorded session deletes the record, cite the exact test or line, or add a new agent test for it to Next Steps 1/2. State the app path that issues the kill for a recorded or ended pane and how it treats a 'no such session' answer.

## Implementation notes

Where the build departed from the text above, and why. The decisions below them still hold.

- **T2, metadata travels as the attach client's existing `ENV:` entries, not new `META:` entries.**
  The attach client already forwards its whole environment (`AttachRequest::from_vars`), so the
  app's `WORKROOM_SESSION_WORKROOM` and `WORKROOM_SESSION_TITLE` already reached the agent, which
  dropped them. `serve::session_metadata` now reads them; no wire change, and attach clients that
  predate #255 send them too.

- **T6, remote sessions tell their host their workroom and title**, which they did not before:

- **T7, "open" is the first time a window shows the workroom, or its restore at launch.** A Mac

- **Open question 2 (keep-awake across Macs), answered by the code.** `keep` restarts one timer for
