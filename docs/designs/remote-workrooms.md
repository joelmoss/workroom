# Design: Remote workrooms on provisioned VMs, via one unified agent

Generated by /office-hours on 2026-09-04

Repo: joelmoss/workroom

## Problem Statement

A workroom today is a local directory: a git worktree or jj workspace on this Mac, with an
embedded terminal libghostty forks locally and VCS panes that read the filesystem in-process.
The ask is a **remote workroom** — the user picks "create a cloud workroom", Workroom
provisions a VM, and a terminal session opens that behaves exactly like a local one,
persistence included.

Nothing in the repo hosts a workroom remotely today. There is no remote-exec, network-filesystem,
or cloud-provider code anywhere in the Go CLI, the Rust `vcs/` crate, or the Swift app, and
`RemoteStateModel.swift` is git-remote ahead/behind, not a network host. The app is not, however,
network-naive: it already reaches the GitHub API through the user's `gh` CLI (including
`gh api graphql`, `WorkroomStatusResolver.swift:323`, and `gh auth status --active --json hosts`
at `:458` behind `GitHubAuthCache`), and already configures ssh for git — `StatusCommandRunner.swift:172`
sets `GIT_SSH_COMMAND … -o BatchMode=yes`, and `VCSRemoteFailure` carries a `hostKeyUnverified`
case. That existing surface matters for credentials (premise 6).

## What Makes This Cool

**The work keeps running when the laptop closes, and follows you to another machine.** That is
the capability a local workroom can never have, and it is what the whole design should optimise
for. Remote compute is the lesser prize; laptop-independence is the new one. Give a workroom a
job, shut the lid, come back to finished tests, a running preview, captured logs — or open the
same workroom from a different Mac and land in the session where you left it.

The second delight is per-task hardware. One VM per workroom means the heavy build gets 64 cores
for twenty minutes and the doc fix gets a tiny box, and both are disposable.

**The terminal mechanism is already built.** `SessionReplayBuffer` and the pty daemon were written
so a terminal survives quitting the app. That is the same problem as surviving a dropped network
link, and the hard parts are already handled: replay on attach, drop the buffer under the
alternate screen and force a repaint via a transient pty row-count bump plus deferred resize-back
and SIGWINCH, strip terminal query sequences (OSC 4/10-21/52, CSI DA/DSR/DECRQM) so a reattaching
client cannot re-answer a stale query (this previously leaked the clipboard), and resynthesise
OSC 2 title and OSC 7 cwd from the foreground pgid when a full-screen program is running.

## Constraints

- **Builder mode.** A side project built because the author wants it. Coolness and architectural
  coherence outrank time-to-demo; the author chose the maximal option at every decision point.
- macOS 15+ Apple Silicon app; the far side is Linux. Anything shared must cross-compile.
- Shipped, notarized, Sparkle-updating, with launch-facing copy that must not describe planned
  capability as existing (PRODUCT.md principle 5). A half-working remote mode cannot ship stable.
- **Provider agnosticism is a design constraint, not an aspiration.** A remote workroom must behave
  the same on every provider. Provider-specific capabilities are *accelerators* beneath a portable
  contract, never the mechanism the product depends on. **The claim has one stated boundary:** a
  hard maximum instance lifetime defeats anything Workroom can do, so it is the single capability
  gate. Idle policy is *not* a gate — it is translated by a far-side per-driver shim (see below).
  **And agnosticism is scoped to the agent, not to the whole far side:** exactly one small,
  auditable, provider-specific component is sanctioned over there. See Provider Decision and Phase 3.

## Decisions Made This Session

- **Workroom provisions the VM**, not bring-your-own ssh host. BYO is a config field and a smarter
  terminal; the provisioned box is the actual point.
- **One VM per workroom**, not one per project. The worktree/workspace abstraction does not apply
  remotely either way — there is no shared `.git` across machines — so remote creation is its own
  path, not a tweak to `create`. Chosen for per-task sizing and blast-radius isolation. The original
  accepted cost was a repo clone per workroom; **deriving each workroom from a per-project base
  removes most of that** wherever a provider supports snapshots or forks, and the full clone cost
  returns only on a provider with neither. See Provider Decision.
- **Unify: one agent for local and remote**, local over a Unix socket. Rejected the fast
  "terminal-only remote, inspector greyed out" slice so remote cannot rot as a second-class path.
  See the honesty note under Recommended Approach — this is an architectural preference, not a
  measured dividend.
- **The agent is Rust, extending `vcs/`.** `wr-vcs-core` already hosts jj-lib and Rust
  cross-compiles to Linux cleanly. Accepted cost: porting the Swift pty daemon and replay buffer,
  the highest-risk work here. Rejected Swift-on-Linux and Go (a third rewrite, no in-process VCS).
- **The driver contract is four methods: `create`, `openStream`, `destroy`, `deriveFromBase`.**
  `openStream` is "give me a bidirectional stream to a process running the agent on the far side" —
  `ssh host wr-agent serve --stdio` is the first implementation, and a provider SDK's exec/attach
  call or a WebSocket satisfies it equally (subject to the SDK-language precondition in Phase 3).
  Without a stream-shaped contract, SDK-only sandbox platforms cannot be drivers at all.
- **Capabilities the provider might lack are implemented in the agent, not required from the
  driver.** Port forwarding, primary-screen scrollback durability, and deciding whether a workroom
  is busy are all Workroom's job, and all provider-agnostic.
- **One provider-specific component is sanctioned on the far side: a per-driver lifecycle shim.**
  Review found the wakefulness translator could not work from the Mac, because a sleeping Mac can
  tell a provider nothing — the exact state the feature exists for. So the agnostic agent decides
  *busy or idle*, and a thin per-driver shim beside it translates that into the provider's own
  control-plane call. Phase 3 already put a per-driver supervisor on the far side, so this uses an
  existing seam rather than opening one. The cost is a provider control-plane credential on the VM,
  which premise 6 now has to account for rather than deny.
- **The portable path ships before any accelerator.** Fast provider capabilities are optimisations
  added to a working portable implementation — never the first implementation. A "pluggable" system
  whose fast path lands first ends up permanently shaped like its first provider.
- **Per-workroom deploy keys for git auth** — keypair generated on the VM, public half registered
  against the repo, revoked when the workroom is destroyed. Rejected ssh agent forwarding
  (premise 6). Rejected a credential broker as correct-but-premature.
- **Sequencing: local-first unify, preceded by a throwaway spike.** Scoped at one day when chosen;
  the provider decision added two more measurements, so treat the day as a budget and let the
  lower-priority items come back unanswered rather than letting it sprawl.

## Provider Decision

Settled by a separate provider sweep run out-of-tree in September 2026, covering roughly 30 products
across agent-sandbox specialists, platform-attached sandboxes, LLM-vendor built-ins, persistent dev
VMs, self-host isolation runtimes, and bare-metal baselines. **That document is not in this repo and
was not preserved**, so every provider figure and capability claim below is second-hand here and
should be re-verified against vendor documentation before anything is bought or built on it — the
sweep itself flagged contradictions on vendors' own pages (conflicting cold-start numbers, session
caps that differ between docs and marketing, isolation tiers described two ways). Treat the reasoning
below as sound and the numbers as stale-by-default.

The sweep found the deciding axes to be lifetime model, isolation tier, and who owns the kernel; SDK
language, cold start and fork primitive are filters after those. That framing is what shaped this
design, and it survives independently of any individual figure.

**How this section is meant to be read.** The provider is a *first driver*, not a foundation.
Everything below either becomes a portable trait or an accelerator; nothing below is allowed to
become a mechanism the product needs. That framing is deliberate and it is the reason the section
comes after the driver contract rather than before it.

**First driver: `boxd.sh`.** KVM microVM with its own kernel, persistent disk, root, auto-HTTPS
subdomain and a per-VM SSH port, `--json` on every CLI command, single Rust binary, gRPC underneath,
€0.049/vCPU-hr. Its standout property is a **copy-on-write fork of a *running* machine — disk and
processes — in 100-200 ms**, which no other surveyed provider does live (exe.dev has only CLI `cp`;
Morph's Infinibranch is nearest at <250 ms). It also **hibernates after 4 h idle, wakes in
milliseconds, and bills disk-only while asleep**, which is what makes many idle workrooms cheap.

**Live fork is an accelerator, not the mechanism.** The portable primitive is *prepare a base, then
derive instances from it* — `deriveFromBase` — and the sweep reported that as near-universal: E2B
templates and snapshot-into-many-forks, Daytona snapshots, Vercel auto-snapshot plus `fork()`, Fly
suspend-as-snapshot, Morph branch, Freestyle fork, CodeSandbox fork, Hetzner snapshots. What is rare
is forking a *running* machine. So the contract asks every driver to derive an instance from a
prepared base, and boxd merely does it in 200 ms with processes attached while Hetzner does it from
a snapshot in a minute. Same product, different speed. (Cloudflare is the genuine exception —
point-in-time R2 backup only, no snapshot or fork — so it would pay a full clone per workroom.)

**Idle policy: the intended answer, and the hole review found in it.** "Close the lid, come back to
finished tests" needs *keep-running-while-disconnected*, and hibernate-on-idle is in tension with it:
if boxd's "idle" means no client attached rather than no CPU activity, a five-hour build dies at four
hours. The intended answer was that the agent defeats it rather than the provider guaranteeing it —
the agent asserts busy, and the driver translates that into whatever keeps its provider awake.

**Review found that could not work from the Mac, and the fix is a far-side shim.** The driver is
client-side (Phase 1 product 3, Phase 4 — provisioning necessarily precedes any far-side agent), and
a sleeping Mac emits no keepalive and holds no connection, so a client-side translator is inert in
exactly the state the feature is defined by. **Resolved by splitting the job:** the agnostic agent
decides busy/idle, and a small per-driver **lifecycle shim** on the same box makes the provider's own
control-plane call. Phase 3 already places a per-driver supervisor there, so the far side already has
a sanctioned provider-specific slot; the shim shares it.

**What the shim costs, stated plainly.** A provider control-plane credential now lives on a
disposable VM — see premise 6, which is rewritten to account for it rather than deny it. Three
consequences worth carrying: the credential's achievable **scope is a per-driver fact** (a provider
whose only token is account-wide makes the shim far more dangerous than one that can mint an
instance-scoped defer token, and that difference belongs in the driver's declared traits, not in a
footnote); the shim is the single provider-specific thing shipped to the far side, so it must stay
small enough to read in one sitting; and it must die with the instance exactly as the deploy key
does, including on the failure paths.

**With the shim, `maxLifetime` is the only capability gate.** A hard wall-clock cap is undefeatable
by anything on either side (E2B: 1 h Hobby, 24 h Pro). Idle policy is no longer a gate, because the
shim translates it per provider — which is what makes the Constraints section's agnosticism claim
true rather than aspirational.

**Creation shape, restated portably.** One **base machine per project** (deps installed, repo
cloned, agent present) and each workroom derived from it. On a live-fork provider that derivation is
sub-second; elsewhere it is a snapshot-derived instance plus a `fetch`. This recovers most of the
per-project cost advantage while keeping per-workroom isolation — the base is a template, not a
shared live box — and it is an evolution of the one-VM-per-workroom decision rather than a reversal.

**What a live fork actually duplicates.** An earlier draft of this section claimed forks would
collide on session UUIDs. That was wrong, and wrong in a way worth recording: by this document's own
definition the base is a *template* with no sessions, so there are no UUIDs to collide, and "the
agent re-mints identity" is incoherent with identity being **client**-minted (`SessionIdentifier`,
16 bytes, minted app-side). What genuinely duplicates across two forks of one base is
**machine-level**: the ssh host key, machine-id, the agent's instance/socket identity, any
base-resident pty, and any credential baked into the base. Tracked as open questions 9-11.

- **Fork the machine, fork the private key.** Premise 6's "blast radius is one workroom" is false if
  every fork inherits the base's deploy key. Mint *after* the fork, never bake it into the base.
- **Fork the machine, fork the ssh host key.** Transport is ssh, and boxd is a per-VM *port*, so
  `known_hosts` keys on `[host]:port`. Either forks share the base's host key (and are mutually
  MITM-able) or each fork gets a fresh one — and a fresh key trips `VCSRemoteFailure.hostKeyUnverified`
  under the `-o BatchMode=yes` the app already sets (`StatusCommandRunner.swift:172`), which cannot
  prompt. The driver needs a stated host-key policy; there is none yet.
- **A hibernated base may not be forkable at all.** A base machine is idle by definition — nobody
  works on it — so after four hours it hibernates, and every fork becomes wake-then-fork. Whether
  boxd can fork a hibernated machine is unverified, which puts a caveat on the sub-second creation
  claim.

The sweep also reported that Firecracker documents resuming one snapshot twice as insecure, with
net/vsock
dropping on resume. boxd is the same KVM-microVM class, and fork-two-workrooms-from-one-base is
exactly that pattern — an inherited hazard to measure, not a foreign one.

**E2B is noted but deliberately out of scope here.** It suits a different job (running agent-written
code inside the product) and its only load-bearing contribution to *this* design is that it is
SDK-only — Python, TS, CLI, REST, no Rust SDK — which makes the SDK-language precondition in Phase 3 concrete
rather than theoretical: an E2B driver would talk REST from Rust. Anything more belongs in its own
document.

**Ruled out:** exe.dev (no live fork, and its $20/mo flat pool is 2 vCPU/8 GB *in total*, which one
full-size workroom consumes); Daytona's OSS path (README says unmaintained since June 2026, core
moved to a private codebase); `kern` (Linux-only by design, and its own docs call its shared-kernel
boundary unsafe for other people's code — fine locally, not shippable in a macOS app).

**Single-vendor risk, stated plainly:** boxd is a small, new provider, and the sweep recorded no
funding or maturity signal for it (unlike exe.dev's Series A). Its self-host licence is also
unknown. That is a real bet — and it is exactly why the driver seam was specified before any
provider was chosen. The
driver seam is what makes boxd replaceable rather than load-bearing.

## Premises

1. **The remote terminal needs no new terminal code.** `GhosttySurfaceView` never touches terminal
   bytes — libghostty owns its own pty, and the persistent path merely sets `config.command` to a
   relay process (`applyPersistentSession`, `GhosttySurfaceView.swift:405-436`). Remote is a
   different byte stream carrying identical frames (`SessionFrame`: 1-byte kind + 4-byte
   big-endian length, 1 MiB cap, `SessionFrame.swift:21-22`).
2. **Persistence is already built, and remote makes it more valuable.** The replay/reattach
   behaviour above was written for app relaunch and generalises to a dropped link — subject to
   open question 2, which is the one thing nobody has measured.
3. **The unified agent is an architectural bet, not a free local win.** ~~It removes the
   in-process cooperative-pool starvation behind the History-loads-forever bug.~~ **REVISED — that
   bug is already fixed.** `HistoryModel.swift:142-145` wraps the log read in `runBlocking` (GCD),
   `VCSProviding.log` is deliberately synchronous, and both providers wrap every read in
   `runBlocking`. There is no outstanding starvation dividend to collect. The remaining
   justification for unify is that remote would otherwise rot as the neglected branch of every
   function — a real argument, but a preference rather than a measurement. See the honesty note
   under Recommended Approach.
4. **The driver contract must be a byte stream, not an ssh endpoint.** Otherwise half the named
   providers cannot be drivers.
5. **The repo reaches the far side from its git remote**, never by syncing the local working copy.
   Reinforced by one-VM-per-workroom: there is no shared `.git` to worktree from. **Amended for
   base derivation:** a derived instance inherits the base's *stale* clone, so every workroom needs
   a `fetch` plus checkout, and that can only happen once its own credential exists. The full
   sequence is in Phase 4; the point here is that "clone from the remote" describes how the repo
   reaches the *base*, and every workroom after that is a derivation plus a fetch.
6. **~~Credentials go over via ssh agent forwarding, never copied.~~ REVISED — wrong.** A forwarded
   agent dies with the client connection, so it is absent in precisely the state this feature
   exists to create: laptop closed, agent still working. It also assumes ssh despite the byte-stream
   contract, and does nothing for HTTPS git, registries, or cloud APIs. **Replaced by:** a
   per-workroom deploy key minted on the VM and revoked with it. The private half never touches the
   Mac; blast radius is one repo; leaks expire by construction. **Cost is lower than first stated:**
   registration is `gh api --method POST /repos/{owner}/{repo}/keys`, and the app already drives
   `gh` with the user's own auth, so **Workroom stores no new credential on the Mac**. Challenge
   credit: the Codex cold read.
   **The "nothing secret on the VM" half of this premise is now retracted.** The lifecycle shim
   (see Provider Decision) puts a *provider control-plane* credential on the instance, so the
   accurate statement is: the VM holds two short-lived, instance-scoped credentials — a git deploy
   key it generated itself, and a provider defer token — and neither is a durable account secret
   stored by Workroom, and both die with the instance. What the Mac stores is still nothing. That is
   a weaker claim than the original and it is the true one; the achievable scope of the provider
   token is a per-driver trait, and a provider that can only issue account-wide tokens is a
   materially worse driver for that reason alone.
   **Three further caveats found in review, all real:**
   (a) with a COW-fork provider the key must be minted after the fork, or every workroom shares the
   base's key and the blast-radius claim is void (OQ10); (b) `POST /repos/{owner}/{repo}/keys`
   requires **admin** on the repo, not write, so this fails on ordinary org repos where the user is
   a writer, and on orgs with deploy keys disabled by policy — pass `read_only: false` explicitly, since a
   read-only key cannot satisfy the push criterion; (c) a deploy key authenticates **git only**,
   not the GitHub API, so it cannot serve the `gh`-backed PR/CI status if that moves to the agent —
   see Phase 2, where the resolution is to keep `gh` on the Mac. Premise 6 holds only with (c)
   resolved that way; running `gh` remotely would void it.
7. **Config absorbs a host descriptor with no migration.** `config.json` is read and written as an
   untyped `map[string]any` under a flock, and unknown keys round-trip untouched
   (`internal/config/config.go:91-148`). The typed read-side view is only `Workroom{Path}` and
   `Project{VCS, Workrooms}`; there is no `kind` discriminator, and `workrooms_dir` / `channel` are
   the only reserved scalars. **But two warnings will false-positive on every remote workroom** and
   must be host-gated: `DirectoryMissing` from the per-workroom `os.Stat`
   (`list_data.go:117-120` → `hasBlockingWarning`, `Models.swift:28`), and `VCSWorkroomMissing`
   (`list_data.go:122-124`), which tests membership of `ListWorkrooms(projectPath)` on the **local**
   project repo — a set a remote clone can never be in, by construction.
8. **The product aims to be provider-agnostic; providers differ in speed and in a small number of
   gates.** The driver declares transport kind (stream-over-ssh vs SDK exec vs WebSocket), how fast
   `deriveFromBase` is and whether it carries live processes, disk durability, `maxLifetime`, and
   how the provider defines idle. `maxLifetime` is definitely a gate — instances that die on a wall
   clock cannot host a workroom. **Idle-definition is not a gate** — the far-side lifecycle shim
   translates it per provider — but the **scope of the control-plane credential that shim needs is
   itself a declared trait**, since an account-wide token on a disposable box is a much worse deal
   than an instance-scoped defer token. The remaining differences are accelerators or
   agent-supplied capabilities (busy/idle decision, port forwarding, primary-screen scrollback).
   Accepted degradation: where a provider cannot suspend with processes, a resumed workroom returns
   primary-screen content but neither its running process nor a full-screen program's screen.

## Cross-Model Perspective

An independent cold read (Codex, `gpt-5.6-sol`, high reasoning) saw the codebase findings and the
decisions but not the conversation.

- **Coolest unconsidered version:** "A workroom that keeps working after the Mac closes… Remote
  compute is interesting; independence from the laptop is the genuinely new capability." It went
  further than the session had: the workroom becomes a durable actor that humans *or agents* enter
  and leave, snapshot, fork, and hand off between devices.
- **What the decisions reveal:** it picked out the unify choice — "he cares most about making
  remote workrooms *real Workrooms*, not bolting cloud terminals onto the side."
- **Prior art:** Coder's open-source provisioner/workspace-agent architecture at ~50%.
  **Disagreed and not adopted:** Coder is a control plane with Terraform provisioning and its own
  database, and its provisioning model is exactly what does not fit the SDK-only sandbox platforms
  the author asked to keep reachable; every item on its own "must still build" list would still be
  built.
  mosh is the more interesting steal — its state-synchronisation-over-datagram model is a better
  answer to a flaky link than replaying a ring buffer, and it is one library-sized idea rather than
  a platform. It becomes the serious option if open question 2 goes badly.
- **Challenged premise 6, and the challenge was accepted.** Its proposed proof: start a remote job
  that waits for the Mac to disconnect and then performs a private `git fetch`.
- **First commit** adopted nearly verbatim as Phase 1. **One correction:** it proposed the Rust
  agent *forward frames to* the existing Swift daemon, which would leave two pty owners —
  incompatible with unify. The agent replaces the daemon rather than proxying to it.

## Approaches Considered

### Approach A: Local-first unify, transport abstract from commit one — **CHOSEN**
Port pty + replay to Rust under a differential harness, switch local workrooms onto the agent over
a Unix socket, then add stream drivers and provisioning. Effort L. Never has two code paths; puts
the dangerous port where it can be diffed against a working original. Cost: the visible payoff is
last, and with premise 3 corrected its early local benefit is gone.

### Approach B: Remote-first vertical slice
Agent remote-only against a container over ssh, live remote prompt in days, retrofit local
afterwards. Rejected: leaves the Swift daemon local and the Rust agent remote for weeks, the exact
divergence unify was bought to prevent, and "retrofit local later" is the commit that does not get
made.

### Approach C: Two-speed agent — ptys now, VCS reads later
Agent owns ptys and exec; its VCS service shells out to the CLI / `jj` / `git` on the far side
while in-process reads stay a local fast path. Rejected on the risk that two VCS read
implementations disagree silently. **That objection is weaker than first argued** — a differential
harness is exactly the mechanism Phase 1 already proposes for the pty port, and the same tool
applies here. C remains the live fallback, particularly for the git half if open question 1 proves
expensive.

## Recommended Approach

**Approach A, preceded by a throwaway spike (one day, six items, prioritised).**

**Honesty note.** With premise 3 corrected, Phases 1-2 are a multi-thousand-line Swift→Rust
port with no measurable local dividend, standing in front of the feature this document exists to
deliver. The remaining case for it is architectural coherence, which is what the author chose
deliberately and repeatedly. That is a legitimate reason. It is not the same as a free win, and if
Phase 0 or open question 1 goes badly, Approach C is the honest fallback rather than a defeat.

### Phase 0 — the spike (one day, thrown away)
On a throwaway branch, prove **six** unknowns, write down what happened, delete the branch. Phase 1
starts from `master` so the spike cannot become the implementation by accident.

**The day is a budget, and two items are gated on four-hour provider timers** (item 5's idle window,
item 6's hibernated base), so start both in the background at hour zero and do the rest while they
run — otherwise this is 8+ hours of wall clock inside a day. Item 1 alone is three syscall families
plus the foreground-pgid logic, so decide in advance which items may come back unanswered. Items 3,
5 and 6 may not.

1. **Rust pty ownership on Linux — including process introspection.** The poll loop and `forkpty`
   are the easy half. The risky half is the foreground-detection layer the OSC 2/7 resynthesis
   depends on: `SessionPTY.swift` is `import Darwin` throughout and uses `KERN_PROCARGS2` (`:151-160`),
   `proc_pidinfo`/`PROC_PIDVNODEPATHINFO` (`:186-187`) and `KERN_PROC_ALL` (`:370-376`). Linux
   equivalents are `/proc/<pid>/{cmdline,cwd,stat}`. Port that, not just the pty.
2. `SessionFrame` framing over a non-socket stream — `ssh host cat` is a sufficient stand-in.
3. **Kill the link mid-TUI, reattach, check the repaint.** The single most important measurement in
   this design. The alt-screen drop plus row-bump/SIGWINCH trick was tuned for a local relaunch
   with a 0.03s settle; whether it survives real network latency is unknown. If it fails, mosh's
   model displaces the replay buffer and the port scope changes.
4. `git clone` on a fresh box using a deploy key generated on that box, registered via `gh api`.
   Try it on an org repo where you are a writer but **not** an admin — that is the case premise 6 caveat (b) says
   fails, and it is the common case.
5. **What does the provider actually measure, and which lever moves it?** The **most important item**
   in the spike, because the agnosticism decision bets the headline capability on defeating idle
   policy. Establish the measurement *first* — CPU activity, an attached client, or a control-plane
   timer — because the lever follows from it and testing the wrong lever proves nothing. An in-guest
   keepalive is unobservable to a provider that counts client attachment, so a naive pass there would
   validate only providers that never needed the service. Then: start a job longer than the idle
   window, disconnect the Mac entirely (asleep, not just detached — that is the real state), and see
   whether it finishes with each candidate lever. OQ17 is now decided in principle — a far-side
   shim — so this measures *which provider call the shim makes* and how narrowly its credential can
   be scoped, not whether the approach is needed.
6. **Derive two instances from one base and diff what they share:** ssh host key, machine-id, agent
   socket identity, any live pty, any credential on disk — and whether networking survives a second
   resume. Open questions 9, 10 and 11 turn on this. Do it on the *live-fork* path, since that is
   the derivation most likely to copy state it should not. Then hibernate the base for four hours
   and derive again — see the hibernated-base caveat in Provider Decision.

### Phase 1 — the agent exists, locally
`feat(agent): tunnel local sessions through a versioned agent stream`

- **The relay is a mode of the agent, not a second binary. DECIDED.**
  `applyPersistentSession` sets `config.command` to a *command line* (`<binaryPath> attach`,
  `PersistentSessionService.swift:47-49`), so libghostty forks a **process** — meaning Phase 1 needs
  both a forked relay executable and the in-process Swift `AgentConnection` the rest of the app uses.
  **One Rust binary serves both roles: `wr-agent serve` owns ptys and services, `wr-agent attach` is
  what libghostty forks.** That is exactly today's `workroom-session daemon|attach` shape, which is
  already shipped and debugged, and it means the frame codec exists once in one language rather than
  being duplicated in Swift and Rust indefinitely.
  What settled it: the unify decision already requires the local agent to be a separate **process**
  (that is how jj-lib leaves the app's address space), so a universal-macOS-Rust executable target is
  unavoidable regardless. Once you are paying for that target, a second binary buys nothing — and
  keeping the Swift relay would have saved no build target while leaving `SessionAttachClient.swift`
  alive inside `macapp/WorkroomSession/`, blocking that directory's deletion.
  **So the build products are two binaries from one crate, plus one open question:**
  1. **A universal macOS `wr-agent`.** `vcs/` produces a static xcframework, not an executable.
     The gap is precise: `macapp/Scripts/build-helper.sh` already builds and signs an executable into
     the bundle (that is exactly what it does for the Go CLI) — what does not exist is a **universal
     Rust** target, and the distributed CLI comes from goreleaser rather than that script.
  2. **A Linux `wr-agent`**, pushed to the far side. **Name the architectures** — if guests can be
     x86_64 *or* arm64 you ship two ELFs per artifact, which also doubles the codesign question in
     the Distribution Plan.
  3. **Still open: where the `HostDriver` lives.** Provisioning precedes any far-side agent, so the

     product) or the driver is simply written in Swift and the trait is not Rust at all. The second is
     probably right — the driver talks HTTP to provider APIs, which Swift does natively — but it is
     not yet decided. Tracked as OQ21.
- **Name what survives (S6).** `macapp/WorkroomSession/` (1967 lines) is the daemon plus attach

  separate target holding `SessionFrame`, `SessionReplayBuffer`, `SessionBytes`, `SessionMessages`

  relay decision: Rust owns the pty, the replay buffer and the framing; Swift keeps only what a

- New crate `wr-agent` beside `wr-vcs-core`. A **versioned** multiplex envelope carrying stream id,
  service kind, and payload — versioned from the first commit; see the Distribution Plan's resume-policy item for what makes the
  versioning
  real rather than ceremonial.
- Terminal service: the pty owner. Port `SessionPTY` including the self-pipe `execve`
  failure-detection trick, which is load-bearing — it is what makes a genuine exec failure report
  `.failure` instead of acking `.attached` and closing moments later.
- **Port under a differential harness, driven by generated input (S1 corrected).** The earlier
  claim that ~200 tests encode these semantics was wrong: `SessionReplayBufferTests.swift` has **15**
  tests in 126 lines, and the whole `macapp/WorkroomAppTests/Session/` directory has **41**. The
  actual specification is the source's own doc comments — `SessionReplayBuffer.swift` (457 lines,
  largely commentary) and `SessionDaemon.swift` (724 lines). So translating the test corpus is
  necessary but nowhere near sufficient. Drive the harness with **generated and fuzzed byte
  streams** — escape-sequence fragments split across chunk boundaries, alt-screen enter/exit,
  truncated UTF-8, embedded queries — and diff the two implementations' replay output, asserting
  the daemon's documented invariants directly.
- **Session identity and cross-machine reattach.** Identity today is a client-minted 16-byte UUID
  per pane (`TerminalSessions.swift:1724`, `persisted ?? UUID()`), stored in a snapshot at
  `Application Support/Workroom/<bundleID>/session.json` (`SessionStore.defaultURL`) — **local
  only**, and **bundle-id-scoped on purpose**: that scoping is called mandatory in its own doc
  comment, because all three identities (Workroom, Dev, Nightly) write under the same parent and an
  unscoped path would let a Dev run's fixture temp-dir workrooms be restored into the release build.
  Whatever replaces this store must preserve that separation. So "open the same workroom from a
  different Mac"
  does not follow from the current model: Mac B knows none of Mac A's pane UUIDs, tab layout, split
  geometry, or titles, and the `.list`/`.sessions` frames return opaque ids with no pane→tab
  mapping. Cross-machine reattach therefore requires **agent-side session naming and enumeration,
  plus workroom UI state living with the workroom rather than the client**. That is a real
  deliverable, not a free consequence; it is scheduled in Phase 4 and tracked as open question 8.
- Integration test: type a sentinel, drop the transport, reconnect with the same pane UUID, assert
  replay.

### Phase 2 — the services, still local
Every item below is a service on the multiplexed stream. The doc previously named only VCS reads;
these are the subsystems that actually gate "a remote workroom is a real workroom".

- **VCS reads.** `VCSProviding` is eight methods that all take `root: URL`. It is **not** reached
  through one switch: `VCS.provider(for:)` is injected as a closure default at
  **four** sites — `VCSWriting.swift:278`, `HistoryModel.swift:53`, `DiffResolver.swift:41`,
  `BranchResolver.swift:24`. Exactly **one** use has no seam at all: `ChangesetDetailView.swift:150`
  calls `VCS.provider(for: root)` directly inline. (This count took two corrections to get right —
  an early draft said six by counting a doc comment and a direct call as injection points, then a
  fix over-corrected by calling two integration tests seamless when they in fact pass
  `{ try VCS.provider(for: $0) }` as an explicit closure literal into the same `makeProvider:`
  parameter. Four defaults, one inline call, and the tests already inject.) So the single site
  needing restructuring is the one that looked cheapest. The seam is convenient where it exists,
  but the routing input is `VCS.repoKind(at:)`
  (`VCSProviding.swift:70-84`), a **local filesystem probe** that returns `.unsupported` for any
  path not on this Mac. Remote routing needs a host threaded to those sites or a provider registry
  keyed on the workroom, not a switch-body edit. Decide which.
- **VCS writes — a whole second protocol the earlier draft missed (C1).**
  `macapp/WorkroomApp/Core/VCSWriting.swift` is 1910 lines and seven methods (`remoteState`,
  `fetch`, `push`, `pullRebase`, `abortRebase`, `commit`, `stagedContentAtRisk`), shelling out to
  local `git`/`jj` with local paths, behind a **13**-case failure taxonomy (`VCSRemoteFailure`,
  `VCSWriting.swift:26-84` — including `authRequired`, `hostKeyUnverified`, `rebaseInProgress` and a
  `locked(VCSLockFile?)` payload) and a presentation layer in `VCSSyncPresentation.swift`. All of it
  has to cross the stream, **including the
  lock-file-on-disk distinction that decides Retry vs Abort** — a local-filesystem fact the remote
  side must report rather than the client infer. Comparable in size to the read side; price it
  separately. **And it carries a second local path the watch discussion already noticed but this
  one did not:** six of the seven methods take `path` *and* `projectRoot` (`stagedContentAtRisk` is
  the exception — it is local-only and takes just `path`), and `projectRoot` is load-bearing:
  `opDirectory(.fetch, …)` returns it (`:373-375`) and `JJSnapshotGate.run(projectRoot:)` keys on it
  (`:1421-1423`), 31 references in the file. For a remote **clone** the project root collapses into
  the workroom itself, exactly as the third watch site does, so those six signatures need that
  reckoning.
- **A file service (C2).** `FileTree.swift` builds and parses VCS commands through a command runner
  rather than `VCSProviding`; `PlainFileViewer.swift:138` mmaps the file off local disk;
  `DiffResolver.swift:280` reads local files. Directory listing and raw file read are their own
  service, not a side effect of the VCS one.
- **Change notification.** FSEvents has no remote equivalent (`WorkroomFileWatcher.swift:56-83`).
  The agent becomes the watcher — FSEvents locally, inotify on Linux — and pushes events on the
  stream. Keep the leading + trailing coalescing; it exists because uncoalesced events forked
  git/jj ~70 times a second. **Note there are three watch sites, not one (F4):**
  `AppStore+WorkroomStatus.swift:761` (the workroom dir), `AppStore.swift:2928-2930` (the
  per-project `.git`/`.jj` dir, because a git worktree's refs live in the main repo), and
  `FileTreeModel.swift:124`. For a remote **clone** the second collapses into the workroom itself,
  so local and remote watch topologies differ — do not port the project-root watch to remote.
- **Three services that exist to make providers interchangeable.** These are the concrete cost of
  the agnosticism decision. An earlier draft called them cheap and called the wakefulness signal
  free; review proved both claims wrong, so here they are honestly:
  - **Busy/idle decision — the design's load-bearing piece, and the signal is not yet sound.** Note
    the split settled in Provider Decision: this service only *decides* busy or idle and reports it;
    a per-driver far-side shim does the provider-specific translating (Phase 3). Two problems remain
    on the deciding half:
    - *The signal is wrong in both directions.* "Foreground pgid is not the shell"
      (`SessionPTY.foregroundProcessGroup`, `tcgetpgrp`; used once today at
      `SessionDaemon.swift:376-377`) reports **idle** for `make &`, `npm run dev &`, or any
      backgrounded job — the shell is back in the foreground — which is exactly the
      kick-it-off-and-close-the-lid case. A `setsid` descendant is invisible entirely, and
      `SessionPTY`'s own `terminationTargets` doc comment (`:217-232`) already documents that hole:
      a shell can `setsid()` a descendant out of the session and escape both `killpg` and
      `getsid`-based matching. There is no pty at all behind the exec service or a detached server.
      And it reports **busy forever** for an idle `vim`, `tmux`, or an agent sitting at its prompt —
      which is a remote workroom's *normal* state, so the box would never hibernate and the cost
      property the provider was chosen for evaporates (see OQ7, €0.049/vCPU-hr with no ceiling).
      The sound signal is process-tree liveness under the session — the tree walk
      `terminationTargets` already performs — combined with a CPU-time or `/proc/loadavg` delta,
      plus an explicit "an idle TUI is not busy" rule, hysteresis, and a maximum-awake ceiling.
    - *And it is not free.* Today the read is one line fired once per attach, inside the attach
      handler. This needs a continuous poll loop that runs **while detached**, a busy/idle policy,
      and a ceiling. That is a new service, not a reuse of an existing one.
  - **Port forwarding over the agent's own stream.** A forwarded port becomes another service on the
    multiplex, so no provider public hostname is required, and it works identically on a local
    container. **Caveat:** it only carries while a client is attached, so "come back to a running
    preview URL" still wants a provider hostname — the same structural limit as wakefulness.
  - **Scrollback durability — buys nothing for the case it was introduced for.** The intent was that
    a stop-and-reboot provider still returns your terminal content. But `SessionReplayBuffer`
    **empties itself** on entering the alternate screen and returns `[]` while it is active
    (`SessionReplayBuffer.swift:3-4`, `:72`, `:118-126`, `:139-141`), so every full-screen program —
    i.e. every long-running agent, i.e. precisely the accepted-degradation case — has an empty
    buffer. And after a reboot the child is dead, so there is no SIGWINCH repaint path either.
    Persisting the buffer therefore covers **primary-screen scrollback only**. Returning a
    full-screen program's *screen* after a reboot needs server-side terminal state — a mosh- or
    tmux-shaped emulator on the far side — which is materially larger scope and belongs next to
    OQ2, not inside this bullet.
- **`gh`-backed status.** `WorkroomStatusResolver` runs `gh pr list`, `gh repo view`,
  `gh api graphql` and `gh run list` **with the workroom as cwd** (`:222,237,277,306,323,433`). For
  a remote workroom that directory does not exist locally, so every PR/CI/branch badge fails with
  `launchFailed`. **One wrinkle: git and jj already differ here.** `ghProbeDirectory` returns
  `vcs == "jj" ? projectRoot : path` (`:391-393`), because a secondary jj workspace has no `.git`
  for `gh` to resolve — and since there is no such thing as a remote *project* (Phase 4), the jj path
  would accidentally keep working while git fails. Whatever replaces this has to unify two
  behaviours, not one. **Resolve it by passing a repo identity instead of a directory and keeping
  `gh` on
  the Mac** — running `gh` on the agent would need a GitHub *API* token over there, which a deploy
  key cannot provide and which premise 6 forbids. This is the branch premise 6 depends on, so it is
  a decision, not an either/or.

### Phase 3 — the stream drivers
- **`HostDriver` is four methods**, deliberately smaller than the earlier draft's six:
  `create` provisions a **base**, `deriveFromBase` provisions a **workroom instance** from one,
  `destroy` takes either, and `openStream` connects to either. (Phase 3's "one creation path" rule
  is about workrooms; it does not orphan `create`, which is how a base comes to exist at all.)
  `start`/`suspend` are gone — lifecycle
  hinting is now driven by the agent's wakefulness reports, so each driver implements whatever its
  provider needs behind that rather than exposing suspend semantics upward. Declared traits:
  transport kind, derive speed, whether derive carries live processes, disk durability, and
  `maxLifetime`.
- **The gates, stated honestly.** An early draft made the headline feature depend on
  `suspend-with-processes`; the agnosticism decision moved that burden into the agent's wakefulness
  service, so a stop-only provider became a *degradation* rather than a disqualification. Review
  then showed a client-side translator cannot run lid-closed, which is why the far-side lifecycle
  shim exists (Provider Decision). With it, there is **one** gate: a wall-clock `maxLifetime`
  shorter than a working day. It belongs in the UI at provider-selection time, not at
  workroom-creation time — as does a warning where the provider can only issue a broadly-scoped
  control-plane token for the shim.
- **The far side carries exactly two provider-specific pieces, and no more.**
  - **A supervisor.** Something must start the agent on boot and after resume, and on the far side
    that is genuinely per-driver (systemd unit, provider init hook, wrapper) because it *is* how that
    provider's box boots. Note the far side differs from local here: a remote agent must survive with
    no client attached, since the busy/idle reports feeding the shim have to keep flowing while your
    Mac sleeps. So remote does need supervision that local does not.
  - **A lifecycle shim.** Takes the agent's busy/idle reports and makes the provider's control-plane
    defer call, so a job survives an idle timer with the Mac asleep (see Provider Decision). Holds
    an instance-scoped provider credential, must die with the instance including on failure paths,
    and must stay small enough to audit by reading. Its credential scope is a declared trait.
  Everything else pushed to the far side is the agnostic agent. If a third provider-specific
  component appears, that is the signal the abstraction is wrong.
- **Local needs no supervisor at all. DECIDED — and an earlier claim in this document was wrong.**
  A previous revision asserted that `SessionDaemon.swift:97-107`'s self-exit
  (`sessions.isEmpty && connections.isEmpty`) had to go, because the agent would also own VCS reads
  and the file watcher. That does not follow: diffs, history and watches are things a **connected
  client** asks for, so an agent with no connections and no ptys is holding nothing anyone can lose.
  The one thing that must outlive the app is a live terminal session — which is precisely what the
  existing rule already protects. So the local agent keeps today's mechanism unchanged:
  `posix_spawn` on connect-failure, a `flock` so only one instance wins, idle self-exit when the last
  pty and client are gone. Zero work, already debugged (including the fallback-socket-path collision
  and the `sockaddr_un` length off-by-one found in review), and no install footprint. If some later
  service genuinely must outlive every client, that is when supervision earns its place, and it will
  be obvious.
- **SDK language is a precondition, not an assumption.** Whatever process opens the driver
  stream embeds the provider SDK in *its* language. "An SDK exec call satisfies the contract
  equally" holds only where an SDK exists for the relay's language. Verify per provider before
  counting it as a driver.
- **Two drivers, different jobs.** A local container over ssh comes first as the **test fixture** —
  it is the cheapest real driver and becomes permanent CI for the remote path. `boxd.sh` is the
  first *real* driver (see Provider Decision); its per-VM SSH port means the transport is plain
  ssh-stdio, the easy case, so the abstraction is exercised without being stressed until an
  SDK-transport driver arrives (E2B over REST is the likely first, though integrating it is not
  scheduled here).
- **One creation path, not two.** `deriveFromBase` is the only creation mechanism; drivers differ in
  how they implement it (COW fork of a live machine, snapshot-derived instance, or a full clone where
  a provider has neither). The earlier draft branched creation on `liveFork` and therefore needed two
  code paths with two sets of bugs. It now needs one, and the accelerator lives inside a driver.
- **The CI gap closes as a consequence.** Because the portable derivation is what ships and what the
  product uses everywhere, the container fixture exercises the real path rather than a fallback
  nobody runs. What remains uncovered by CI is boxd's *live-process* derivation specifically — a
  narrower gap than the whole fork path, and one a nightly boxd job can cover if it earns it.
- **State a host-key policy** (see Provider Decision). Fresh-key-per-fork plus `BatchMode=yes` cannot prompt, so
  the driver has to deliver the expected host key out of band or pin the base's.
- **Agent bootstrap over the transport.** Workroom.app ships the Linux agent binary and pushes it on
  first connect rather than baking provider images. One source of truth, no image maintenance, and
  it works for SDK-transport providers with no image concept. (This is the one piece of Coder's and
  VS Code Remote's approach worth copying.) See the Distribution Plan for the two things that must be
  confirmed
  before this is load-bearing.

### Phase 4 — provisioning, creation, lifecycle, and the UI
- **Remote creation is one sequence, `deriveFromBase`, with driver-specific speed.** Provision a
  per-project base once (deps installed, repo cloned, agent present), then derive each workroom from
  it. Whether the driver does that as a live COW fork, a snapshot-derived instance, or a full clone
  is internal to the driver; the sequence above it never changes:
  **derive → re-init machine identity → mint keypair on the instance → register the public half via
  `gh api` from the Mac → fetch and check out → serve requests.** Every step before the last must
  roll the instance back on failure, and an instance must not serve a request until identity and
  credentials are its own (open questions 9 and 10) — inherited state is the failure mode wherever
  derivation copies a running machine.
- **Build order within this phase is fixed by the agnosticism decision:** the slowest correct
  derivation first (snapshot or clone, whichever the fixture supports), then boxd's live fork as an
  optimisation behind the same interface. Not the other way round.
- **Who performs creation, Go or Rust?** Provisioning and derivation are the driver's job (Rust,
  client-side per Phase 1 product 3). The **repo work** — clone, fetch, checkout — is the only part with a Go CLI
  shape, and the answer is to **keep the Go CLI on the Mac and run the repo commands through the
  agent's exec service**. The trap in the alternative: shipping a Linux Go binary to the far side
  means the Distribution Plan carries a second pushed binary *and* the CLI writes a
  `~/.config/workroom/config.json` on the VM, forking config semantics across machines for no gain.
  Where the CLI does run locally its `--json` contract is untouched (one envelope on stdout, NDJSON
  on stderr), so `WorkroomCLI.run`'s parsing stays reusable — but note that derivation itself
  produces no envelope, because it is an API call rather than a command.
- **The base machine is a fourth kind of thing** the config and UI have to model: not a project, not
  a workroom, but a per-project template with its own lifecycle (build, refresh when deps change,
  destroy). Nothing in the current schema anticipates it, though premise 7's untyped map absorbs it.
- **Remote deletion needs its own path too (C5).** The local path is `git worktree remove` / `jj
  workspace forget` plus a teardown script. Remote is destroy-the-box plus revoke-the-key, and
  `delete-project --with-workrooms` cascades per-workroom teardown, so it needs the remote fork as
  well — not just `--from-disk`'s safety gate.
- Config: a host descriptor on **both** the project and the workroom entry — not an either/or, since
  one VM per workroom plus a per-project base machine means both levels carry host state. No
  migration needed (premise 7). **But note what cannot be represented:** `add-project` requires PATH
  to be an existing local Git/JJ repo, and project keys are canonicalized local paths
  (`config.CanonicalPath`). So there is no such thing as a *remote project* — only remote workrooms
  belonging to a locally-registered project. That is a real product constraint, not an oversight;
  say it in the UI rather than discovering it.
- Host-gate **both** `DirectoryMissing` and `VCSWorkroomMissing` (premise 7), and add a distinct
  state for "the provider destroyed the box" — a reclaimed spot instance or expired sandbox TTL is
  not a deleted local directory and must not render as `hasBlockingWarning`.
- `delete-project --from-disk`'s safety gate (`cmd/delete_project.go:174-229`) is built on
  `filepath.Rel` ancestor semantics over local absolute paths and has no notion of a host. It must
  **refuse** remote paths rather than reason about them.
- **Cross-machine session enumeration** (from Phase 1's S4 note): agent-side session naming, a
  pane→tab mapping on the wire, and workroom UI state stored with the workroom.
- **OSC 7 and cmd-click (C7).** `SessionDaemon.swift:395-401` deliberately emits
  `kitty-shell-cwd://localhost<cwd>` because Ghostty validates the OSC 7 host against the local
  hostname. From a remote agent that is a *remote* path labelled local, and
  `TerminalLinkOpener.absolutePath(for:cwd:)` (`TerminalLinkOpener.swift:27-31,202`) will then
  resolve a cmd-clicked file against it **on the Mac**. Week-one bug; needs a host-tagged cwd and a
  link opener that routes through the file service.
- Per-workroom deploy key: mint on create, revoke on destroy, and revoke on the failure paths too.
- Idle state per remote workroom in the sidebar. **Cost display is deliberately deferred** —
  it needs per-provider billing APIs and there is no spending policy yet (open question 7).

## Open Questions

1. **How does the Rust agent read git — and the earlier answer here was wrong.** The draft proposed
   spiking `git2-rs`. Correction: **gix is already in the tree.** `vcs/Cargo.lock:664` has
   `gix 0.85.0` with 46 `gix-*` crates, pulled transitively by `jj-lib =0.43.0`, and the only
   `-sys` crates in the lock (`core-foundation-sys`, `js-sys`, `linux-raw-sys`, `windows-sys`) are
   pure-Rust platform shims — no C toolchain anywhere. So adopting gix costs roughly a
   `Cargo.toml` line, while `git2-rs` would *add* `libgit2-sys` plus `openssl-sys`/`libz-sys` to a
   C-free tree and undercut the "Rust cross-compiles cleanly" premise behind the language choice.
   **Spike gix, not git2-rs.** The real risk is unchanged and stays real: output parity against
   SwiftGitX/libgit2 — `GIT_SORT_NONE` page ordering (documented at `VCSProviding.swift:19-24`) and
   rename detection (`GitCommitDiff`). Note this retires `wr-vcs-core`'s own stated invariant
   ("the ONLY crate allowed to depend on jj-lib… jj-only by design",
   `vcs/crates/wr-vcs-core/Cargo.toml:8`), which needs an explicit decision rather than a silent
   overturn — possibly a second crate rather than widening that one.
2. **Does the alt-screen repaint trick survive real network latency?** Phase 0 item 3 answers it.
   If not, mosh's state-synchronisation model becomes the serious option and the replay buffer's
   port scope changes.
3. ~~**Provider selection.**~~ **ANSWERED for the first driver** — boxd.sh, with a local container
   as the fixture. See Provider Decision. Residual risk is vendor maturity, not selection. Which
   provider becomes the *second* driver is open, and the agnosticism claim is unverifiable until one
   exists (OQ18).
4. **What does a remote "Run command" tab do?** Run tabs are explicitly never persistent
   (`TerminalPersistentSessionPolicy`), a local-only assumption a remote dev server probably
   invalidates.
5. **The Quick Terminal bypasses `TerminalSessions`** and builds a bare `GhosttySurfaceView`.
   Presumably local forever — but decide it rather than inherit it.
6. **Non-GitHub remotes.** Now the *primary* credential problem (premise 6), since GitHub needs no
   new stored secret. A plain git-over-ssh remote has no deploy-key API and no answer here.
7. **Provider-side destruction and cost runaway.** No idle-timeout policy, no spending ceiling, and
   no answer for unpushed commits on a box about to be reclaimed. Unpushed work on a destroyed VM
   is unrecoverable — a worse failure than anything a local workroom can produce.
8. **How much workroom UI state moves to the agent?** Cross-machine reattach needs pane→tab
   mapping, titles, and split geometry to live with the workroom. Where the line falls between
   "session state" and "client layout" is undecided.
9. **What machine identity does a fork need re-minted?** Not session UUIDs — those are client-minted
   and a template base has no sessions. The real list is ssh host key, machine-id, the agent's
   instance/socket identity, and any base-resident pty. Phase 0 item 6 measures which of these
   actually duplicate; the answer decides how much post-fork initialisation the driver owns.
10. **Deploy key across a live fork, and the base's own credential.** Mint post-fork or every
    workroom shares the base's key. Separately unresolved and arguably harder: what the **base**
    authenticates as when it clones the repo in the first place. It is the one machine that outlives
    every workroom, so a per-workroom-lifecycle key is exactly the wrong shape for it.
11. **Is the inherited snapshot hazard real here?** The sweep records Firecracker documenting that
    resuming one snapshot twice is insecure, with net/vsock dropping on resume. boxd is the same
    class, and fork-two-from-one-base is that pattern. Measure it (Phase 0 item 6) rather than
    assume the wrapper handles it.
12. **boxd self-host licence is unknown**, and the provider is new with no maturity signal recorded.
    Worth knowing before it becomes the only real driver — the exit is a second driver, which the
    seam already allows.
13. **Can the wakefulness service actually defeat an idle timer?** The agnosticism decision bets the
    headline capability on it. Phase 0 item 5 settles it. A bad answer does not reopen the provider
    choice — it turns `keepAwake` back into a capability gate, which is a worse product.
14. **What is the local rollback?** Phases 1-2 replace shipped session code for every *local* user
    and the Nightly flag protecting remote does not protect that; the Distribution Plan names
    keeping the Swift daemon selectable for one release as the mitigation, but the rollback trigger
    and the dual-run period are undecided.
15. **What is the `maxLifetime` floor?** It is the one hard gate, so it needs a number. A working day
    is the obvious candidate, but a workroom is supposed to outlive a working day — which suggests
    the real floor is "no cap at all", and that quietly excludes a whole class of sandbox provider
    from ever being a driver. Decide it before advertising provider-agnosticism, because it is the
    boundary of that claim.
16. **Does the base machine need its own wakefulness answer?** It is idle by construction, so the
    busy signal never fires for it, so it always hibernates — which is correct for cost and
    inconvenient for derive latency. Possibly it wants the opposite policy from a workroom.
17. ~~**Where is the keepalive emitted from?**~~ **ANSWERED — a far-side per-driver lifecycle
    shim.** The agnostic agent decides busy/idle; the shim translates it into the provider's
    control-plane call, because a sleeping Mac can emit nothing. Premise 6 is rewritten to account
    for the instance-scoped provider credential this requires. What remains open is narrower and
    per-provider: **how tightly can that credential be scoped?** An instance-scoped defer token is
    fine; an account-wide token on a disposable box is not, and it should disqualify or downgrade a
    driver. Phase 0 item 5 measures it for boxd.
18. **What counts as the second driver?** The agnosticism claim is unverifiable with one. The local
    container is called both "the cheapest real driver" and "the test fixture" in this document —
    decide whether it counts. If it does, the success criterion is nearly free and worth little; if
    it does not, a second real provider (E2B over REST, or Hetzner) needs scheduling, and nothing
    schedules one.
19. **Does the busy signal work at all?** Its replacement (process-tree liveness plus a CPU-time or
    loadavg delta, with hysteresis and an awake ceiling) is specified in Phase 2 but unbuilt and
    unmeasured. False-busy is a remote workroom's default state under the naive version, and
    false-busy costs money continuously with no ceiling (OQ7).
20. **What is the credential path when the user is not a repo admin?** Premise 6 caveat (b) states
    the failure and this document has no answer for it, despite the summary above once claiming it
    was fixed. It is the *common* case on org repos. Candidates, none evaluated: a fine-grained PAT
    scoped to the repo, a GitHub App installation token, or a dedicated machine user. Each reopens
    "Workroom stores a secret", which premise 6 exists to avoid — so this is a real decision, not a
    detail, and it is separate from OQ6 (non-GitHub remotes).
21. **Is the client-side `HostDriver` Rust or Swift?** Provisioning precedes any far-side agent, so
    the driver runs on the Mac. Swift is the likely answer — it talks HTTP to provider APIs, which
    Swift does natively, and it avoids a third Rust build product — but that makes the driver trait a
    Swift protocol rather than a Rust trait, which is worth stating deliberately rather than drifting
    into. Small, but it shapes where every driver lives.

## Success Criteria

- Create a remote workroom from the app; a terminal opens on the far side with the repo present.
- **The same workroom behaves identically on two different providers**, differing only in creation
  latency. This is the criterion the agnosticism decision exists to satisfy, and it cannot be
  claimed until a second real driver exists.
- Two workrooms derived from one base share neither a deploy key nor an ssh host key.
- On a live-fork provider, derivation from a warm base completes in well under a second (a
  hibernated base is wake-then-derive) — as a measured *speed-up* over the portable path,
  not as the only path that works.
- A job longer than the provider's idle window finishes with no client attached, on a provider whose
  idle policy would otherwise have stopped it. That is the wakefulness service doing its job.
- Start a long-running agent in it, quit Workroom entirely, reopen hours later, and land in the
  same session with the alternate-screen program correctly repainted.
- Do the same from a **different Mac** — gated on open question 8; this criterion is *not*
  satisfied by the current session-identity model and requires the Phase 4 enumeration work.
- Close the laptop; the remote agent completes a `git fetch` and a `git push` with no client
  attached. (The concrete test that premise 6's revision was necessary.)
- Changes, History, the diff viewer and the Files tree all work against a remote workroom and agree
  with what the same commands report on the box itself — including a push, a pull-rebase, and a
  commit, since VCS writes are half the surface.
- PR and CI badges resolve for a remote workroom rather than failing `launchFailed`.
- Local workrooms run on the same agent, with the Swift daemon still **selectable** for one release
  as the rollback named in the Distribution Plan (a third state on the existing
  `backgroundSessions` preference,
  `DefaultsKeys.swift:76`). Deletion of `SessionDaemon`, `SessionPTY` and their helpers is a
  criterion for the release *after* that, not for Phase 1. When it lands, `macapp/WorkroomSession/`
  goes entirely — `SessionAttachClient.swift` included, since `wr-agent attach` replaces it — while
  `macapp/WorkroomSessionProtocol/` remains in slimmed form as the Swift client's wire codec.
  **Note the tension this accepts:** Approach A was chosen partly because it "never has
  two code paths", and a selectable daemon is two code paths for one release. That is a deliberate,
  time-boxed exception for rollback safety, not a reversal of the unify decision — and it is
  narrower than Approach B's rejected version, which would have run two paths indefinitely with the
  remote one diverging.
- The ported replay buffer matches the Swift original on the generated/fuzzed corpus. Every session
  and store test passes **except** `SessionDaemonEndToEndTests` (7 tests) and
  `SessionDaemonHarness`, which drive the deleted binary and are rewritten against the agent rather
  than expected to pass.

## Distribution Plan

- **The app and CLI** keep their existing pipeline: tag-driven GitHub Releases, Sparkle appcast,
  notarization, channel classification (see the `curate-release` skill). Unchanged.
- **Two artifacts ship to the far side, not one:** the provider-agnostic Linux `wr-agent`, plus a
  per-driver **lifecycle shim** (and whatever supervisor unit that driver needs). Both ride inside
  Workroom.app and are pushed on first connect. The shim is small and provider-specific by design —
  it is the sanctioned exception to agnosticism — but it means the bootstrap pushes a *set* keyed by
  driver rather than a single binary, and each driver's shim needs its own Linux build target.
- **Two things must be confirmed before push-on-first-connect is load-bearing:**
  - **A Linux ELF inside a notarized `.app`.** `lipo`/`ARCHS` checks do not apply to an ELF;
    the exposure is the reverse. The ELF must **not** land in `Contents/MacOS` and must be sealed
    as a resource. Confirm codesign and notarization accept it before Phase 3 depends on push-the-
    binary bootstrap; if they do not, the "no provider images" claim collapses.
  - **Resume policy versus version lockstep.** Phase 1 versions the envelope because an agent
    on a suspended VM can be older than the app reconnecting to it; Phase 3's bootstrap implies
    lockstep. These reconcile only with a stated policy: does reconnecting to a suspended box
    **replace** the running agent — killing the pty children this feature exists to preserve — or
    negotiate with the old one over the versioned envelope? Unspecified today, and it decides
    whether the versioning is real or ceremonial.
- **New CI burden:** a Rust Linux cross-compile for `wr-agent` (note `prost` in the lock means
  `protoc` is a build-time requirement) plus the container-driver integration job.
- **A past trap, already fixed, worth not re-introducing.** Xcode's `ARCHS` is a space-separated
  list, and this repo once case-matched it as a single token, silently falling back to arm64 on
  universal builds and shipping an arm64-only Go CLI inside a fat `.app` for 23 betas.
  `macapp/Scripts/build-helper.sh:28-50` is the **fix** — it iterates `ARCH_LIST` and hard-errors on
  an unknown arch, with the regression written up in its own comment. Any *new* universal Mac binary
  must go through that same iteration rather than growing its own arch handling, and CI should
  `lipo`/`file` the shipped artifact regardless.
- Remote mode must not reach the stable channel until it works, per PRODUCT.md principle 5. Ship it
  behind a Settings flag on Nightly first.
- **The flag protects the wrong half, and this is the largest risk in the plan.** That Nightly
  flag guards *remote*. But Phases 1-2 replace ~2000 lines of shipped, incident-hardened Swift
  session code with a fresh Rust implementation for **every local user**, unflagged, before any
  remote code ships. The differential harness proves replay parity on a byte corpus; it proves
  nothing about pty ownership, exec-failure detection, or the alt-screen repaint on real hardware
  with real TUIs. Mitigation: keep the Swift daemon **selectable** for at least one release (the
  existing `backgroundSessions` preference is the natural place for a third state), dual-run them
  during development, and write down the rollback before Phase 1 lands. Tracked as open question 14.

(15, not ~200), gix already vendored via jj-lib, "the only network code is the self-updater", and
premise 3's local dividend having already shipped. Plus one flat contradiction (cross-machine
reattach versus locally-persisted session identity) and the undefined relay binary. It also named
five subsystems the draft had missed entirely — `VCSWriting`, the file viewer and tree, the `gh`
badges, `TerminalLinkOpener`'s cwd, and `VCSWorkroomMissing`.

**Round 2 (scored 7/10),** on the revised text plus the new Provider Decision. It confirmed round 1's
corrections landed with no stale claims left behind, and found one further false code claim — the
`VCS.provider(for:)` injection count, which was six and is actually four, with the miscount hiding
the one call site that has no seam. Its substantive finding was that the Provider Decision had been
*bolted on rather than propagated*: premise 5 unrevisited, Phase 0's item list not updated, the
fork-collision analysis naming something that cannot happen, the headline feature depending on the
wrong trait, the fork path silently losing CI coverage, and the driver's execution location
unstated. All of those are now fixed above, along with two credential holes (repo-admin permission,
and the GitHub API versus git distinction) that would have blocked week one on ordinary org repos.

**After round 2, a design change (not a review finding).** The author's constraint that this be
provider-*agnostic*, not merely provider-pluggable, shrank the driver from six methods to four,
moved idle-policy defeat and port forwarding into agent services, replaced the two-branch creation
strategy with a single `deriveFromBase` sequence, and fixed the build order so the portable path
ships before any accelerator. It also closed round 2's CI gap as a side effect.

**Round 3 (scored 6/10 — down from 7), on that revision.** It judged the propagation far cleaner
than round 2's, but found the reframe had **broken the mechanism twice**, both provable from this
repo's own code rather than from provider claims:

- **The wakefulness translator cannot run lid-closed**, because it is client-side and the Mac is
  asleep — inert in the one state the feature exists for. Now OQ17, and the retraction of the
  "only `maxLifetime` is a gate" claim follows from it.
- **The busy signal is wrong in both directions**, with false-busy being a remote workroom's default
  state (an agent at its prompt is a non-shell foreground pgrp forever), which would delete the cost
  property the provider was chosen for. It also cited `SessionPTY` as proof the pgid read is sound
  while that file's own `terminationTargets` comment documents the `setsid` escape. Signal
  replacement specified in Phase 2; OQ19.
- **Scrollback durability returns an empty buffer for the case it was invented for** — the replay
  buffer empties on alt-screen entry, so every full-screen program has nothing to persist.
  Rescoped to primary-screen only.
- Plus: premise 6's admin-permission hole documented but never resolved (now OQ20 candidates
  listed), `create` orphaned by the one-creation-path rule, deletion-vs-selectable contradicting
  across two sections, a spike item measuring the wrong lever, and **six file:line claims that did
  not hold** — including one that inverted an already-fixed arch bug into a standing trap, and an
