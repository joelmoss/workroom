# Design: First-time boxd setup in the app, on a shared remote-setup sheet

Generated by /office-hours on 2026-10-13
Branch: master
Repo: joelmoss/workroom
Status: APPROVED
Mode: Builder

## Problem Statement

A user who has never set up boxd gets no help from Workroom:

- **CLI missing.** The boxd entry in the sidebar's New Workroom menu and in the New Workroom picker is
  greyed out with "not installed" (`RemoteWorkrooms.unavailability(of:)`,
  `macapp/WorkroomApp/Core/RemoteWorkrooms.swift:84`). Nothing on that path says where to get it.
- **Signed out.** The create calls `RemoteHosts.key(for: .boxd)` →
  `BoxdHostDriver.signedIn()`, which runs `boxd auth --json` with a 120 s timeout. Measured on boxd
  0.2.23: signed out, that command does not fail. It prints "Not logged in. Let's fix that.", tries
  to open a browser at `https://app.boxd.sh/?session=<uuid>`, and blocks on "Waiting for
  confirmation...". So today a signed-out create most likely opens a boxd sign-in tab unannounced
  behind a spinner, then either carries on (if the user signs in within 120 s) or fails with
  "timed out after 120s. Sign in with `boxd auth login`." (Inferred from the CLI probe; the browser
  launch itself was blocked by the probe's sandbox and has not been watched in the app.)
- **GitHub not connected.** The machine is created, then the clone fails minutes in, and the error
  sheet adds `Place.credentialHint`: "Connect it with `boxd manage integrations connect git`."

exe.dev already solves the same problem with `ExeDevSetup` + `ExeDevSetupSheet` (#454, merged
2026-10-13). boxd should get the same experience.

## What Makes This Cool

Picking boxd for the first time, with nothing installed, ends in a working boxd workroom without the
user ever opening a terminal: Install, Sign In and Connect GitHub are buttons. Each step is checked
from boxd itself, ticks itself off, and Create Workroom resumes the create the sheet interrupted,
with the same project, base branch and split placement.

## Constraints

- **Every boxd command that needs an account starts the browser login when signed out**, not just
  `auth`: `manage integrations list --json` and `manage billing --json` do the same (measured, temp
  `HOME`). No check may run one of these unguarded.
- **An explicit token never starts the login.** `boxd --token <bad> auth --json` exits 1 with
  "error: authentication failed: the token from --token / BOXD_TOKEN is invalid or expired";
  `BOXD_TOKEN=<bad> boxd manage integrations list --json` exits 1 with "invalid or expired session"
  (measured, outside the sandbox: the token path dials `boxd.sh:9443` directly).
- **Stored credentials** are `$HOME/Library/Application Support/boxd/credentials.json`, shaped
  `{token, api_url, user_id, cli_name}` (key names read from the owner's file; values not read).
  This is boxd's private file, not a documented contract.
- **`manage integrations list --json` shape** (observed 2026-10-13 on the owner's signed-in account):
  `{"agents":[...],"integrations":[{"class":"private","configured":true,"connected":true,
  "connected_by":"Joel Moss","id":"git","manageable":true,"mcp":false,"name":"Git"},
  {"class":"shared","configured":true,"connected":false,"connected_by":"","id":"git",...}],
  "toolkit_connections":[]}`. The user's own GitHub sign-in is the `id: "git"`, `class: "private"`
  entry; the `class: "shared"` one is the org's. An unconnected private entry has only been seen in
  its shared form (`connected: false`, `connected_by: ""`), so a fresh account's exact output is part
  of the pre-code probe.
- **Where Workroom runs the boxd binary:** only `BoxdHostDriver.cli(...)`
  (`macapp/Packages/HostDrivers/Sources/HostDrivers/BoxdHostDriver.swift:337`), which every driver
  operation (create, delete, sleep and status checks, the crashed-create sweep, `signedIn()`) goes
  through. Panes, `exec`, `openStream` and attach use plain `ssh` with details read from boxd's block
  in `~/.ssh/config` and `~/.ssh/known_hosts` (`SSHDetails`); they never run boxd.
- **`boxd auth login --json` prints no JSON.** stderr carries the sign-in URL; boxd launches the
  browser itself and blocks until confirmed. `boxd manage integrations connect git` is the same kind
  of blocking browser flow.
- **Install** is `curl -fsSL https://boxd.sh/downloads/install.sh | sh`, to `~/.local/bin/boxd`, no
  sudo; `RemoteHosts.boxdCandidates` already looks there first, and `RemoteHosts` already re-resolves
  the CLI per create ("installing it later takes without a relaunch").
- Owner decisions carried over from #454: a check that errors or gives an unknown answer does not
  block Create (boxd's own error decides); GitHub must be connected even for public repositories,
  because pushing needs it.
- Out of scope (owner choice): connecting Claude Code / Codex integrations on the user's machines.

## Premises

1. One shared remote-setup design serves exe.dev and boxd: a model per provider, checked from the
   provider, polled with 3 s to 30 s backoff, `confirmedThisLaunch`, presented by the create gate in
   `AppStore+WorkroomCreation`.
2. boxd's steps are Install, Account, GitHub (`git` integration). A Billing step is added only if a
   fresh-account probe shows one is needed.
3. "not installed" stops greying out the boxd entry: picking boxd opens the sheet, Install first.
4. Checking sign-in must never start boxd's interactive login; fixing today's check is part of this
   work.
5. A check that can't answer doesn't block Create.
6. Install runs boxd's official installer only on an explicit click, and says where it installs.

## Cross-Model Perspective

Codex (cold read, gpt-6.1-sol, 2026-10-13):

- **High:** "The CLI turns an observation into an action." The account check needs a driver fix,
  not just a sheet, because `signedIn()` also feeds the org and account checks before create, delete
  and sweep. Suggested, in order: inspect local credential state without launching boxd (no file and
  no effective `BOXD_TOKEN` means signed out; unreadable or unfamiliar content means unknown, never
  signed in); validate through an explicit token, which it asked to be proven; or get an upstream
  non-interactive status command. Killing the process after "Waiting for confirmation" can't undo a
  browser launch that already happened.
- **Medium:** challenged premise 2's GitHub requirement for public repositories. Not adopted: the
  owner already decided for exe.dev that GitHub is required because pushing needs it.
- **High:** prove the auth boundary first (missing, corrupt, expired and valid credentials, token
  overrides, network failure, org switches), then a typed `signedOut / signedIn(account, org) /
  unknown(reason)` observation; keep login a separate, cancellable operation started only by the
  Sign In button, and never let polling start another login.

Its token suggestion was probed in-session and holds (see Constraints).

## Approaches Considered

### Approach A: Sibling sheet with shared step chrome (recommended in session, not chosen)

A new `BoxdSetup` and `BoxdSetupSheet` beside the exe.dev pair, sharing only the step row and
indicator view. Lowest risk to the just-shipped exe.dev flow; a third provider would copy again.

### Approach B: One remote-setup protocol (CHOSEN)

One protocol, one presenter and one sheet shell that exe.dev and boxd both fill. Described below.

### Approach C: Terminal-led sign-in

Ruled out: it puts CLI text in front of a new user where exe.dev users get buttons, which is not the
zero-terminal version the owner chose.

## Recommended Approach

Approach B, the owner's choice: polling, backoff and launch-confirmation written once, and a third
provider slots in. It accepts reworking `ExeDevSetup` and its sheet shortly after #454 merged, so the
exe.dev flow must come out of this behaving exactly as it does today.

### 1. Driver: a non-interactive boxd account check (fixes today's bug on its own)

In `BoxdHostDriver`:

- `func account() async -> AccountState` with `signedOut`, `signedIn(Account)` and
  `unknown(String)`.
  - No `BOXD_TOKEN` in the environment and no credentials file → `signedOut`, with no CLI call.
  - A credentials file Workroom can't read → `signedOut`, with the reason "boxd's sign-in can't be
    read", never `unknown` or `signedIn` (boxd itself starts its login for such a file; see the guard
    below). The file is read leniently: any JSON object with a string `token` is readable, and
    every other key is optional, so only boxd dropping or renaming `token` breaks the read.
  - Otherwise run `boxd auth --json` with `BOXD_TOKEN` (and `BOXD_API_URL` when the file's
    `api_url` is not boxd's default) set from the file, so an expired session fails with exit 1
    instead of opening a browser. Exit 1 with boxd's "invalid or expired" wording → `signedOut`
    ("your boxd sign-in expired"); any other failure → `unknown`.
- Every `cli(...)` call goes through the same guard, which reads the credential once per call:
  - **Absent** (no `BOXD_TOKEN`, no credentials file): throw a signed-out `HostDriverError` without
    running boxd. boxd would start its login in exactly this state, so this is the case the guard
    exists for.
  - **Readable**: run boxd with `BOXD_TOKEN` (and `BOXD_API_URL` if needed) from the file, so an
    expired token fails with exit 1 instead of opening a browser.
  - **Present but unreadable** (truncated, not JSON, or a shape Workroom doesn't know): treated like
    absent, so boxd is not run. Measured 2026-10-13 with a throwaway `HOME`: a truncated file,
    `garbage` and `{"foo":1}` each made `boxd auth --json` print "Not logged in. Let's fix that." and
    start the browser login. The Account step says boxd's sign-in can't be read and offers Sign In,
    which rewrites the file.
  - **Still unreadable after a successful Sign In** (`boxd auth login` exits 0, the file still has no
    string `token`): the guard still never runs boxd without a token, because an unreadable file is
    exactly what makes boxd start its login. The Account step says boxd's sign-in format has changed
    and Workroom needs an update, and the create stays blocked. This is a deliberate exception to
    "unknown doesn't block": the alternative risks a surprise browser login on every boxd call,
    including background sleep checks and sweeps. Asking boxd for a documented non-interactive flag
    (Open Question 3) removes the dependency.
  This keeps create, delete, sleep checks and the crashed-create sweep (#373) from launching a login,
  since `cli(...)` is the only place Workroom runs boxd (see Constraints).
- **The interactive commands bypass the guard on purpose.** Sign In (`boxd auth login`) and Connect
  GitHub (`boxd manage integrations connect git`) run through a separate, cancellable launcher, with
  the same `HOME` as `cli(...)` and with no `BOXD_TOKEN` or `BOXD_API_URL` set, so a stale token
  can't override the login being made and boxd writes the new credentials where `account()` reads
  them. The installer runs with the same `HOME` and nothing else added. Only these three are started
  by a click; nothing else in Workroom runs boxd outside `cli(...)`.
- `signedIn()` becomes a thin wrapper over `account()` for its existing callers, keeping its
  "Sign in with `boxd auth login`" wording where no sheet is in front of the user.
- The credentials path derives from the `HOME` the CLI runs with, so a dev harness can point boxd at
  a throwaway identity (see Next Steps).

### 2. Shared remote-setup layer

- `protocol RemoteSetup: AnyObject, Observable` (`@MainActor`): `title`, `intro`, `isReady`,
  `refresh()`, `cancel()`, and a `steps` list of `SetupStepState` (`locked`, `current`, `waiting`,
  `done`) with titles, which the shell's indicators read.
- `SetupPoller`: the 3 s to 30 s backoff loop, `pollID` and cancellation, lifted out of
  `ExeDevSetup.poll()` unchanged. Each model supplies `isWaiting` and `checkWaitingSteps()`.
- `RemoteSetupSheet<Setup: RemoteSetup, Steps: View>`: the header, the step list with indicators,
  Cancel (`.cancelAction`) and Create Workroom (`.defaultAction`, disabled until `isReady`), and
  `.onDisappear { setup.cancel() }`. Each provider passes its own step content through a
  `@ViewBuilder`. exe.dev's step content (key creation, email, in-sheet terminal, plan, GitHub) moves
  into `ExeDevSetupSteps` with no wording or behaviour change.
- `PendingRemoteSetup { project, splitAnchor, place, setup: any RemoteSetup }` replaces
  `PendingExeDevSetup`; `ModalState.hasModalPresentation` counts it; RootView keeps one
  `.sheet(item:)`. The create gate in `createRemoteWorkroom` becomes one call:
  `RemoteSetups.needed(for: place, ...)`, returning nil (ready) or the setup to show, after the
  project checks as today, so nobody installs boxd for a project boxd can't take.
- `confirmedThisLaunch` stays per provider, keyed by provider in `RemoteSetups`.

### 3. boxd's steps (`BoxdSetup` + `BoxdSetupSteps`)

- **Install.** Shown only when `RemoteHosts.boxdExecutable()` is nil. Copy: what boxd is, that
  Workroom runs boxd's own installer, and that it installs `boxd` to `~/.local/bin` with no admin
  rights. "Install boxd" runs the install command as a child process (no terminal) with a spinner;
  success re-resolves the executable and moves on, failure shows the installer's last error line and
  "Try Again". It never runs without the click.
- **Account.** From `account()`. `signedOut` → "Sign In" runs `boxd auth login` as a cancellable
  child process, which opens the browser itself. The step shows "Finish signing in in your browser"
  and, once the URL is parsed from stderr, an "Open the sign-in page again" link. The process exiting
  0 re-checks and ticks the step. Done shows the account and the active org (boxd's org name).
  Cancel and closing the sheet kill the login process. Polling only re-reads `account()` and never
  starts another login. `unknown` shows its reason under the step with both "Sign In" and
  "Check Again", and counts as ready for Create (the owner's rule: boxd's own error decides).
- **GitHub.** Locked until signed in. Checked with `manage integrations list --json` (through the
  guard): done when the `id: "git"`, `class: "private"` entry has `connected: true` (shape observed,
  see Constraints). Needed when the list decodes but has no connected private `git` entry, whether
  the entry says `connected: false` or is missing, so a fresh account whose list holds only the
  shared entry, or none, is offered Connect GitHub. Only output that doesn't decode as an
  `integrations` list counts as unknown, which doesn't block Create. The fresh account's actual
  output is recorded in the pre-code probe. "Connect GitHub" runs
  `boxd manage integrations connect git` the same way as Sign In. A check that errors shows its
  error and "Create Workroom will still try", as exe.dev does.
- **Billing (conditional).** Added only if the fresh-account probe shows a new account can't make
  machines. It would read `manage billing --json` and run `boxd manage billing connect` (Stripe).
- The menu and picker stop showing "not installed": `unavailability(of: .boxd)` returns nil, and the
  sheet's Install step takes over. `Failure.boxdNotInstalled` stays for a CLI removed mid-create.

## Open Questions

1. **Does a brand-new boxd account need a payment method before it can make a machine?** This decides
   the Billing step. Probe with a fresh account (owner: "Not sure, probe it").
2. **Does a stored but expired session start the login too?** The design avoids the question by
   always passing the token explicitly, but it should be confirmed. (A corrupt file does start it:
   measured, section 1.)
3. **Relying on boxd's private credentials file.** Workroom needs only a string `token` from it.
   If boxd drops or renames that key, boxd creates are blocked with "Workroom needs an update" until
   Workroom follows (section 1), by choice over risking surprise logins. A documented non-interactive status flag from boxd (for example
   `boxd auth --non-interactive`) would remove the dependency. Worth asking boxd for.
4. **Does the installer run cleanly from a GUI app** (no TTY, Finder's minimal `PATH`, `curl`
   present)? Probe before building the Install step.
5. **Multiple orgs.** The sheet shows the active org but doesn't let the user pick one. Fine for a
   first-time user (they have only their own org); revisit if org choice becomes a request.

## Success Criteria

- A Mac with no boxd CLI and no boxd account picks boxd in New Workroom and ends with a running boxd
  workroom without opening a terminal.
- No boxd command Workroom runs ever opens the browser login unless the user clicked Sign In
  (checked with a throwaway `HOME`: signed out, expired token, corrupt credentials file).
- The exe.dev setup flow behaves exactly as before the refactor (same steps, wording, polling and
  Create resume); its existing tests pass unchanged or are moved, not weakened.
- A boxd account that is already ready never sees the sheet, and later creates in the same launch
  skip the checks.
- Unit tests cover `account()` (no file and unreadable file → `signedOut`, valid → `signedIn`,
  expired → `signedOut`, other failure → `unknown`),
  `BoxdSetup`'s step states and `SetupPoller`'s backoff.

**Problem**

### R3-2 — feasibility (blocking)

**Problem**
